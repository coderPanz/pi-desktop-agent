# 子应用构建（Sub-app Builder）设计方案

> 状态：**设计稿，未实现**。本文只写要做什么、为什么这么做、边界在哪；接口以代码为准，实现后回填。M1 的产物是用户本机显式确认安装的“本地自动化工具”，**不是安全沙箱，也不是可分发插件格式**；正式隔离执行以 M3 为准。
> 与既有文档的关系：取代 [`技术方案.md`](知识中心/技术方案.md) 的 D10「工具自举」，并把 D11「智能 UI」收进本模块的界面层。
>
> 标「已核实」的来自本仓库源码或 `node_modules/@earendil-works/pi-durable@1.4.0` 的 `.d.ts`；标「待验证」的必须先做实验。

---

## 1. 定位

**出厂只有「对话」和「笔记/知识库」。其余能力由用户说出来，Agent 造出来，装上去。**

```
用户：我要一个能把工作区里的 markdown 按标签统计的功能
  ↓
Agent 生成「子应用」：能力（工具/任务）+ 界面（可选）+ 数据（文档定义）
  ↓
静态校验 → 子进程试跑 → 用户确认安装
  ↓
侧栏出现「标签统计」，工具也挂进当前会话
```

三层含义，别混用：

| 说法 | 含义 |
|---|---|
| 工具自举（旧） | 只生成一个 tool |
| **子应用（本文）** | 能力 + 界面 + 数据，一个可安装/启用/禁用的整体 |
| 插件市场 | 不做 |

### 1.1 边界（V1 明确不做）

- 不做在线市场、不做远程安装：M1 只接受当前用户在本机对话中生成的候选包；不导入、下载、分享或同步第三方 `tool.mjs`
- 不做 npm 依赖安装：子应用零依赖，不允许 `import`
- 不做子应用之间的依赖与相互调用
- M1 不开放工作区写入、网络与命令执行；M3 再按能力 profile 强制开放
- 不做卸载已安装子应用的历史数据（只下架能力，数据留给用户手动清）

---

## 2. 三个平面

子应用 = 三个平面的合集，可以只做前两个：

| 平面 | 产物 | 落点 | 谁执行 |
|---|---|---|---|
| **能力** | `tool.mjs`（工厂，零依赖） | `registry.install()` 热挂载 | 受限子进程（M3）/ 主进程（M1，见 §4 风险） |
| **界面** | `ui.json`（受控 DSL） | 渲染进程用固定组件集渲染 | 渲染进程 |
| **数据** | `docs`（文档 kind 声明） | pi-durable `defineDoc` | 主进程 |

**V1 只做「能力」**；「界面」在 M2（§10）接入。原因见 §10.1：界面机制是新东西，先证明"对话造能力"闭环。

## 3. 产物格式

```
<数据根>/subapps/<slug>/
├─ versions/<version>/
│  ├─ manifest.json       # 必需：身份、版本、能力申请、校验和
│  ├─ tool.mjs            # 可选：能力（导出工厂）
│  ├─ ui.json             # 可选：界面（受控 DSL，M2）
│  └─ README.md           # 可选：给人看的说明（模型写）
└─ history/<version>.json # 每次激活的 manifest 快照（审计用）
```

生效版本以 `app.subapps[].version` 为唯一事实来源；版本目录一经落盘不原地修改。升级先将候选版本写入新的临时目录，再原子 rename 为 `versions/<version>/`，因此可在切换失败时恢复先前版本。

### 3.1 manifest

```jsonc
{
  "schemaVersion": 1,
  "slug": "tag-count",                 // 目录名，同时也是 id 前缀
  "title": "标签统计",                  // 侧栏显示名（M2 才有界面）
  "version": 3,                        // 安装器填写的单调递增最终版本
  "createdAt": 1764000000000,           // 安装器填写

  // 能力申请：安装时逐条展示给用户确认
  "requestedCapabilities": {
    "tools": ["user.tag_count.count"], // 会挂进 registry 的工具名
    "readPaths": ["<workspace>"],      // 申请读取范围（相对工作区）
    "writePaths": [],                   // M1 必须为空；M3 才可申请写入
    "network": false,                   // M1 必须为 false；M3 才可申请出网
    "runsCommands": false               // M1 必须为 false；M3 才可申请命令执行
  },
  "enforcement": "m1-local-confirmed", // 由安装器写入；M3 改为 sandbox-profile，不可伪装为已隔离

  // 界面声明（M2）
  "ui": { "kind": "dsl", "dslVersion": 1, "icon": "chart" },

  "checksum": "sha256:…"               // tool.mjs + ui.json 的内容哈希
}
```

**校验规则（安装时强制）**

- `slug` 只允许 `[a-z0-9-]{2,40}`，且不能与内置扩展同名（`coding` / `kb` / `subapps`）
- `version` 由安装器分配：候选包不携带最终版本；安装器按已安装版本生成严格递增的 `nextVersion`
- `checksum` 必须等于 `sha256(tool.mjs bytes + "\0" + ui.json bytes-or-empty)`；与实际文件不符 → 拒绝（防止安装后被外部改动）
- `requestedCapabilities.tools` 必须全部以 `user.<slug规范化>.` 开头，且与 `tool.mjs` 导出的一致；装载器必须在 install 前检查当前 registry snapshot 并拒绝跨子应用同名工具（registry 本身允许重名，不可依赖其拒绝）
- M1 拒绝 `writePaths` 非空、`network=true`、`runsCommands=true` 的候选包，并且装载器只注入只读 API；这不是对主进程 JavaScript 的强制隔离，不能以“声明”冒充“已强制约束”

## 4. 信任与隔离

这是整个模块的地基，先定死。

### 4.1 代码在哪跑

| 阶段 | 位置 | 理由 |
|---|---|---|
| 静态校验 | 主进程（纯文本分析，不执行） | 便宜 |
| **试跑** | **受限子进程**（Seatbelt、临时工作区、拒绝网络） | 只做可加载、可创建、最小输入可执行的 smoke，不授予主进程权限 |
| 正式调用（M1） | 主进程（`registry.install` 后由 Harness 调度） | 现有架构；**不构成隔离执行** |
| 正式调用（M3） | tools worker（Seatbelt 子进程） | 目标形态；按能力 profile 硬性限制 |

**M1 的风险必须写清楚**：静态规则和受限试跑都不是 JavaScript 安全边界。生成的工具在主进程里执行，原则上能取得与桌面应用同等的权限；“只通过 `api.env`”是源码契约和生成规范，不是 M1 可证明的强制限制。M1 仅可接受当前用户本机生成并显式确认安装的工具，绝不接第三方来源。安装页必须说明“正式执行尚未隔离”；M3 才把文件、网络与命令能力收进内核沙箱。

### 4.2 生成代码的静态约束

- **零依赖**：`tool.mjs` 不允许任何 `import` 语句（工厂从参数拿 `Type` / `defineTool`，见 §5.2）
- 拒绝常见高风险标识符：`process`、`require`、`eval`、`Function`、`import(`、`child_process`、`globalThis.process`；M1 采用保守词法扫描并拒绝模板字面量，避免漏检插值表达式
- 大小上限：单文件 256KB；并限制试跑与正式调用的超时、输出大小、读取文件数和总读取字节数
- 校验失败 → 不进入试跑，直接把理由返回给模型让它改

这些是**生成质量与误用防护**，不是可信安全沙箱；不得据此允许第三方代码或放宽 M1 的来源边界。

### 4.3 安装确认

- **只能由用户手势触发**：Agent 生成完 → 界面弹「安装确认」（展示 title / 工具名 / 申请能力 / diff / 静态规则与 smoke 结果）→ 用户点「安装」
- 模型不能自己调 `install`（安装通道只挂在 IPC 上，且要求 `isTrustedSender` + 用户点击携带的一次性 `installToken`）
- M1 安装页必须明确“将在桌面应用主进程执行，正式执行尚未隔离”；用户确认是知情授权，不是技术沙箱
- smoke 失败默认阻止安装；只有用户再次明确确认“仍然安装”才允许强制安装，并记录 `smoke: failed`

## 5. 后端设计

### 5.1 装载点

```
DesktopRuntime.open
  └─ createPiRegistry({ extensions: [coding, subapps 加载器] })
       └─ 启动时：读 app.subapps → 逐个 load → registry.install（失败标 failed，不阻塞启动）
```

- `Registry.install/uninstall` **支持运行时装卸（已核实）**，所以"装完即用、禁用即摘"不需要重启
- 装载失败清单写入 `app.subapps[].status = "failed"` 与原因，界面可看

### 5.2 工具源码契约（已定死，模型必须照这个写）

```js
// 不 import 任何东西；依赖由装载器注入。
// M1 只接受 tools；actions 为 M2 预留，未实现前必须为空对象。
export default function create({ Type, defineTool }) {
  return {
    tools: [
      defineTool({
        name: "user.tag_count.count",
        description: "统计工作区 markdown 里出现最多的标签",
        parameters: Type.Object({ top: Type.Optional(Type.Number()) }),
        async execute(args, api, context) {
          // M1 约定仅通过只读 api.env 访问工作区。
          const files = await api.env.listDir(".", context)
          return { output: [{ type: "text", text: "…" }] }
        },
      }),
    ],
    actions: {},
  }
}
```

返回值必须是 `{ tools, actions }`：`tools` 是非空数组，`actions` 是以 action 名为键的函数表。M1 要求 `actions={}`；M2 才启用它，避免届时依赖一个未定义的隐式导出。装载器在创建 extension 前校验工具名、数量、描述和参数 schema，并以实际导出反查 manifest。

理由：从 `<数据根>/subapps/` 加载时 `@earendil-works/pi-durable` 不在其解析链上；注入依赖同时解决打包后的解析问题。

- 加载：`import(pathToFileURL(file).href + "?v=" + version)`（版本进 URL 绕开 ESM 缓存）
- 扩展名固定：`createExtension({ name: "subapps:<slug>", tools })`

### 5.3 文档（数据平面）

新增一个 session 级文档：`app.subapps`（kind 一旦写入即契约）。

```ts
type AppSubapp = {
  slug: string
  title: string
  version: number
  previousVersion?: number  // 最近一次可恢复的已安装版本
  enabled: boolean            // 用户可禁用（下架能力，保留文件）
  status: "ready" | "failed" | "disabled"
  error?: string              // status=failed 时的原因
  requestedCapabilities: {
    tools: string[]
    readPaths: string[]
    writePaths: string[]
    network: boolean
    runsCommands: boolean
  }
  enforcement: "m1-local-confirmed" | "sandbox-profile" // 当前实际执行保障，不由候选包自由填写
  smoke: "passed" | "failed" | "skipped"
  installedAt: number
}
type AppSubapps = { items: AppSubapp[] }
```

**为什么用 session 级而不是 conversation 级**：子应用是"这台机器上装了什么"，与具体会话无关；分叉会话不该带出不同的子应用清单。

### 5.4 安装流程（带补偿的切换，不伪称跨介质原子事务）

```
1. 校验候选 manifest（§3.1）+ 静态检查（§4.2）；安装器分配 nextVersion、createdAt、规范 checksum
2. 写入临时目录；从临时目录 import，校验工厂返回值与 manifest 一致
3. 受限子进程 smoke：在临时工作区以最小参数调用一次，超时 30s、输出截断
4. 用户确认（IPC 往返，带 installToken）；smoke 失败须二次明确确认
5. 原子 rename 临时目录到版本目录；保留现有生效版本，不先删除
6. import 新版本并 registry.install；成功后再卸载旧 extension
7. harness.commit 写 app.subapps（升级时同时写入 `previousVersion`）；成功后将 manifest 快照写入 history
```

文件系统、registry 与 durable 文档不是同一个事务，必须显式补偿：第 5–7 步任一失败时，卸载新 extension、恢复旧 extension、删除新版本目录或标记为未激活；只有旧版本成功恢复不了时才写入 `status=failed`。启动时清理未激活的临时目录，并以 `app.subapps` 的 `version` / `previousVersion` 记录重建或回退 registry。

### 5.5 升级与禁用

| 操作 | 语义 |
|---|---|
| 升级 | 同 slug 由安装器分配新 version：先验证并安装新 extension，成功后才卸载旧 extension；旧版本目录保留，`history/<version>.json` 留审计快照 |
| 禁用 | `registry.uninstall` + `enabled=false`；所有版本文件保留，可再启用 |
| 删除 | 需要二次确认；先 `uninstall`，再删目录，再从 `app.subapps` 移除。**已产生的用户数据不动** |
| 回退（内部恢复） | 安装/升级失败时以 `app.subapps.previousVersion` 恢复前一版本并重新 install；V1 不暴露用户手动回退 UI |

### 5.6 安装 / 卸载后刷新系统提示词

**目标**：子应用装好之后，用户在「对话」里提到相关场景时，主对话**直接调用**它的能力，而不是回答"我没有这个功能"。

现状：`coding` 的 `project` 小节每次请求前渲染（`PromptSection.render`），缓存只按文件 mtime。
子应用清单来自 `app.subapps`（文档），**与工作区文件无关**——所以必须在清单变化时让提示词失效。

设计（M1 就要有，否则新手装完用不上）：

```
subapp.install / setEnabled / remove 成功
  → 写 app.subapps（一个 commit）
  → 发布 registry（工具随之装卸）
  → 使「子应用清单」小节缓存失效（版本号 +1）
       ↓
下次请求渲染 system prompt 时带上：
  已安装能力：user.tag_count.count（标签统计）、user.md_count.count（md 文件计数）
  用法：按工具说明直接调用；不确定参数时先 subapp.list 查
```

- 新增一个 `subapps` 小节（`PromptSection`），只列同时满足 `enabled && status=ready`、且确实存在于当前 `RegistryReader.snapshot()` 的工具名 + 一句话说明
- 缓存键 = `app.subapps` 内容 hash + registry snapshot 工具名 hash：任一变化即重渲染，没变直接用上次的（避免每次请求都读文档）
- **不要**把工具 JSON schema 塞进提示词（模型本来就能看到工具列表），只给"有这些能力"的事实
- 停用/删除后同样要失效，否则模型会调用一个已经不存在的工具（表现为 `tool_unavailable`）

**为什么单独一节而不是塞进 `project`**：`project` 描述工作区（文件、脚本、提交规范），子应用是"这台机器装了什么"，
两者失效条件不同；混在一起会导致改一个文件就把子应用清单也重算一遍。

**待验证**：同一请求里 `registry.install` 之后工具列表是否立刻对下一次请求生效（`RegistryReader.snapshot()` 每次取最新，预期生效，但要实测）。若不能保证，安装成功的 UI 不得承诺“同一轮可调用”，而应在下一次请求前重建 snapshot。

## 6. 前端设计

### 6.1 现状与缺口

渲染进程只 import 静态组件，ESLint 禁止它 import `@pi/core` / `node:*` / `pi-durable`。**没有任何"加载外部 UI"的通道**——这是本模块最大的新增面。

### 6.2 侧栏与路由（M2）

- 侧栏在「最近会话」之上插入一段「子应用」列表（来自 `app.subapps`，仅 `status=ready`）
- 点击 → 主区域从「对话」切到「子应用页面」（`App.tsx` 顶层的 `view` 状态：`conversation | subapp:<slug>`）
- 子应用页面只做两件事：渲染 DSL、把交互变成 IPC 调用

### 6.3 DSL 渲染器

**不走"生成 React 代码"路线**（那等于在主窗口跑不可信代码）。走受控 DSL：

```jsonc
{
  "v": 1,
  "root": {
    "type": "card",
    "children": [
      { "type": "heading", "text": "标签统计" },
      { "type": "table", "columns": ["标签", "次数"],
        "rows": [["sandbox", 12], ["git", 7]] },
      { "type": "button", "label": "重新统计", "action": "refresh" }
    ]
  }
}
```

- 组件白名单（V1）：`card` / `heading` / `text` / `table` / `list` / `button` / `input` / `divider`
- 属性白名单：`type, children, text, columns, rows, label, action, placeholder, value, tone`
- 限制：≤64KB、深度 ≤16、节点数 ≤500、`action` 只能取声明过的 handler 名
- 校验器**先于渲染器存在**：渲染器只接受校验通过的 DSL，不做"边渲染边容错"

### 6.4 交互 RPC 与 UI 状态

```
渲染进程点按钮
  → IPC "subapp.action" { slug, action, payload, actionId }
  → 主进程从 §5.2 的 actions 表调用声明过的 handler
  → handler 返回完整 DSL
  → 主进程先校验 DSL，再推送给渲染进程整体替换当前页面
```

M2 初版不提供表达式、模板求值、任意 patch 或 HTML；“完整 DSL 替换”是唯一的刷新语义，避免另造一套数据绑定语言。`ui.json` 是初始 DSL；进入页面时读取它，交互后仅在内存中保留最后一份通过校验的 DSL。除非后续的数据平面显式声明并定义 schema，**不把动态结果写进 `app.subapps.<slug>.lastResult`**。

幂等：`actionId = randomUUID()`，同一次点击的重试复用；主进程按 `actionId` 去重，并对 action 的输入、执行时长和返回 DSL 大小施加限制。

## 7. 契约（新增 IPC）

| 通道 | 用途 |
|---|---|
| `subapp.list` | 列出已安装（含 failed/disabled），供侧栏渲染 |
| `subapp.preview` | 以 Agent proposal 的 `candidateId` 获取结构化预览（manifest + 源码 + 试跑输出 + 静态检查结果），并只向可信 renderer 签发 token |
| `subapp.install` | 带 `installToken` 的安装（token 由 `subapp.preview` 一次性发放，60s 过期） |
| `subapp.setEnabled` | 启用/禁用 |
| `subapp.remove` | 删除（二次确认由界面负责） |
| `subapp.ui` | 取某个子应用的 DSL（M2） |
| `subapp.action` | DSL 交互（M2） |

推送：`subapp.proposed`（Agent 提交的候选已完成检查，携带 `candidateId`）与 `subapp.changed`（列表或某个子应用状态变化）。

Agent 只能调用内置 `subapp.propose` 提交候选包：它会做静态检查与 smoke、保存主进程候选，但**不会**签发 token 或安装。renderer 收到 `subapp.proposed` 后，才以 `candidateId` 调用 `subapp.preview`。`installToken` 必须绑定候选内容 hash、slug、可信 sender 与过期时间，并且单次使用。`subapp.install` 只接收 token，不接收渲染进程重新提交的 manifest、源码或能力声明，避免预览后的内容被替换。启用已有版本时重新校验 checksum。

## 8. 安全清单（合并后按此验收）

1. 静态检查拦下 `import` / `process` / `eval` / `child_process` 等常见高风险写法（§4.2）；该检查**不得**被当作安全沙箱或第三方代码准入依据
2. smoke 在 Seatbelt 子进程、临时工作区、拒绝网络的环境中运行；它只证明最小路径可跑，不证明正式执行受限
3. M1 只允许当前用户本机对话生成的候选包；安装必须用户手势 + 一次性 token，安装页明确主进程执行风险，模型无法直接调 `subapp.install`
4. M1 拒绝写入、网络与命令执行的申请，只注入只读 API，但不声称能强制约束主进程 JavaScript；M3 才由 worker profile 对获准的读写、网络与命令能力硬性限制
5. checksum 不符 → 拒绝安装；安装后被外部改动 → 启动时标记 `failed`，不加载
6. DSL 全部走白名单校验，拒绝 `javascript:`、HTML 注入、未声明 action、超限节点/深度/大小
7. 加载或切换失败必须恢复前一可用版本；恢复失败时标 `failed` 并停用，不静默降级成“没这个子应用”

## 9. 崩溃与恢复

| 场景 | 行为 |
|---|---|
| 安装中途崩溃 | 候选文件仍在临时目录、`app.subapps` 未提交 → 下次启动清理残留临时目录 |
| 版本目录已落盘但尚未提交 | 新版本不被 `app.subapps` 引用 → 下次启动不加载，并按保留策略清理 |
| commit 后或切换中崩溃 | 重启后按 `app.subapps` 记录的版本重新 install；若失败，尝试前一可用版本并标记原因 |
| 子应用代码被外部改坏 | checksum 不符 → `status=failed` + 原因，界面提示“重新安装或删除” |
| 主进程在工具调用中崩溃 | 沿用现有语义：`replay: unsafe` 的工具不自动重放 |

## 10. 分期

### 10.1 为什么先做 M1

界面机制（侧栏路由 + DSL 渲染器 + 校验器）是**全新的一整块**，且没有现成参考。先做 M1 能验证最重要的一条链：**"用户说需求 → 生成 → 校验 → 试跑 → 确认 → 装完即用"**。这条链不通，界面做得再好也没用。

### M1：能力子应用（无界面）

- 产物：`subapps/<slug>/versions/<version>/{manifest.json, tool.mjs, README.md}`
- 范围严格限定为**只读分析工具**：工具生成 → 静态校验 → 受限 smoke → 安装确认 → `registry.install` → `app.subapps`
- 启动恢复、禁用、删除、升级，以及版本切换失败时恢复前一版本
- **安装后刷新系统提示词**（§5.6）：下一次请求的工具 snapshot 与 prompt 都能看到新能力；只有 snapshot 的实测语义支持时，才承诺同一会话立即调用
- 验收：在对话里说「给我一个统计工作区 md 文件数的工具」→ 安装后下一次请求能调用 `user.md_count.count`；重启后仍在
- 验收：装完后问「用你新装的能力统计一下」→ 模型直接调已安装工具，不需要用户再提供工具名
- 验收：候选包申请写入、网络或命令执行时，M1 安装被拒绝，而不是以未强制的 manifest 声明放行

### M2：界面子应用（受控 DSL）

- 新产物 `ui.json` + handler；侧栏入口 + 页面路由；DSL 校验器与渲染器
- 验收：装一个"标签统计"子应用，侧栏出现入口，点开能看到表格，点「重新统计」后数据刷新

### M3：真隔离

- 生成工具的执行搬进 tools worker（Seatbelt + 能力 profile）
- 验收：子应用里的工具**无法**写到工作区外、无法在 `network:false` 时联网（用现有沙箱用例改造成子应用版）

## 11. 风险与待验证

| 项 | 说明 | 处理 |
|---|---|---|
| M1 生成代码在主进程执行 | 静态规则无法阻止 JavaScript 绕过，原则上仍可能取得应用权限 | 只允许当前用户本机生成、显式确认；安装页明示未隔离；严禁第三方来源；M3 收口 |
| 声明权限与实际权限混淆 | M1 主进程不能证明 `readPaths` 等声明被强制 | M1 拒绝写/网络/命令申请、仅注入只读 API，并将其称为“申请”；M3 以 worker profile 作为唯一强制来源 |
| `import()` 动态加载 ESM | Electron 打包后路径与 asar 可能出问题 | **已验证**：未签名 macOS 目录安装包可从 asar 内主进程加载数据目录版本目录下的 mjs；保留 `pnpm p0:subapps:package` 作为回归验证 |
| ESM 缓存 | 同 URL 二次 import 拿旧代码 | 版本进 URL；开发态与未签名 macOS 目录安装包 P0 均已验证 |
| 试跑与正式执行的差异 | smoke 通过不代表真实数据正确或正式执行受限 | 只报告“最小路径可跑”，不承诺正确性或隔离性 |
| 跨介质切换失败 | 文件、registry、durable 文档没有共同事务 | 不先卸载旧版本；为每步定义补偿与启动恢复（§5.4、§9） |
| 模型生成质量 | 可能写出跑不起来的代码 | 校验失败把原因回给模型，最多重试 3 次后放弃 |
| `app.subapps` 成为契约 | kind 一旦写入不能改名 | 先定字段，再写实现 |
| 提示词与实际能力不同步 | 装了但模型不知道，或已停用仍调用 | §5.6：使用文档 hash 与 registry snapshot hash；停用/删除同样刷新 |

## 12. 与既有模块的接缝

| 模块 | 关系 |
|---|---|
| `coding` 扩展 | M1 装载器只注入其受控的只读 `ExecutionEnv` 能力，不注入 `write` / `bash`；这不替代 §4 所述主进程风险。M3 再按 profile 开放并接入改动卡片 |
| 知识库 `kb` | M1 子应用可以读 `kb/wiki/`（只读），不能写 `raw/` |
| 智能 UI `smartui` | 本方案的 M2 消化了它的 DSL 设想；`smartui` 只保留"对话内联渲染"的定位，不再单独做一套 |
| 沙箱 | 试跑（M1）与正式执行（M3）都依赖现有 Seatbelt 方案；`network:false` 直接复用 `PI_SANDBOX_NET=deny` |
| 改动卡片 | 子应用写工作区时同样计入「本轮改动」，可撤销 |
| 系统提示词 | 安装后经 `subapps` 小节把「有哪些能力」告诉主对话，见 §5.6 |

## 13. 架构总览

```text
┌──────────────────────── 渲染进程（Renderer）────────────────────────┐
│ 对话：提出需求 → 生成预览 → 用户安装确认                             │
│ M2：侧栏子应用列表 / SubappPage / 固定 DSL 组件渲染器                 │
└─────────────────────────────┬───────────────────────────────────────┘
                              │ 受类型约束、可信 sender 校验的 IPC
                              ▼
┌────────────────────────── 主进程（Main）────────────────────────────┐
│ SubappService                                                        │
│ ├─ CandidateStore：候选源码、检查结果、一次性 installToken            │
│ ├─ StaticValidator：manifest、命名、checksum、静态规则                │
│ ├─ SmokeRunner：Seatbelt 子进程最小路径测试                           │
│ ├─ Installer：版本落盘、热装卸、升级、补偿与崩溃恢复                  │
│ ├─ SubappLoader：导入 tool.mjs，校验 { tools, actions }               │
│ ├─ ActionDispatcher（M2）：执行 action 并校验完整 DSL                 │
│ └─ PromptSection：以 durable 记录 + registry snapshot 渲染能力摘要  │
│                                                                      │
│ DesktopRuntime → Pi Registry                                         │
│   coding / kb / subapps:<slug> → user.<slug>.* tools                 │
│                                                                      │
│ Harness + durable：session 级 app.subapps                            │
└───────────────────┬──────────────────────────┬─────────────────────┘
                    │                          │
                    ▼                          ▼
      <数据根>/subapps/<slug>/        M1：仅 smoke 受限执行
      versions/<version>/*            M3：tools worker + Seatbelt + profile
```

### 13.1 代码落点

| 架构层 | 现有落点 | 新增/修改方向 |
|---|---|---|
| Runtime / registry | `apps/desktop/src/main/runtime.ts`、`packages/core/src/harness/registry.ts` | 构造 `SubappService`，启动恢复后向现有 registry 热装 extension |
| IPC | `packages/shared-types/src/ipc.ts`、`apps/desktop/src/main/ipc.ts`、主进程 `IpcRouter` | 增加 `subapp.*` 类型、白名单和路由；安装 token 仅由主进程持有候选包 |
| 提示词 | `packages/extensions/coding/src/context.ts` | 新建独立 `subapps` PromptSection，不与 `project` 缓存耦合 |
| 持久化 | `packages/shared-docs/` 与 Harness 文档定义 | 定义 session 级 `app.subapps` 契约及迁移前验证 |
| 前端（M2） | `apps/desktop/src/renderer/` | 侧栏、`SubappPage`、`DslValidator`、`DslRenderer`；不加载外部 React/JS |

### 13.2 运行时链路

```text
模型调用 subapp.propose 提交候选包
  → 静态检查 + 受限 smoke
  → CandidateStore 保存候选内容 hash，推送 subapp.proposed(candidateId)
  → renderer 以 candidateId 调 subapp.preview，取得绑定可信 sender 的 installToken
  → 用户手势提交 installToken
  → 版本目录原子落盘
  → registry.install(subapps:<slug>)
  → harness.commit(app.subapps)
  → registry snapshot / PromptSection 缓存失效
  → 下一次请求即可看到并调用 user.<slug>.*
```

M1 的正式调用仍在主进程，故上图中的静态检查、只读 API 注入和 smoke 都不是安全隔离；它只适用于本机用户显式确认的候选包。M3 将正式执行迁移至 worker 后，才由 capability profile 成为实际权限边界。
