# 工具参数为什么要用 Type.xxx

`Type.xxx` 不是包装，它是生成 **JSON Schema** 的构造函数。工具的参数定义运行时就是一个标准 JSON Schema：

```json
{
  "type": "object",
  "required": ["path"],
  "properties": {
    "path": { "type": "string", "description": "相对工作区根目录的文件路径" },
    "offset": { "type": "integer", "minimum": 1, "description": "起始行号" }
  }
}
```

## 原因：运行时要用，TS 类型在编译后被擦除

工具参数在两个地方被运行时使用：

| 用途 | 需要什么 | 谁在用 |
|---|---|---|
| 告诉模型怎么调用这个工具 | 运行时对象 | 模型请求里的 `tools[].parameters` |
| 校验模型返回的 `arguments` | 运行时对象 | Harness 在 `execute()` 之前校验 |

`pi-ai` 的 `Tool` 类型要求的就是 TypeBox 的 schema：

```ts
export interface Tool<TParameters extends TSchema = TSchema> {
  name: string;
  description: string;
  parameters: TParameters;
}
```

写 `interface ReadFileArgs { path: string }` 无效：接口在运行时不复存在，既发不给模型，也无法用于校验。

## 一份定义，两个产物

`defineTool` 从参数 schema 推出 `Static<TParameters>`：

```ts
async execute(args, api, ctx) {
  args.path;   // string
  args.offset; // number | undefined
}
```

同一个 `Type.Object({...})` 同时提供：

1. **运行时**：JSON Schema，发给模型并用于校验；
2. **编译期**：`args` 的 TS 类型，用于补全与类型检查。

若分开手写 TS 类型与 JSON Schema，两者会漂移：加了参数却忘了改 schema，模型就永远传不进来。

## 关键字的实际作用

以 `read_file` 为例：

| 写法 | 运行时效果 |
|---|---|
| `Type.Optional(...)` | 不进入 `required`；不传不会校验失败 |
| `Type.Integer({ minimum: 1 })` | `offset: 0` 或 `-1` 在进入 `execute` 前被拒 |
| `Type.Integer({ maximum: N })` | 模型传超上限的值被拦，避免一次读爆内存 |
| `description` | 进入发给模型的 schema，是给模型看的说明书，直接影响调用正确率 |

## 为什么用 TypeBox 而不是 zod

- `pi-ai` 显式要求 `TSchema`，并直接 `export { Type } from "typebox"`，两者配套使用。
- TypeBox 的对象本身就是 JSON Schema，可原样发给 provider，无需转换。
- zod 得到的是另一套对象，需要额外转成 JSON Schema 才能给模型。

## 容易踩的坑

`TSchema` 允许写很松的定义：

```ts
Type.Any();     // 等于不校验
Type.Unknown(); // 同上
```

参数写成 `Type.Any()` 等于放弃校验，模型传什么都会进入 `execute`，只能在函数里手写判断。因此工具自举阶段的静态校验会明确禁止 `Any` / `Unknown`。

## 一句话

`Type.xxx` 在运行时描述工具的入参契约：既变成发给模型的 JSON Schema，又变成 `execute(args)` 的 TS 类型，同时给 Harness 提供校验依据。换成 TS 类型或注释都做不到。
