# `busyTimeoutMs` 与 `walAutoCheckpointPages`：SQLite 的等待与 WAL 整理

这两个配置来自：

```ts
export type CreateStorageOptions = {
  readonly busyTimeoutMs?: number
  readonly walAutoCheckpointPages?: number
}
```

它们都是 **SQLite 数据库的底层运行参数**，不是 pi-durable 的会话、任务或模型业务配置。

平时直接：

```ts
await createStorage({
  kind: "file",
  file: "/path/session.sqlite",
})
```

通常不必设置它们。当前项目会将 `busyTimeoutMs` 默认为 `5000` 毫秒；`walAutoCheckpointPages` 未传时则让 pi-durable 的 SQLite 适配器采用自己的默认行为。

---

## 1. `busyTimeoutMs`：数据库被占用时最多等多久

```ts
readonly busyTimeoutMs?: number
```

单位是**毫秒**。

SQLite 同一时刻不能让多个写入操作真正同时修改同一个数据库文件，确保操作的原子性。
若另一连接正写入，当前连接可能遇到“数据库正忙 / 被锁住”。

```text
进程 A：正在向 session.sqlite 写入一条 entry
进程 B：也想写入 task 状态
```

此时 B 可以：

```text
立刻失败：数据库正忙
```

或者：

```text
等待 A 写完、释放占用，再继续
```

`busyTimeoutMs` 就是第二种策略的最大等待时间。

```ts
busyTimeoutMs: 5000
```

表示：

> 数据库暂时忙时，最多等待 5 秒；5 秒内仍不能执行才报错。

### 为什么需要等待

“忙”不一定是错误，可能只是另一个很短的写入事务恰好先开始：

```text
00.000 秒：A 开始写入
00.010 秒：B 尝试写入，发现 A 尚未完成
00.030 秒：A 写完并释放占用
00.030 秒：B 继续写入，成功
```

若超时设为 `0`，B 在 `00.010 秒` 就会失败。设置 `5000` 后，B 能等待 A 完成。

### 不同值的效果

| 设置 | 含义 |
| --- | --- |
| `busyTimeoutMs: 0` | 数据库忙时立刻失败。 |
| `busyTimeoutMs: 5000` | 最多等待 5 秒；本项目默认。 |
| `busyTimeoutMs: 30000` | 最多等待 30 秒；较少忙错误，但调用可能长时间卡住，问题也更晚暴露。 |

### 它不是多进程协作方案

`busyTimeoutMs` 只是 SQLite 遇到临时占用时的等待时间，**不是**让多个 Harness / agent runtime 同时安全写同一个数据库文件的方案。

本项目的设计约定是：

```text
一个 SQLite 数据库文件，只允许一个 Harness 作为写入者。
```

应避免：

```text
Electron 主进程 ─┐
CLI 进程 ────────┼─ 同时打开并写 session.sqlite
测试进程 ────────┘
```

该配置可缓解短暂 SQLite 锁竞争，但不能解决两个独立 runtime 同时调度、同时运行任务带来的高层一致性问题。

## 2. `walAutoCheckpointPages`：WAL 日志多大时自动整理

```ts
readonly walAutoCheckpointPages?: number
```

要理解它，先理解 WAL。

### WAL 是什么

WAL 是 **Write-Ahead Logging** 的缩写，通常翻译为“预写日志”。

启用 WAL 模式的 SQLite 数据库通常相关联两个文件：

```text
session.sqlite       主数据库文件
session.sqlite-wal   写入日志文件
```

写入时，SQLite 通常先把新变更追加到 `session.sqlite-wal`，而不是每次都立刻改动主数据库文件：

```text
写入前：
session.sqlite      主数据
session.sqlite-wal  空或较小

写入后：
session.sqlite      可能尚未合并全部最新内容
session.sqlite-wal  追加了最新变更
```

读取时 SQLite 会综合主文件和 WAL，因此即使新变更暂时还在 WAL，读到的数据仍然正确。

### checkpoint 是什么

持续写入后，WAL 文件会不断变大。

**checkpoint** 是 SQLite 将 WAL 中已稳定的变更合并回主数据库文件，并清理或缩小 WAL 的过程：

```text
checkpoint 前：
session.sqlite      较旧主体
session.sqlite-wal  累积大量新变更

checkpoint 后：
session.sqlite      合并后的新主体
session.sqlite-wal  被清理或缩小
```

### Pages 阈值是什么意思

```ts
walAutoCheckpointPages: 1000
```

表示：

> 当 WAL 累积到大约 1000 个 SQLite 数据页时，SQLite 自动尝试 checkpoint。

这里使用“页数（page）”而不是字节数。一个 page 具体有多少字节取决于数据库设置，常见大小是若干 KiB。

### `0` 的含义

```ts
walAutoCheckpointPages: 0
```

表示关闭“WAL 达到固定页数时自动 checkpoint”的机制。

这不是说 WAL 从此永远不能整理；只是不会由这个大小阈值自动触发。显式操作、关闭数据库或 SQLite 的其他行为仍可能执行 checkpoint。

关闭后要注意：

```text
持续写入
  ↓
WAL 可能持续变大
  ↓
占用更多磁盘空间，重开数据库时可能需处理更多日志
```

少数高频写入场景可能希望自己控制 checkpoint 时机，以降低自动 checkpoint 对某次写入延迟的影响。

## 3. 两项配置的区别

| 配置 | 解决的问题 | 通俗理解 |
| --- | --- | --- |
| `busyTimeoutMs` | 此刻数据库被别的连接占用 | “门被别人占着时，我在门口最多等多久？” |
| `walAutoCheckpointPages` | 写入日志不断累积 | “日志攒到多大时，自动整理进主库？” |

```text
busyTimeoutMs：

写入请求 B
    │
    ▼
数据库正被 A 占用？
    │
    ├─ 否 → 立即执行
    │
    └─ 是 → 最多等 busyTimeoutMs
                    │
                    ├─ A 释放 → B 执行
                    └─ 超时 → B 报错


walAutoCheckpointPages：

不断写入
    │
    ▼
WAL 日志是否达到 N 页？
    │
    ├─ 否 → 继续累积
    └─ 是 → 自动 checkpoint，合并并整理 WAL
```

## 4. 项目代码实际如何使用

```ts
return await openNodeSqliteStorage(target.file, {
  busyTimeoutMs: options.busyTimeoutMs ?? DEFAULT_BUSY_TIMEOUT_MS,
  ...(options.walAutoCheckpointPages === undefined
    ? {}
    : { walAutoCheckpointPages: options.walAutoCheckpointPages }),
})
```

可翻译成：

```ts
return await openNodeSqliteStorage(数据库文件路径, {
  // 调用方未指定时，数据库忙最多等 5 秒。
  busyTimeoutMs: 调用方设置 ?? 5000,

  // 只有调用方明确指定 WAL 自动整理阈值才传入；
  // 未指定则由 SQLite 适配器使用自身默认行为。
  walAutoCheckpointPages: 调用方明确设置时才传入,
})
```

两项默认策略不同：

```text
busyTimeoutMs：项目明确固定默认值为 5000ms。
walAutoCheckpointPages：项目不覆盖，由 SQLite 适配器决定默认值。
```

---

## 总结

> `busyTimeoutMs` 管“数据库临时被占用时等多久”；`walAutoCheckpointPages` 管“写入日志积累到多大时自动整理”。

一般业务开发无需修改它们。只有遇到频繁 SQLite busy 错误，或需要针对高频写入控制 WAL 文件大小、写入延迟与 checkpoint 时机时，才需要调整。
