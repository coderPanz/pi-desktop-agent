# NodeExecutionEnv 和 node:fs 像吗

像，底层就是 `node:fs` + `node:child_process`。但它是一层**有约定的包装**，用法差别很大。

## 对应关系

| `NodeExecutionEnv` | Node 原生 |
|---|---|
| `readTextFile` | `fs.readFile(path, "utf8")` |
| `writeFile` | `fs.writeFile` |
| `listDir` | `fs.readdir` + `stat` |
| `exists` | `fs.access` / `existsSync` |
| `createDir` | `fs.mkdir({ recursive: true })` |
| `renameFile` | `fs.rename` |
| `canonicalPath` | `fs.realpath` |
| `exec` | `child_process.spawn`（字符串时套一层 shell） |

新建实例很轻，没有连接或池子，本质是薄壳。

## 四个本质区别

### 1. 失败用返回值，不用异常

```ts
// node:fs
try {
  const text = await fs.readFile(p, "utf8");
} catch (error) {
  if (error.code === "ENOENT") { /* ... */ }
}

// NodeExecutionEnv
const read = await env.readTextFile(p, ctx);
if (!read.ok) {
  read.error.code;  // "not_found" | "permission_denied" | ...
  read.error.path;
}
```

错误码是归一化的（`not_found` / `permission_denied` / `is_directory` / `not_supported` 等），不是 errno 字符串。工具里因此不需要满屏 `try/catch`。

### 2. 每个操作都带 `ctx`

```ts
env.readTextFile(p, ctx);
env.exec(command, options, ctx);
```

`ctx` 里的取消信号会传进去：调用方取消后，文件读取中断、子进程被杀。用原生 fs 需要自己透传 `AbortSignal`。

### 3. 抽象层，不只本地

```ts
interface ExecutionEnv extends FileSystem, Shell {}
```

`NodeExecutionEnv` 只是其中一种实现，同一份工具代码可跑在本地、测试临时目录、以及将来可能的远程/容器实现上。这也是工具必须用 `api.env` 而不是 `import "node:fs"` 的原因。

### 4. `exec` 的输出是流式的

```ts
await env.exec(command, {
  cwd,
  timeout,
  onOutput: (text) => api.output(text),
}, ctx);
```

返回值只有 `exitCode`（超时时附带 `spillPath`），文本全靠 `onOutput` 收集。超时只杀该命令的进程，子进程记录在 `activeChildPids`，由 `cleanup(ctx)` 统一收尾。

## 反直觉的一点

`cwd` 不是 `process.chdir()`：

```ts
readTextFile("a.txt", ctx);   // → resolvePath(this.cwd, "a.txt")
```

它只影响本实例内相对路径的解析，不改变进程工作目录，也不影响其他实例。多个不同 `cwd` 的环境可以安全并存。

## 一句话

`NodeExecutionEnv` = `node:fs` + `child_process` 的薄包装，但把异常换成 `Result`、把取消变成 `ctx` 参数、把本地抽象成接口，并统一了输出流与进程清理。功能相近，写法差别很大。
