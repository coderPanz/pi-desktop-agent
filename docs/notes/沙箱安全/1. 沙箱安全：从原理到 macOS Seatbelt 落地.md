# 沙箱安全：从原理到 macOS Seatbelt 落地

## 先说结论

**沙箱安全不是“让程序变安全”的魔法，而是给某个不完全可信的进程划一条可由操作系统强制执行的权限边界。**

本项目在 macOS 上的做法是：不把整个桌面应用关进沙箱，而是在每次执行 `bash` 命令前，用系统的
Seatbelt 启动器 `/usr/bin/sandbox-exec` 给**命令及其后代进程**附上一份策略。策略默认：

1. **只准写工作区和临时目录**；
2. **默认不准联网**；
3. 常见凭证目录和 dotenv 额外禁止读取，宿主凭证不自动继承给命令；但这仍不是完整的读取白名单。

因此，它解决的是“模型或脚本通过 shell 把本机文件写坏、持久化或联网外传”的一部分风险；它**不**解决
“工作区内误删”“读取未列入限制的敏感文件”“主进程自身的文件操作”等问题。把这条边界的范围说清楚，比把它称为
“全面安全”更重要。

---

## 一、先理解：什么是沙箱安全

可以把运行程序所拥有的能力想成一串钥匙：读文件、写文件、开网络连接、启动程序、给其他进程发信号……
没有沙箱时，子进程通常继承启动者的系统权限，能使用的钥匙很多。

**沙箱做的事情是：在进程调用操作系统服务时，额外检查“这把钥匙能不能用”。**

```text
程序想执行：写 ~/.zshrc
        │
        ▼
操作系统处理文件写入请求
        │
        ├─ 普通 Unix 权限是否允许？
        └─ 沙箱策略是否允许？  ── 否 ──► 返回 EPERM / Operation not permitted
                                      是
                                      ▼
                                   完成写入
```

这带来三个必须同时成立的概念：

| 概念 | 含义 | 常见误解 |
| --- | --- | --- |
| **主体** | 被限制的进程及其子进程 | “整个应用都在沙箱里” |
| **策略** | 允许或拒绝哪些操作、哪些资源 | “装了 sandbox-exec 就自动安全” |
| **执行点** | 操作系统在文件、网络、进程等操作发生时做判定 | “外面有一个监工进程在分析 shell 文本” |

所以，沙箱不是命令黑名单，也不是虚拟机。`rm -rf`、`curl`、Python、Node 都可以启动；只是在它们真正尝试写文件或连网时，内核会按策略拒绝不该拥有的能力。

### 1.1 沙箱解决什么，不解决什么

安全问题要先写成威胁模型，才能知道该不该用沙箱。

| 风险 | Seatbelt 能否直接缓解 | 本项目的状态 |
| --- | --- | --- |
| shell 命令写入家目录、系统目录 | 能，只要 profile 未放行目标路径 | 已限制写入工作区与临时目录 |
| shell 命令联网下载、上传数据 | 能，只要 profile 拒绝网络 | 默认拒绝，可配置放行 |
| shell 的孙子进程绕过限制 | 能，策略随进程树继承 | 已覆盖 |
| `rm -rf` 删除工作区 | 不能；工作区本来就是写白名单 | 由审批、Git 快照和备份承担 |
| 读取 `~/.ssh` 等常见凭证目录、dotenv | 默认拒绝，已存在软链的真实目标也屏蔽 | 不是所有敏感文件的读取白名单 |
| `read` / `write` / `edit` 工具直接写盘 | 不能；这些代码运行在主进程，不是 shell 子进程 | 由 `paths.ts`、`guard.ts` 的应用层边界承担 |
| CPU 打满、内存耗尽、逻辑错误 | 不能；这是资源控制或可靠性问题 | 需另加 timeout、资源限制等机制 |

**结论：安全能力只能按“主体 + 操作 + 资源”来描述。**例如“shell 子进程不得向工作区外写文件”是可验证的边界；“应用已经安全”不是。

## 二、为什么本项目选择 macOS Seatbelt

macOS 有两种容易混淆的“沙箱”：

| 机制 | 适用场景 | 启动方式 |
| --- | --- | --- |
| **App Sandbox** | 面向签名、分发的 macOS App；通过 entitlements 声明能力 | 由系统根据应用签名和 entitlement 建立 |
| **Seatbelt / Sandbox Profile Language（SBPL）** | 进程级、按 profile 限制操作；这里用于限制 shell 子进程 | `/usr/bin/sandbox-exec -f profile.sb command` |

这里使用的是第二种。它的优势不是“更强大”，而是与现有架构相配：所有 bash 执行都汇聚到
`ExecutionEnv.exec()`，在那里加一个启动前缀，就能覆盖 shell 和它再启动的工具链，而无需改造每个命令。

> `/usr/bin/sandbox-exec` 是 Apple 标为 deprecated 的旧接口，不应被当作长期稳定的公开产品 API。当前项目仍在 macOS 上使用它；必须探测其存在、测试真实策略，并在不可用时**明确失败**，而不是悄悄以无沙箱方式继续执行。对需要长期、强隔离的不可信代码执行，应评估容器或 VM 等替代方案。

## 三、Seatbelt 是怎样真正生效的

### 3.1 从命令到内核检查的路径

以用户请求运行 `pnpm test` 为例，实际链路是：

```text
模型 / 工具请求："pnpm test"
        │
        ▼
NodeExecutionEnv.exec()
        │  被 withSandbox() 包装
        ▼
/usr/bin/sandbox-exec -D WS=<真实工作区> -D TMP=<真实临时目录> \
  -D HOME_DIR=<真实家目录> -D PROFILE_DIR=<策略目录> -D CREDENTIAL_0=<凭证路径> … \
  -f <临时/profile.sb> /bin/zsh -f -c "pnpm test"
        │
        ▼
sandbox-exec 读取、编译 profile，并把限制应用到自身
        │
        ▼
exec shell  →  shell fork/exec pnpm  →  pnpm 启动 node / esbuild / …
        │
        ▼
任一后代进程请求写文件、建 socket 等受限操作时，macOS 按策略判定
```

关键不在于 `sandbox-exec` 留在外面“监视”目标程序。它读取 profile 后会执行目标程序；限制作为进程的
安全上下文随 `fork`/`exec` 传给后代。也就是说，`zsh → pnpm → node → esbuild` 这条进程链共享同一条
边界，不能靠再套一层 shell 就跳出去。

从开发者视角，只需记住一句话：**策略在操作发生时由系统检查，而不是靠解析命令字符串检查。**
因此，软链接、换语言、间接启动子进程都不应成为“绕过命令文本规则”的手段；前提是 profile 本身写得足够窄。

### 3.2 Seatbelt profile 如何表达权限

Seatbelt 使用 S 表达式风格的 SBPL。项目生成的核心规则等价于：

```lisp
(version 1)
(allow default)

; 写操作先整体拒绝，再仅允许少数位置
(deny file-write*)
(allow file-write*
  (subpath (param "WS"))
  (subpath (param "TMP"))
  (subpath "/private/var/folders")
  (literal "/dev/null")
  (literal "/dev/stdout")
  (literal "/dev/stderr"))

; 本应用策略目录禁止被命令改写
(deny file-write*
  (subpath (param "PROFILE_DIR"))
  (regex #"/pi-sandbox-[^/]+(/|$)"))

; 另有常见凭证目录与 dotenv 的 file-read* 拒绝规则，完整规则见 sandbox.ts
; 网络默认拒绝；配置为 allow 时不生成这条规则
(deny network*)
```

逐句理解：

- `(allow default)`：未特别限制的操作先按允许处理；这不是“全开后就没用”，后续规则会明确收紧写和网络。
- `(deny file-write*)`：拒绝一类文件写操作，包括创建、改写、删除、重命名等。
- `(subpath (param "WS"))`：只对运行时传入的工作区及其后代目录放开写入；`-D WS=...` 会提供该参数。
- `(literal ...)`：仅放开这个精确路径，适合标准输出等设备节点。
- `(deny network*)`：拒绝网络相关操作；其效果是连接失败，而不是让 `curl` 命令无法启动。
- 读取黑名单包括 `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.azure`、`~/.kube`、`~/.config/gcloud`、`~/.config/gh`
  与 `.env` / `.env.*`，普通 `.env.example` 除外；凭证目录会同时绑定真实目标，不能靠目录软链绕过。
- 禁止 shell 联网不等于禁止外传：未屏蔽的敏感文件仍可能被打印到工具输出，再由主进程提交给模型。

策略采用“**先广泛拒绝，再按最小范围放行**”的形状。不要反过来写成“允许所有路径，再列几个禁止路径”：漏掉一个敏感目录时，默认就是放行的。

### 3.3 路径为何必须先真实化

文件系统中的同一位置可有多个字符串路径，例如 macOS 上 `/var` 通常会指向 `/private/var`。软链接也会让
`workspace/link` 表面上在工作区、实际指向工作区外。

项目在生成参数前调用 `realpathSync()`：

```ts
const workspace = realDirectory(options.workspace)
`WS=${workspace}`
```

解析失败、目录不存在或路径不是目录时必须拒绝，不能退回字符串路径；文件系统根也不能作为写白名单。
这样 profile 获得的是内核解析后应匹配的真实根路径。**路径白名单的安全性依赖这个步骤。**只做
`startsWith("/workspace")` 之类字符串比较，既会误判，也容易被 `..` 或软链接绕开。

## 四、本项目的实现：从配置到执行

实现位于 [`packages/core/src/agent/sandbox.ts`](../../../packages/core/src/agent/sandbox.ts)，接线位于
[`packages/core/src/agent/env.ts`](../../../packages/core/src/agent/env.ts)。它可拆成五步。

### 第一步：决定是否启用，以及网络规则

```ts
const mode = options.sandbox ?? sandboxModeFromEnv()
if (mode === "off") return env
```

- `PI_SANDBOX=seatbelt`：强制使用 Seatbelt。
- `PI_SANDBOX=off`：关闭。只适合排障，不应把它误当成安全默认值。
- 未设置时：`darwin`（macOS）默认 `seatbelt`，其他平台默认 `off`。
- `PI_SANDBOX_NET=allow`：不生成网络拒绝规则；其他值和未设置默认 `deny`。

无论是否开启 Seatbelt，命令环境都只继承 PATH、HOME、语言、临时目录等运行变量。`shell-env.ts` 会过滤
宿主、`shellEnv` 与每次执行传入的环境，并强制设置 `inheritEnv: false`，避免 SDK 重新合并宿主凭证。

如果启用了 Seatbelt 却找不到 `/usr/bin/sandbox-exec`，`prepareSandbox()` 会抛错。这个 **fail closed** 行为很重要：
“沙箱坏了但仍照常运行”会让调用方错误地以为边界还在。

### 第二步：为本次执行准备私有 profile 文件

```ts
const directory = mkdtempSync(path.join(os.tmpdir(), "pi-sandbox-"))
const profile = path.join(directory, "profile.sb")
writeFileSync(profile, seatbeltProfile(network), { mode: 0o600 })
```

每个执行环境都有独立临时目录和 profile 文件，文件权限为 `0600`。工作区和临时目录不是把路径拼进
profile 文本，而是通过 `-D` 作为参数传入：

```ts
[
  "/usr/bin/sandbox-exec",
  "-D", `WS=${workspace}`,
  "-D", `TMP=${realDirectory(os.tmpdir())}`,
  "-D", `HOME_DIR=${home}`,
  "-D", `PROFILE_DIR=${directory}`,
  // 另传入每个常见凭证目录的真实目标 CREDENTIAL_0、CREDENTIAL_1 等
  "-f", profile,
]
```

参数化可以把固定策略和每个会话不同的工作区分开，避免手工插值路径时的转义错误。

### 第三步：只替换 `exec`，不假装隔离整个应用

`withSandbox()` 是 `NodeExecutionEnv` 的装饰器。它保留原环境的超时、取消、输出处理和进程清理逻辑，
但把每个 `exec` 改写为带启动前缀的 argv：

```ts
// 字符串命令：明确交给 shell 解析
[...prefix, shell, "-c", command] // zsh 在 -c 前加 -f，跳过用户 .zshenv

// argv 命令：目标程序直接跟在启动前缀后
[...prefix, ...command]
```

这一步的边界非常精确：只有 `ExecutionEnv.exec()` 启动的进程进入 Seatbelt。`readTextFile()`、
`writeFile()` 等方法仍在 Electron/CLI 的主 Node 进程中运行，它们不会因为这个装饰器而自动获得内核沙箱。

### 第四步：执行与清理

底层 `NodeExecutionEnv` 以 argv 方式启动 `/usr/bin/sandbox-exec`。启动器加载策略后执行 shell 或目标程序；
原有的超时和 abort 仍负责结束受管理的进程组，不保证终止主动脱离进程组的程序。
环境清理先调用 `inner.cleanup()`，再删除临时 profile 目录；任一项失败都继续执行另一项，并保留两项错误。
profile 创建失败也会回收已创建的目录。

profile 在启动时已被读取并应用；删除策略文件不是“解除”正在运行进程的限制。它只是清理临时材料。

### 第五步：明确当前 profile 的实际授权面

| 能力 | 当前行为 | 原因 |
| --- | --- | --- |
| 写工作区 | 允许 | 工作区是 `WS` 白名单 |
| 写系统临时目录 | 允许，策略目录除外 | `TMP` 和 `/private/var/folders` 被放行，`pi-sandbox-*` 被额外保护 |
| 写家目录、系统目录 | 拒绝 | 命中 `deny file-write*` |
| 读取常见凭证目录、dotenv | 默认拒绝 | 额外的 `deny file-read*` 规则，网络放行不解除它 |
| 读取其他家目录、系统文件 | 通常允许 | 尚未建立全局读取白名单 |
| 默认联网 | 拒绝 | 生成 `deny network*` |
| `PI_SANDBOX_NET=allow` 时联网 | 允许 | 不生成网络拒绝规则 |
| 主进程的文件 I/O | 不受这份 Seatbelt profile 约束 | 主进程没有通过 `sandbox-exec` 启动 |

特别注意：`/private/var/folders` 是一个较宽的临时目录例外，是为 macOS 和工具链的临时行为准备的便利性
取舍；它不等同于“只允许一个临时文件”。如果威胁模型要求更严格的写边界，应把它缩小到专用目录，并先完成
兼容性测试。

## 五、怎样验证它真的在工作，而不是只相信文档

验证应覆盖“允许”和“拒绝”两边，并使用**工作区外且不在临时目录中**的目标路径。不要用 `/tmp` 验证拒绝：
它通常正是被允许的临时区域。

下面是一个独立的最小示例：

```bash
workdir="$(mktemp -d)"
workdir="$(cd "$workdir" && pwd -P)"  # macOS 临时目录也要使用真实路径
cat > /tmp/example.sb <<'EOF'
(version 1)
(allow default)
(deny file-write*)
(allow file-write* (subpath (param "WS")))
(deny network*)
EOF

# 允许：写进工作区
sandbox-exec -D "WS=$workdir" -f /tmp/example.sb /bin/sh -c \
  'echo ok > "$1/inside.txt"' sh "$workdir"

# 拒绝：写家目录；预期看到 Operation not permitted
sandbox-exec -D "WS=$workdir" -f /tmp/example.sb /bin/sh -c \
  'echo no > "$HOME/seatbelt-should-fail.txt"'
```

项目级测试还应至少覆盖：

1. 工作区内创建、改名、删除都按预期工作；
2. 家目录或另一工作区的写入失败；
3. 工作区内软链接指向外部时，外部写入仍失败；
4. `sh -c 'sh -c ...'` 等多层子进程仍受限；
5. 默认网络连接失败，显式允许网络后才成功；
6. `sandbox-exec` 不存在、profile 创建失败或损坏时，命令不会无沙箱执行；
7. 凭证、dotenv 与策略目录保护生效，允许的普通读取不受误伤；
8. 超时、取消和环境清理会终止仍在同一进程组内的后代。

运行 `pnpm test:sandbox`。macOS CI 也执行这些明确命名的测试文件，文件缺失或 macOS 上缺少启动器会失败。
文件工具的路径检查在权限错误、断链、取消或无法确认真实边界时拒绝，但检查与实际 I/O 之间的竞态尚未消除。

被拒绝时，应用通常只会看到 `EPERM`、`EACCES` 或 `Operation not permitted`。排查 macOS 沙箱拒绝还可使用：

```bash
log stream --predicate 'eventMessage CONTAINS "Sandbox"'
```

日志格式和可见信息会随 macOS 版本变化，因此它适合诊断，不应被当作业务逻辑的判断依据。

## 六、落地检查表：把“有沙箱”变成可信的安全设计

在新增命令入口或修改 profile 前，依次回答以下问题：

1. **主体是谁？** 是仅 shell 子进程，还是还包括文件工具、插件 worker？不要把未进入 Seatbelt 的代码算进去。
2. **要挡的动作是什么？** 写、读、网络、执行、进程观察、还是资源滥用？每一种都要有对应规则或其他控制。
3. **允许清单是否最小？** 特别检查工作区、临时目录、缓存目录和设备节点；宽泛的 `subpath "/"` 会使边界失效。
4. **路径是否真实化？** 白名单根必须处理软链接和 macOS 的 `/var`/`/private/var` 别名。
5. **失败会怎样？** 启动器缺失、规则生成失败、操作被拒绝时，是否明确报错而非静默降级？
6. **还有什么没被挡？** 工作区内破坏、未列入黑名单的敏感读取、主进程 I/O、模型 API 出口和资源消耗必须另行控制。
7. **是否有自动化实测？** 至少为每一条拒绝规则写一个“确实失败”的测试，为每个必须业务行为写一个“仍可成功”的测试。

**最后的判断标准不是“用了 Seatbelt”，而是：不可信命令即使被批准执行，也只能在经过验证的最小能力集合内行动。**
