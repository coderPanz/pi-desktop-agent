# `openFixture()`：测试环境工厂

```ts
async function openFixture() {
  const storage = new MemoryStorage()
  const models = createModels({ credentials: new InMemoryCredentialStore() })
  const registry = createPiRegistry()
  const host = await HarnessHost.open({ storage, models, registry })
  const manager = await SessionManager.open({ harness: host.harness, storage })
  return { storage, host, manager }
}
```

`openFixture()` 是测试中的**最小运行环境工厂**。每条测试调用它，获得一套相互隔离、可以运行会话功能、但不会联网调用模型的系统。

依赖关系如下：

```text
MemoryStorage ─┐
models ────────┼─> HarnessHost ──> Harness ──> SessionManager
registry ──────┘
```

## 1. 内存存储：`MemoryStorage`

```ts
const storage = new MemoryStorage()
```

创建一个内存版数据库。会话、entries、任务和文档等数据都写入其中，但不写入 SQLite 或其他磁盘文件。

特点：

- 每次调用 `openFixture()` 都有一套全新的空白数据；
- 测试之间不会相互污染；
- 不需要手动清理测试数据库；
- 测试结束或进程退出后，数据自然消失。

例如 fork 测试写入的 `test.note`，只存在于本次 fixture 创建的 `storage` 中。

## 2. 模型目录与凭据：`createModels()`

```ts
const models = createModels({
  credentials: new InMemoryCredentialStore(),
})
```

创建 Harness 所需的模型管理对象。

`InMemoryCredentialStore` 只把凭据保存在内存，本测试也没有注册 provider 或真实模型，所以没有 API Key、不会请求模型服务。测试只覆盖本地行为，例如创建会话、写 entry、fork、reset、读取 entries、watch 和 inbox；这些操作不依赖模型推理。

> 若测试提交真正需要模型响应的 `input`，在此环境下会因无可用模型/凭据而无法正常完成。

## 3. 工具与扩展注册表：`createPiRegistry()`

```ts
const registry = createPiRegistry()
```

创建工具和扩展的注册表。Harness 初始化时需要该对象，以确定会话中可提供哪些工具和扩展能力。

当前测试不执行具体工具调用，所以使用最小（或近似空）的项目注册表即可。

## 4. 组装并启动 Harness：`HarnessHost.open()`

```ts
const host = await HarnessHost.open({ storage, models, registry })
```

`HarnessHost` 将 storage、models 和 registry 组装成可运行的 durable `Harness`，并封装固定的启动顺序：

```text
1. Harness.open(storage, { models, registry })
2. harness.resume()
3. harness.root()
```

因此 `host` 提供：

```ts
host.storage // 当前的 MemoryStorage
host.harness // 已打开、已 resume 的 durable Harness
host.root    // 默认 root Conversation
```

`harness.root()` 会确保 root 会话存在，其 ID 是 `ROOT_CONVERSATION_ID`（通常为 `1`）。

`HarnessHost` 还提供幂等关闭：

```ts
await host.close()
```

即使重复调用，底层 Harness 也只实际关闭一次。因此测试通常在 `finally` 中调用它，确保资源被释放。

## 5. 创建项目层会话管理器：`SessionManager.open()`

```ts
const manager = await SessionManager.open({
  harness: host.harness,
  storage,
})
```

`SessionManager` 是项目对 durable `Harness` 的会话操作封装，负责提供应用层 API：

```ts
manager.create()
manager.select(id)
manager.fork()
manager.submit(...)
manager.entries()
manager.reset()
manager.inbox()
manager.view()
```

未传 `conversationId` 时，`SessionManager.open()` 默认取得 `harness.root()` 的 ID。因此初始化完成后：

```ts
manager.conversationId === ROOT_CONVERSATION_ID
host.root.id === ROOT_CONVERSATION_ID
```

## 6. 返回的三个对象如何使用

```ts
return { storage, host, manager }
```

| 对象 | 用途 |
| --- | --- |
| `storage` | 直接检查持久化记录，例如 fork 会话是否写入正确的 `ConversationRecord.parent`。 |
| `host` | 访问底层 Harness 或 Conversation，并在测试结束时关闭资源。 |
| `manager` | 经由项目层 API 测试创建、选择、fork、reset、队列和 watch 行为。 |

例如：

```ts
const { storage, host, manager } = await openFixture()
```

- 使用 `manager.fork()` 创建分叉；
- 使用 `storage.conversation(forked.id, ctx)` 验证其 `parent` 记录；
- 使用 `host.harness.conversation(...)` 取得底层会话对象并写入测试 entry；
- 在 `finally` 中执行 `await host.close()`。

## 为什么是 `async function`

初始化包含异步步骤：

```ts
await HarnessHost.open(...)
await SessionManager.open(...)
```

在这些操作完成前，Harness 可能尚未打开、调度尚未恢复、root 会话尚未确保存在。因此测试必须等待 fixture 准备完毕后再操作会话。

## 总结

`openFixture()` 为每条测试创建一套独立的：

> **内存存储 + 无真实凭据的模型环境 + 注册表 + 已启动 Harness + 默认指向 root 的 SessionManager**

它让测试能够验证本地会话逻辑，而不依赖磁盘数据库、API Key 或网络。
