# Agent 与人工同时编辑文件时会发生什么

> Pi / coding-agent 的 `read`、`write`、`edit` 和人工编辑器操作的是同一份磁盘文件，但默认没有 Google Docs 一类的实时协同、自动合并或抢锁提醒。

可以把文件想成白板：

```text
Pi read：看一眼白板上的内容
人工编辑：擦掉并重新写
Pi write/edit：按它刚才看到的内容继续修改白板
```

如果两边恰好同时改到同一内容，就可能覆盖或发生编辑失败。

---

## 1. `read`：只读取调用瞬间的磁盘内容

```ts
read(path)
```

`read` 的含义是：在调用的那个瞬间，从磁盘读取文件内容。

```text
10:00:00  Pi read 文件，看到：const title = "旧标题"
10:00:03  人工保存修改：const title = "新标题"
```

Pi 不会自动收到“文件已被人工修改”的通知，也不会自动重新读取。因此它后续思考时仍可能基于 10:00:00 时的旧内容；只有下一次显式调用 `read`，才会看见最新磁盘版本。

| 人工保存的时机 | Pi 的 read 能否看到 |
| --- | --- |
| Pi read 前 | 能，读取到最新已保存版本 |
| Pi read 后 | 不能自动得知，Pi 持有的是此前读到的内容 |
| Pi 再次 read | 能，读取到此时的最新版本 |

> 未保存的编辑器内容不在磁盘上，Pi 完全读不到，也无法保护。

---

## 2. `write`：通常整文件覆盖，风险最大

`write` 通常将准备好的完整内容写进目标路径。

假设 Pi 准备写入：

```ts
export const name = "Pi"
```

而人工在 Pi read 后手动保存为：

```ts
export const name = "Manual"
export const enabled = true
```

Pi 随后执行完整 `write` 时，效果通常是：

```text
当前整份文件
    ↓
替换为 Pi 准备好的整份文件
```

于是人工新增的：

```ts
export const enabled = true
```

可能丢失。

**结论：**对已有文件，`write` 最容易覆盖 Pi 读取之后人工保存的改动。它通常不会自动做三方合并。

---

## 3. `edit`：基于旧文本匹配，较能避免误覆盖

`edit` 通常不是提交整份文件，而是给出明确替换规则：

```ts
{
  path: "example.ts",
  edits: [
    {
      oldText: "const title = '旧标题'",
      newText: "const title = '新标题'",
    },
  ],
}
```

典型执行过程：

1. 执行 edit 时读取文件当前内容；
2. 在当前内容中查找 `oldText`；
3. 只有唯一匹配时才替换为 `newText`；
4. 找不到、匹配不唯一或替换区域重叠时，报错且不写入。

### 情况 A：人工改了不相关的位置

Pi 要改：

```ts
const port = 3000
```

人工改的是：

```ts
const host = "localhost"
```

Pi 的 `oldText` 仍能唯一匹配时，edit 正常成功；两边的修改一般都可保留。

### 情况 B：人工改了 Pi 正要替换的位置

Pi 原计划：

```ts
oldText: "const port = 3000"
newText: "const port = 4000"
```

人工先保存：

```ts
const port = 5173
```

Pi 执行时找不到 `const port = 3000`，通常会得到类似 `oldText not found` 的错误，而不是猜测是否覆盖人工的 `5173`。

这是一种轻量保护：Pi 应重新读取文件、理解人工改动，再决定如何继续。

### 情况 C：人工格式化或重构了文件

即使实际业务逻辑不冲突，人工运行 Prettier、调整导入顺序、抽取函数或重命名，也可能改变 Pi 用来匹配的 `oldText`。结果通常仍是 edit 失败而不写文件；Pi 需要重新读取。

---

## 4. 最危险的时间窗口

```text
① Pi read：读取 A 版本
② Pi 思考并生成修改方案
③ 人工保存 B 版本
④ Pi write/edit：执行基于 A 版本制定的修改
```

| Pi 的后续动作 | 常见结果 |
| --- | --- |
| 再次 `read` | 看到 B 版本，相对安全 |
| `edit`，人工改了同一段 | `oldText` 找不到，失败，不写入，相对安全 |
| `edit`，人工改了无关位置 | 常可成功，两边修改可共存 |
| 完整 `write` | 可能用 Pi 的完整内容覆盖 B，风险最大 |
| `bash` 执行重定向、生成器、格式化器等 | 取决于命令；同样可能整文件或批量覆盖 |

不要只防 `write`。Agent 使用 `bash` 时也可能改文件：

```bash
npm run format
codegen
sed -i ...
cat generated.ts > src/api.ts
```

这些操作的覆盖和并发行为取决于具体命令。

---

## 5. 默认没有什么能力

普通 coding-agent 默认不会：

- 实时监听整个工作区内的人工保存；
- 自动刷新模型此前已读到的文件内容；
- 像协作文档一样逐字符合并；
- 每次写入前自动执行三方合并；
- 自动保护编辑器中尚未保存的内容。

Agent 会话历史可能记录它曾读过或修改过哪些文件，但这只是执行记录，不是 Git，也不是协同编辑系统。

---

## 6. 人工与 Agent 协作时更安全的做法

### 6.1 人工改完后明确要求 Agent 重读

最可靠的做法：

```text
我刚手动修改了 packages/core/src/session/manager.ts，请重新读取后再继续。
```

这样 Agent 会基于最新磁盘内容工作，而不是继续依赖旧 read 结果。

### 6.2 修改已有文件时优先精确 `edit`

安全性通常可粗略排序为：

```text
精确 edit
  > 小范围 patch
  > 整文件 write
```

`edit` 中的 `oldText` 相当于一个简单检查：“只有当前文件仍有这个预期片段时，才进行替换。”

### 6.3 避免同时修改同一小段

若 Agent 正在改：

```text
packages/core/src/session/manager.ts 的 abort() 方法
```

人工最好改另一个文件，或至少改该文件不相邻的区域。若确实必须改同一段，保存后应让 Agent 重新读取。

### 6.4 用 Git 审查和保留检查点

完成后检查：

```bash
git status --short
git diff -- packages/core/src/session/manager.ts
```

重要改动前，可以先创建自己的 Git checkpoint：

```bash
git add -A
git commit -m "保存当前工作进度"
```

即使后来发生覆盖，也更容易对比或恢复。

---

## 一句话总结

- `read`：只知道读取瞬间的已保存磁盘内容；人工后续修改不会自动同步给 Agent。
- `edit`：通常通过 `oldText` 在当前文件中精确匹配；人工改到同一段时常会失败而不覆盖。
- `write`：通常整文件覆盖，对人工并发修改风险最高。
- 默认没有自动协同、自动合并或写入锁。
- 人工修改后最好的提示是：**“我刚改了这个文件，请重新读取后继续。”**
