# pi-durable 的 Storage：把会话、执行、状态与恢复串成一个系统

> **核心理解：`Storage` 不是“聊天记录数据库”。它是 pi-durable 的唯一事实来源**
>
> 对话文本、模型上下文边界、排队输入、正在运行的 generation、工具调用、任务检查点（pi 中的任务执行有检查点这个概念， 执行过程中会生成检查点，任务中断恢复执行时会从最近的检查点继续执行）、扩展状态、用量统计、fork 的历史关系，都是先作为一次原子提交（commit）写入 Storage；只有提交成功后，Harness 才向 UI / watch / event stream 发布可见状态，并继续安排执行。

tips：Entry 是不可变的历史事实；transcript 是这些 entry 组成的会话记录；Document 和后续 entry 可以改变当前状态或模型上下文，但不能原地篡改已经写入  
 │ 的 entry。

因此可以把 pi-durable 看成一个围绕持久化状态机设计的 agent runtime：

```text
应用 / CLI / Electron UI
        │ submit、fork、reset、配置、扩展状态
        ▼
Harness / Session（语义、调度、任务状态机、单条提交线）
        │ StorageWrite[]：一次原子 commit
        ▼
Storage（事实源：表记录 + 文档版本）
        │ CommitPublication / watch 的来源
        ├──────────────► ConversationView / UI
        └──────────────► 重启后的 Harness 恢复并继续执行
```

## 1. 为什么 Storage 是“串联一切”的中心

普通聊天程序很容易把状态分散在内存：

- UI 内存里放聊天消息；
- Promise / async 函数栈表示“模型正在生成”；
- 工具调用过程在局部变量中；
- 队列在一个数组中；
- 刷新、崩溃或进程重启后，这些状态就丢失或彼此不一致。

pi-durable 反过来设计：**先把事实持久化，再让程序执行它们**

例如用户提交一个输入，概念上不是“直接调用模型”，而是：

```text
submit(input, requestId) 【提交类型为：input；请求幂等 Id】
  │
  ├─ 原子提交：创建 submission；若可立刻保存成功；则创建 pi.user entry、创建 generation task、更新 pi.live
  │
  ├─ commit 成功后，UI/watch 才能看到用户输入和忙碌状态
  │
  ├─ Scheduler 从已提交的 task 读取 checkpoint，调用模型
  │
  ├─ 流式 partial / 工具输出按节流间隔继续提交
  │
  └─ 最终原子提交：assistant entry、usage、submission done、任务 terminal、清理 pi.live
```

这套顺序解决了几个关键问题：

1. **崩溃恢复**：进程在模型或工具执行中断掉，重开同一个 Storage 后，未终结 task 仍有输入和 checkpoint，可继续调度。
2. **不会“显示了但没记住”**：UI 只能从已提交状态推导；每个可见状态都有持久化依据。
3. **不会“写一半”**：一次 commit 中的 entry、任务状态、文档更新要么全部成功，要么全部不出现。
4. **可重放和幂等**：submission 的 `requestId` 持久化，同一请求在重启后重发仍能定位到已有 submission，而不是重复创建工作。
5. **前端不必猜状态**：忙碌、工具进度、排队消息、token 用量都由已提交的文档状态给出。
6. **可替换后端**：Harness 面向 `Storage` 接口编程；内存、SQLite、IndexedDB、JSONL、Cloudflare Durable Object 可以有相同语义。

这里的“durable”不只是“聊天记录保存下来”，而是：

> **Agent 的控制流也变成持久化数据。**
>
> 模型调用、工具调用、等待、重试、取消、子任务等，不依赖某个仍活着的 JavaScript 调用栈；它们由 Storage 中的任务状态机重新驱动。

## 2. 三层职责：Harness / Session 与 Storage 不要混淆

### 2.1 `Storage`：可靠地保存，不解释业务语义

`Storage` 是底层接口。它提供：

- 分配全局递增 ID：`mintId()`；
- 原子写入一批 `StorageWrite`：`commit()`；
- 查询 conversations / entries / tasks / submissions / documents；
- 文档的当前值和历史时点读取；
- 关闭底层资源。

它要保证的主要是不变量包括：

- 一批 writes 原子可见；
- 全局 ID 不重复；
- 会话、entry 的不可变创建；
- document incarnation 与 revision 的一致性；
- 读取结果是脱离内部可变状态的值。

但 Storage **不负责理解**“一个 task 的状态迁移是否符合任务定义”“某个 entry 是否是合法 assistant 消息”等高层语义。接口说明明确指出，Storage 信任拥有它的 Session 提供语义上有效的记录、引用、祖先关系和状态迁移。

### 2.2 `Session`：一条串行的原子变更线

`Session` 将所有变更排在同一条 mutation line 上：

```ts
await session.commit(async (tx) => {
  // 只能经 tx 读取和修改本次事务相关状态
  // 可追加 entry、更新 document、创建/更新 task、安置 submission
}, context)
```

它是业务一致性的核心：同一事务内，可以将彼此相关的事实一起提交。例如“用户输入已经进入 transcript + generation task 已创建 + pi.live 标记为 busy”必须一起成功。

在 commit 回调中应通过 `tx` 读取，而不要调用外部 `harness.snapshot()`、`watchDoc()` 等可能再次排队到同一 mutation line 的 API；否则会出现等待自己释放锁、永远无法返回的情形。

### 2.3 `Harness`：在已存事实之上运行 agent

Harness 持有一个打开的 Storage，并提供：

- `Conversation` 句柄；
- task scheduler；
- 内置 generation / tool / compaction 等任务；
- extension registry、模型、执行环境；
- documents 的快照与 watch；
- 对提交完成后变更的发布。

`Conversation` 句柄本身几乎不保存状态，真正状态在 Storage。两个会话句柄是否指向同一会话，应比较 `id`。

## 3. Storage 的逻辑数据模型

Storage 的核心有五类持久化对象：

```text
Conversation ──拥有──► Entry（不可变 transcript）
      │                       ▲
      │                       │ fork parent 链决定“哪些 entry 可见”
      │
      ├──────────────► Submission（一次外部提交的生命周期）
      ├──────────────► Task（可恢复的执行状态机）
      └──────────────► Document（可版本化的 JSON 状态）

一次 Commit 可同时修改上述多类对象。
```

| 类型 | 解决什么问题 | 写入特性 |
| --- | --- | --- |
| `ConversationRecord` | 一个 transcript 的身份、fork 历史边、所有权边 | 创建后不可变 |
| `EntryRecord` | 历史事件、显示内容、模型上下文贡献 | 追加后不可变 |
| `SubmissionRecord` | 外部输入/写入从进入系统到完成的生命周期、幂等 | 随状态更新 |
| `TaskRecord` | generation、tool、compaction、业务 task 的可恢复执行状态 | 随状态机迁移替换 |
| `DocumentRecord` + revisions | agent 配置、live 进度、inbox、usage、扩展业务状态 | 版本化 JSON，可增量更新 |

所有 ID 来自同一个 Session-global 数字命名空间。虽然 TypeScript 用 branded type 区分 `ConversationId`、`EntryId`、`TaskId`、`SubmissionId`、`DocumentId`，它们在存储层共享全局递增顺序。这带来两个用途：避免不同记录类别的 ID 碰撞，也使 ID 顺序可代表创建顺序。

每次成功原子提交还会获得一个严格递增的 `Seq`（sequence）。`Seq` 代表提交顺序，不代表业务对象 ID；允许有间隔。

## 4. Conversation：会话身份、fork 历史和所有权

### 4.1 结构

```ts
type ConversationRecord = {
  id: ConversationId
  parent?: {
    conversationId: ConversationId
    at: EntryId
  }
  owner?: {
    conversationId: ConversationId
    taskId: TaskId
  }
}
```

| 字段 | 含义 | 为谁服务 |
| --- | --- | --- |
| `id` | 会话的全局唯一身份 | 所有会话 API、entries 查询、documents 和 tasks 的归属 |
| `parent.conversationId` | fork 来源会话 | fork 历史继承与可见 entries 查询 |
| `parent.at` | fork 时包含的父 entry 上限，**含该 entry** | 将 fork 的历史固定在准确时间点，避免看到父会话之后新增的消息 |
| `owner.conversationId` | 创建该子会话的父会话 | 子 agent / 子会话归因、树形展示、级联 abort / idle wait |
| `owner.taskId` | 创建者 task | 将子会话绑定到具体运行任务的生命周期 |

### 4.2 `parent` 与 `owner` 是两种完全不同的边

这两个字段都指向其他对象，但不能混为一谈：

```text
parent：历史边（“我从谁的哪条记录处分叉”）
owner ：执行所有权边（“哪个 task 创建并管理我”）
```

- `parent` 影响 `entries()` / context 的可见历史；
- `owner` 影响归因、任务子树取消和等待空闲；
- 人手创建的会话通常是 `{ kind: "ownerless" }`，没有 `owner`；
- fork 会写 `parent`，但可以仍是 ownerless；
- subagent 会话可能有 `owner`，却不一定有 `parent`。

### 4.3 fork 为何不复制历史

fork 创建的是这样的记录：

```ts
{
  id: forkedId,
  parent: { conversationId: parentId, at: entryId },
}
```

当读取 fork 的 entry 时，Storage 先看 fork 自己的 entries；读到尽头后沿 `parent` 向上，且父段只允许 `id <= at`：

```text
父会话： A ── B ── C ── D
                     │
                     └── fork 于 C：子会话后续写 E

父会话可见：A, B, C, D
fork 可见 ：A, B, C, E
```

这使得历史继承是按需解析的，不需要复制大量 records，同时确保两条分支在分叉点后互不污染。多层 fork 也只是继续沿父链切出多个有限片段。

## 5. Entry：不可变 transcript 与模型上下文控制

### 5.1 结构

```ts
type EntryRecord = {
  id: EntryId
  conversationId: ConversationId
  kind: string
  model?: readonly Message[]
  data?: JsonValue
  head?: EntryId
  edits?: readonly ContextEdit[]
  byTaskId?: TaskId
}
```

Entry 是一条**不可变事件记录**。它不是单纯的“聊天气泡”：同一条 entry 可以同时承担 UI 显示、模型上下文、审计、状态边界等职责，但字段刻意将这些职责分离。

| 字段 | 含义 | 典型用途 / 服务对象 |
| --- | --- | --- |
| `id` | 全局唯一 entry ID | 排序、fork cutoff、引用、上下文范围 |
| `conversationId` | entry 实际写入的会话 | 存储索引与本地段查询 |
| `kind` | 应用定义的判别符 | UI 如何渲染、扩展如何识别；内置例子有 `pi.user`、`pi.assistant`、`pi.tool-result`、`pi.reset`、`pi.compaction` |
| `model` | 此记录向模型上下文贡献的 `Message[]` | 生成下一轮请求的模型上下文；缺失时表示展示/记账条目，不向模型说任何内容 |
| `data` | 严格 JSON 的应用负载 | UI 元数据、工具结果、扩展业务信息；模型不自动读取它 |
| `head` | 此 entry 所选择的 active context 起点 | reset、compaction 等截断模型可见上下文；旧历史仍存在 Storage |
| `edits` | 对早前可见 entry 的模型贡献做 omit / replace | 只改模型看到的上下文，不改原始 transcript，适合上下文修订 |
| `byTaskId` | 产生该 entry 的 durable task | 追踪回答/工具结果来自哪个执行单元；手动写入的 entry 一般没有 |

### 5.2 `kind`、`data`、`model`：三个视角分离

这是理解 pi-durable transcript 的关键。

```ts
{
  kind: "chat.mention",
  data: { author: "ann", text: "can you check the build?" },
  model: [{ role: "user", content: "ann: can you check the build?" }]
}
```

- `kind` 给应用：这是一个 mention，而非普通气泡；
- `data` 给应用 / 扩展：用于展示作者、样式、业务字段；
- `model` 给模型：它真正要看见的用户语义。

因此可以有只供 UI 用的 entry：

```ts
{ kind: "app.note", data: { openedFile: "README.md" } }
```

它没有 `model`，所以不进入模型上下文。反过来，模型上下文也不必须等同于 UI 内容。

### 5.3 `head`：不删除历史，只移动模型上下文起点

`head` 字段是 active context 的边界标记。最新的可见 head marker 决定模型可看见的 transcript 起点。

- `reset()` 会写入 `pi.reset` 等带 `head: "self"` 语义的 entry；
- compaction 会写入包含摘要的 `pi.compaction` entry，并将 head 放在它保留的范围；
- 更早的 entry **仍在 Storage 中**，仍可审计、显示或用于别的分析，但不再自动发送给模型。

这避免了“为了缩短上下文只能删除旧聊天”的设计。pi-durable 将“完整历史”和“当前喂给模型的上下文”明确区分。

### 5.4 `edits`：只改上下文解释，不篡改历史

`ContextEdit` 的结构是：

```ts
type ContextEdit =
  | { target: EntryId; action: "omit" }
  | { target: EntryId; action: "replace"; messages: readonly Message[] }
```

它记录“在推导模型 context 时如何处理某条早期 entry”。原 entry 没被覆盖，因此 transcript 的事实仍可信；只是后续模型请求可选择省略或替换其消息贡献。

### 5.5 不可变 entry 的价值

Entry 一旦写入便不更新。流式回答看似在不断修改文字，实际是通过 task/document 的进度状态和节流提交实现；最后的历史结果以 entry 固化。这种 append-oriented 思路让：

- fork 能稳定地按 entry ID 截断；
- 回答、工具结果、重置和摘要都有审计轨迹；
- UI 可从 committed entry 构建稳定 transcript；
- 重启不会找不到“上一步做到了哪里”。

## 6. Submission：外部请求的持久化生命周期与幂等

### 6.1 Submission 不等于 Entry

外部调用 `conversation.submit(...)` 产生的是 Submission。它代表“一个请求进入系统，并最终被安置、回答或明确终止”的生命周期；Entry 则是 transcript 中已经落位的一条事件。

```text
用户/API 调用 submit
      │
      ▼
Submission（queued / placed / done / unanswered）
      │                      │
      │                      └── entry：它被放进 transcript 的位置
      │
      └── input 成功回答后有 answer：assistant entry 的位置
```

### 6.2 结构和状态

共同字段：

```ts
type SubmissionRecordBase = {
  trace?: TelemetryCarrier
  id: SubmissionId
  conversationId: ConversationId
  requestId?: string
}
```

| 字段 | 含义 / 服务对象 |
| --- | --- |
| `trace` | adapter 所有的遥测传播上下文，用于连接观测链路 |
| `id` | 这次提交的稳定身份，重启后可重新获取并等待 |
| `conversationId` | 提交属于哪个会话 |
| `requestId` | 主机提供的、**会话内作用域**的幂等键；同一个键重试会找到原 Submission |

输入（`type: "input"`）的状态：

| 状态 | 含义 | 关键字段 |
| --- | --- | --- |
| `queued` | 已被系统接纳，但还在 inbox，尚未进入 transcript | 暂无 `entry` |
| `placed` | 已写入 transcript，并归入一个活跃 run | `entry` 是用户输入 entry |
| `done` | 已成功得到模型回答 | `entry` + `answer`（assistant entry） |
| `unanswered` | 已终结但不可能再得到回答 | `reason`，可选 `detail`；可能尚无 entry |

被动写入（`type: "write"`）的状态较简单：

| 状态 | 含义 |
| --- | --- |
| `queued` | 还未到可安全放置的边界 |
| `done` | entry 已追加 |
| `unanswered` | 无法放置并终结，有 `reason` / 可选 `detail` |

### 6.3 为何需要它

没有 Submission，调用方很难可靠回答：

- 用户请求是否被接收，还是网络断开前根本没进系统？
- 忙时它在排队还是已进入本轮？
- 它对应哪条 user entry 和哪条 assistant answer？
- 重启后如何继续等待同一个请求？
- 客户端重试是否会造成双重提问或双重外部副作用？

`requestId` 是恢复策略的重点。若调用方在不确定提交是否成功时重试同一个 key：

```ts
await root.submit({
  type: "input",
  content: "Hello",
  requestId: "greeting-1",
}, context)
```

pi-durable 会在该会话内定位已有 submission，而不是再次接纳一条相同输入。

## 7. Task：将异步执行改造成可恢复状态机
在 pi 中 task 是异步任务的统称，包括模型调用，工具调用，压缩上下文任务等。
task 记录存在 checkpoint 机制，也就是检查点，恢复后可从检查点继续执行 task
### 7.1 Task 保存的不是“结果”，而是执行位置

Task 是 pi-durable 可靠性的核心之一。它用持久化状态机代替悬在内存中的 async 函数：每个 phase 结束/推进时，把下一步所需 checkpoint 写入 Storage。

内置任务包括：

- `pi.generation`：模型请求、回答和工具轮控制；
- `pi.tool`：每一个工具调用；
- compaction 相关任务；
- 扩展或应用定义的自有 task。

概念上：

```text
TaskRecord = 不变的身份和输入
           + 当前状态（pending/running/waiting/sleeping/...）
           + checkpoint（从哪里恢复）
           + ownership / abort / 时间 / outcome
```

### 7.2 结构

```ts
type TaskRecord<I, S, R> = {
  id: TaskId<R>
  conversationId: ConversationId
  kind: string
  version: number
  input: I
  owner?: TaskId
  background: boolean
  abortRequested: boolean
  abortReason?: "restart"
  abandonOnRestart?: true
  startedAt?: number
  endedAt?: number
  restarts?: number
  trace?: TelemetryCarrier
  links?: readonly TelemetryCarrier[]
  state: TaskState<S, R>
  memos?: Readonly<Record<string, JsonValue>>
}
```

| 字段 | 含义 | 为谁服务 |
| --- | --- | --- |
| `id` | task 身份；泛型参数描述最终 result 类型 | scheduler、task graph、等待结果 |
| `conversationId` | task 所属会话 | 会话级取消、busy / view 展示、上下文读取 |
| `kind` | registry 中注册的 task 定义名 | 重启后找到对应逻辑和迁移代码 |
| `version` | task 定义版本 | 旧 checkpoint / input 的 migrate |
| `input` | 原始输入 | task 重启、重试、审计；不会因每一步而丢失 |
| `owner` | 父 task；缺失代表由 conversation 直接拥有 | 子任务树、级联 abort、等待 |
| `background` | 会话直接拥有的后台任务标记 | 是否参与普通 idle wait、普通会话 abort、级联关系 |
| `abortRequested` | 持久化取消标记 | scheduler 在运行前采取 abort 路径；取消不会只依赖内存 signal |
| `abortReason` / `abandonOnRestart` | 重启后应被放弃的特殊规则 | 防止“只在内存中有人等待”的任务被错误恢复 |
| `startedAt` / `endedAt` | 首次运行与终结的时间 | 运行时长、观测与诊断 |
| `restarts` | 未产生新进展即被崩溃/驱逐/重置打断的连续次数 | crash-loop 防护；到限制后停放等待人工 retry |
| `trace` / `links` | 创建时的遥测关系 | 分布式追踪 |
| `memos` | task 活跃时 first-writer-wins 的小型 JSON memo | 对重放稳定的少量状态 / 幂等辅助 |

### 7.3 `TaskState`：每一个状态都能恢复

任务的状态大致如下：

```ts
type TaskState<S, R> =
  | { status: "pending"; checkpoint: S }
  | { status: "running"; checkpoint: S }
  | { status: "waiting"; checkpoint: S; on: TaskId[]; policy: "failFast" | "allSettled" }
  | { status: "sleeping"; checkpoint: S; until: number }
  | { status: "completing"; outcome: TaskOutcome<R> }
  | { status: "terminal"; outcome: TaskOutcome<R> }
```

| 状态 | 意义 |
| --- | --- |
| `pending` | 已持久化，随时可被 scheduler 调度。进程重启前为 `running` 的 task 也会以可重新运行的形式恢复。 |
| `running` | 已被当前进程中的某次 invocation 预留；仍带 checkpoint，避免内存是唯一事实。 |
| `waiting` | 等待 `on` 中的子任务终结；保留 checkpoint 和 join 策略。 |
| `sleeping` | 等待持久化时间点 `until`；不占用 invocation，重启后仍能被唤醒。 |
| `completing` | outcome 已决定，但普通 owned work 尚未全部终结，因此尚不能完全结束。 |
| `terminal` | 永久终态，有不可变的 outcome receipt；不会再执行代码。 |

终态 outcome 又区分：

- `completed`：有 `result`；
- `failed`：预期的业务 / 领域失败，带结构化 error；
- `aborted`：显式取消；
- `orphaned`：定义缺失或迁移不可用，无法恢复；
- `faulted`：未捕获异常、没有 durable progress 等运行时契约故障。

### 7.4 checkpoint 是恢复边界

Task phase 不应假设“函数执行到一半还能从 await 后继续”。进程重启时，JavaScript 栈消失，phase 会从其开头重新执行；因此下一步必须写进 checkpoint，并在新的 phase 中继续。

以睡眠为例：

```ts
await runtime.sleepUntil(
  task.input.at,
  { phase: "deliver" }, // 这是下一次恢复的 checkpoint
  context,
)
```

Storage 保存 `{ status: "sleeping", until, checkpoint }`。时间到后新进程可从 `deliver` phase 继续，而不是试图恢复旧函数栈。

### 7.5 工具调用为何也要存成 task

每个工具调用先被记为 durable task，再执行 `execute()`：

- 意图先落盘，崩溃后不会忘记“这个工具本来要做”；
- 声明 `replay: "safe"` 的工具可在重启后重跑；
- 非安全重放的工具不会被盲目重复外部副作用，而会按中断规则产出结果；
- 工具输出进度、最终结果 entry、usage 与调用状态可以一致地提交。

注意：`replay: "safe"` 不是替代外部系统的幂等设计。一个会写外部资源的工具即使能重跑，仍应自己使用幂等键或等价机制。

## 8. Document：与 transcript 并存的类型化、版本化状态

### 8.1 为什么还需要 Document
document 是 pi 中的一种状态管理机制，表示当前状态，entry 表示历史已经确认不可更改的状态
Document 是与 transcript 并存的、**类型化 JSON 状态**：

- 用于当前状态读取和 UI watch；
- 可和 entry / task 在同一 commit 中更新；
- 有 scope、history、fork 策略和 schema version；
- 可保留完整历史或只保留最新值。

它不是另一个“随便放对象的 KV store”；定义 document 时要明确其生命周期语义：

```ts
const Todos = defineDoc<{ items: string[] }>({
  kind: "app.todos",       // 持久化协议名
  version: 1,               // 值结构版本
  scope: "conversation",   // session / conversation / task
  history: "latest",       // 或 rewindable
  fork: "initial",         // initial / current / asOf
  initial: () => ({ items: [] }),
  checkpointWhen: () => false,
})
```

### 8.2 DocumentRecord：文档“这一代”的身份

```ts
type DocumentRecord = {
  id: DocumentId
  kind: string
  key?: string
  createdAt: Seq
  retiredAt?: Seq
  scope: ...
  history?: ...
  fork?: ...
}
```

| 字段 | 含义 / 服务对象 |
| --- | --- |
| `id` | 当前 incarnation（这一代文档）的唯一 ID；同一逻辑地址重建也不复用 ID | revision 精确归属、审计 |
| `kind` | 稳定的文档定义名，例如 `pi.agent` | token / 定义匹配、持久化协议与迁移 |
| `key` | document family 成员键；缺失表示 singleton | 同类多实例状态，例如每个嵌套调用一个成员 |
| `createdAt` | 创建该 incarnation 的 commit `Seq` | as-of 成员关系、历史查询 |
| `retiredAt` | 退役 commit `Seq`；缺失代表当前有效 | 替换文档、历史查询、避免地址冲突 |
| `scope` | `session` / `conversation` / `task` 及 owner ID | 控制可见范围和生命周期 |
| `history` | 对 conversation doc：`latest` 或 `rewindable` | 是否支持过去时点 `snapshotAsOf()` |
| `fork` | 新 fork 该如何初始化此 doc | `initial` / `current` / `asOf`，决定配置/状态继承语义 |

“逻辑地址”由：

```text
kind + scope + 可选 key
```

共同确定。在一个地址的当前时点，只能有一个未退役的 incarnation。

### 8.3 scope：状态属于谁

| scope | 归属 | 适合存什么 |
| --- | --- | --- |
| `session` | 整个打开的 Harness / Storage 生命周期 | 全局应用状态、跨会话索引等 |
| `conversation` | 一个会话 | agent 配置、inbox、live、usage、会话级扩展状态 |
| `task` | 一个具体 task | 嵌套调用 journal、工具局部可恢复状态 |

只有 conversation document 定义 history 与 fork 语义，因为 fork 的本质是从一个 conversation 生成另一个 conversation。

### 8.4 history：`latest` 和 `rewindable`

- `latest`：只保留当前状态。新的完整 base 可替换旧 revisions，适用于不需要“回到某条 entry 时的旧值”的状态。
- `rewindable`：保留可进行 as-of 读取的历史，允许：

  ```ts
  await harness.snapshotAsOf(Token, conversationId, atEntryId, context)
  ```

  适合 fork 必须继承“分叉点当时的状态”的 document。

### 8.5 fork：`initial`、`current`、`asOf`

fork 时每个 conversation document 可独立选择其初始化来源：

| 策略 | fork 获得什么 |
| --- | --- |
| `initial` | 文档定义的默认初值；不继承父状态 |
| `current` | 父会话 fork 创建时的当前值 |
| `asOf` | 父会话在 fork cutoff entry 对应时点的值；要求 document 是 `rewindable` |

这解释了一个容易遗漏的事实：**conversation fork 不只涉及 entries。**

- entries 通过 `ConversationRecord.parent` 链按需继承；
- 支持 fork 的 documents 会在创建 fork 的同一 commit 中按其 policy 创建副本；
- 例如 `pi.agent` 是 rewindable，fork 获取父会话在分叉 entry 时的 agent 配置；
- `pi.provider` 则刻意不是父值复制：fork 会有新的 provider session identity，防止供应商侧会话 / prompt cache 身份混淆。

### 8.6 值与 revision：base / delta

Document 的值不是都在 `DocumentRecord` 中。其内容保存在 revision 流：

```ts
type DocumentContent =
  | { version: number; kind: "base"; value: JsonObject }
  | { version: number; kind: "delta"; ops: readonly Op[] }
```

- `base`：完整 JSON 快照；
- `delta`：Chord 的操作增量；
- `version`：内容结构版本，用于迁移；
- 读取时从最近合适的 base 开始重放后续 delta，物化为 `StoredDocument.value`。

`checkpointWhen(value, ops, info)` 决定一次普通变更何时应存为新的完整 base，而不是增量。目的不是“每次都最省空间”，而是在读取重放成本与存储量之间取得边界：避免无限长的 delta 链。

### 8.7 内置 documents：运行时的“当前仪表盘”

pi-durable 自己使用 document 保存许多核心状态：

| 文档 kind | 主要结构 / 意义 | 谁使用 |
| --- | --- | --- |
| `pi.agent` | 每会话的模型、thinking、extensions、tools、instructions、cwd 等选择 | 每次 generation / tool / section 解析 agent；fork 在 cutoff 时继承 |
| `pi.provider` | `{ sessionId: string }` | 将稳定 UUIDv7 传给 pi-ai/provider，用于 provider session affinity / prompt cache；fork 获取新 identity |
| `pi.live` | `run`、generation partial/retry、工具槽、nested tools、compaction 状态 | UI 判断 busy、渲染流式内容和工具进度；`manager.isBusy()` 正是看 `live.run` |
| `pi.inbox` | `{ items: InboxItem[] }` | 忙时排队的 steer / followUp / write；队列边界根据 settings 放置它们 |
| `pi.usage` | 按 provider/model 的模型 usage、按工具名的 usage | 会话和全局的 token / 成本统计 |
| task 文档，如嵌套调用状态 | 某 task 的局部可恢复执行资料 | 工具嵌套调用、journal、重放控制 |

其中 `pi.live` 的一部分典型形状：

```ts
{
  run?: { taskId, inputs: SubmissionId[] },
  generation?: {
    attempt: number,
    message?: AssistantMessage, // 已节流提交的 partial
    retry?: { at, error },
    deferred?: { pollAt },
  },
  tools?: [{ callId, name, status, taskId?, entry?, output?, details? }],
  compactions?: [{ taskId, reason, blocking, attempt, retry? }],
}
```

这就是 UI 不必维护“自己猜的 loading 状态”的原因：一旦 `pi.live.run` 存在，会话就忙；不存在则该 run 已经完成或被清理。

## 9. 一次 commit 到底写什么

Storage 接受的原子写入单元是：

```ts
type StorageWrite =
  | { type: "conversation"; value: ConversationRecord }
  | { type: "entry"; value: EntryRecord }
  | { type: "task"; value: TaskRecord<...> }
  | { type: "submission"; value: SubmissionRecord }
  | { type: "document.create"; record: DocumentCreate; content: Base }
  | { type: "document.copy"; record: DocumentCreate; source: DocumentCopySource }
  | { type: "document.change"; id: DocumentId; content: Base | Delta }
  | { type: "document.retire"; id: DocumentId }
```

一次 `Storage.commit(writes, context)` 成功时：

1. 后端以**一个原子事务**持久化整批 writes；
2. 分配并返回该批次的 `Seq`；
3. 此后的 Storage 读取可以观察到整批结果；
4. Session/Harness 据此发布 `CommitPublication` 和更新 views / watches；
5. scheduler 才可能基于其中新建或更新的 task 工作。

例如“一个 input 被立即放置并启动 run”的真实语义不一定恰好只写这些项，但应当作为**一个一致原子单元**包含类似事实：

```text
- submission: queued → placed
- entry: 新增 pi.user
- task: 新增 pi.generation（带 initial checkpoint）
- document: pi.live 写入 run/taskId/inputs
- document: pi.inbox 移除刚放置的 item（如果此前排队）
```

任何一项没有持久化成功时，其他项也不能单独留下。否则最糟糕的情况会是：UI 已经展示用户消息，但没有 task；或者 task 存在却没有输入 entry；或者 busy 一直显示但找不到可运行的任务。

## 10. 从用户输入到回答：Storage 如何串起整条链

以下是一次不含工具调用的概念流程：

```text
(1) Host 调用 Conversation.submit(input, requestId)
      │
      ├─ Storage: 创建 SubmissionRecord
      │    - 若会话闲：直接 placed
      │    - 若会话忙：queued，同时 pi.inbox 加 item
      │
(2) 输入被放置到边界
      │
      ├─ Storage: 新建 pi.user EntryRecord
      ├─ Storage: SubmissionRecord → placed
      ├─ Storage: 创建 pi.generation TaskRecord（pending + checkpoint）
      └─ Storage: pi.live.run = { taskId, inputs }
      │
(3) Scheduler 执行 generation phase
      │
      ├─ 从 entries + head + edits 推导模型 context
      ├─ 从 pi.agent / pi.provider / registry / settings 取得运行配置
      ├─ 调用 provider
      └─ 流式 partial：按 progress 策略周期性提交到 pi.live.generation.message
      │
(4) 得到最终回答
      │
      ├─ Storage: 新建 pi.assistant EntryRecord
      ├─ Storage: pi.usage.models 累加本次 usage
      ├─ Storage: SubmissionRecord → done，answer = assistantEntryId
      ├─ Storage: TaskRecord → terminal(completed)
      └─ Storage: 移除 pi.live.run / generation 等当前运行态
      │
(5) UI 从 watch 接到已提交的新 ConversationView
```

若模型要求工具：

```text
pi.generation（assistant entry 含 tool calls）
   └─ 创建 pi.tool × N TaskRecord
        ├─ pi.live.tools 发布每个工具槽与输出进度
        ├─ 每个工具完成后写 pi.tool-result entry
        └─ generation 等待工具 tasks，随后进入下一 generation phase
```

若进程在任何 phase 之间崩溃：已提交事实还在；未提交内存动作消失；Harness 重开后根据任务状态重新调度，而不是假装它知道未提交动作已经完成。

## 11. 物理后端：接口一致，耐久性不同

pi-durable 的同一 Storage 语义可以由多个后端实现：

| 后端 | 使用场景 | 持久性特点 |
| --- | --- | --- |
| `MemoryStorage` | 单元测试、临时运行 | 纯内存，进程结束即消失；但接口/隔离语义用于验证实现 |
| IndexedDB | 浏览器单机 | 一个 IndexedDB 数据库；应避免多个 tab/worker 竞争同一库，可用 Web Lock |
| SQLite | Node / Electron 长期 agent | 一个数据库文件；WAL + `synchronous = NORMAL`，进程崩溃后 commits 可恢复，电源/宿主故障下最新提交可能丢失 |
| JSONL | 可检查的追加日志、简单环境 | 目录中的 append-only 文件；内存会随历史增长，长期运行更建议 SQLite；`fsync: true` 可在每个 commit marker 前刷新 |
| Cloudflare Durable Object SQLite | 每对象一个云端 runtime | 使用 DO 的 SQLite storage transaction 作为 commit |

`MemoryStorage` 并不是“功能较弱的假实现”。它有意 clone / detach 读写值，以接近序列化存储的所有权边界，并可用于 Storage conformance 测试；只是它不持久化。

### 11.1 SQLite 物理 schema（实现细节）

SQLite 实现目前使用这些主要表：

```text
durable_metadata
record_ids
conversations
entries
tasks
submissions
documents
document_revisions
```

| 表 | 存储内容 | 特别的索引/列为何存在 |
| --- | --- | --- |
| `durable_metadata` | `next_id`、`next_seq` | 跨重开保持全局 ID 和提交序号单调递增 |
| `record_ids` | ID 与记录类别 | 保证全局 ID 命名空间不被不同类别误用 / 冲突 |
| `conversations` | `ConversationRecord` JSON | 额外投影 `owner_conversation_id`、`owner_task_id`，便于查 owner 子会话 |
| `entries` | `EntryRecord` JSON | 投影 `conversation_id`、`head`、`commit_seq`；按 `(conversation_id, id DESC)` 查询 transcript，head 索引用于找上下文边界 |
| `tasks` | 最新 `TaskRecord` JSON | 投影 `conversation_id`、`kind`、`status`、`abort_requested`、`background`，便于 scheduler / task graph 筛选 |
| `submissions` | 最新 `SubmissionRecord` JSON | 投影 `conversation_id`、`request_id`、`status`；`(conversation_id, request_id)` 解决幂等定位 |
| `documents` | `DocumentRecord` JSON | 投影 kind / scope / owner / family / key / created / retired，定位某逻辑地址在某时点的 incarnation |
| `document_revisions` | document 的 base 或 delta 内容 | 主键 `(document_id, seq)`，按 document + revision 顺序物化状态 |

可以看到 SQLite 使用的是**“完整 JSON record + 少量索引化投影列”**的折中：

- record JSON 保留协议的完整性和演进弹性；
- 高频过滤、排序和定位的字段被拆成列和索引；
- 不必把每个扩展自定义字段都固定为 SQL schema；
- Storage 仍对外暴露统一 TypeScript records，而不是让上层依赖 SQL。

这些表名和 SQL 列是当前 SQLite adapter 的实现细节；业务代码应优先使用 `Storage` / `Harness` API，而不是直接依赖表结构。

## 12. 文档版本与 fork 在物理层如何配合

fork 时有两类数据：

1. **entries**：不复制；`ConversationRecord.parent` 记录历史来源与 cutoff，读取时沿父链可见。
2. **documents**：根据定义的 `fork` policy 在 fork 创建 commit 中创建新的 document incarnation；SQLite 的 `document.copy` 会从选定 source 的 selected point 物化成新 document 的 base。

这正好平衡两种需求：

- transcript 历史通常很大，并且天然适合父链共享；
- 可变 document 状态必须在 fork 后独立，不能让两个会话共用同一份可变当前值；
- `asOf` 需要 document revision 历史，才能得到分叉点当时的 agent/config 状态。

所以可以记成：

```text
fork 的 entry = 共享祖先历史的“逻辑可见性”
fork 的 doc   = 按 policy 物化出的“独立状态副本”
```

## 13. UI、watch 与 Storage：为什么 UI 可以只订阅 committed state

`ConversationView` 是由已提交 Storage 状态构建的结构视图：

```ts
type ConversationView = {
  conversation: ConversationRecord
  entries: readonly EntryRecord[]
  docs: Readonly<Record<string, JsonObject>>
}
```

它一般包含：

- 当前 conversation record；
- 当前 active transcript（由 fork 历史、head 等规则导出）；
- `pi.live`、`pi.inbox`、`pi.usage`、`pi.agent`、`pi.provider` 等内置 documents。

`viewState()` 可取得可观察的只读 Chord state，`watch()` 则交付每一次已提交变更对应的精确操作（ops）。慢 consumer 最多积压有限帧，超过限制后会收到完整最新 view，以避免无限积压。

重要边界：**watch 不是数据库变更日志重放接口。**

- 新连接 / 断线重连的客户端先从“当前完整状态”开始；
- watch 递送之后的 committed frames；
- UI 设计应能从当前 view 自身渲染，不应依赖从进程启动以来永不丢帧的内存事件。

这使 Electron/CLI/API 层可以更简单：它们是已提交事实的呈现者，而不应再维护第二份竞争性的业务状态机。

## 14. 错误模型：为何 Storage 错误会结束 Harness

Storage 是事实源，因此它的写入失败不能被运行时随意忽略。

pi-durable 的关键规则：

1. **任何 `commit()` 或 `mintId()` 错误都会使 Session/Harness 失败并关闭。**
   - 当前调用 reject；
   - 后续操作和等待会以 `SessionFailed` 失败；
   - watches / event stream 以 `session_failed` 结束；
   - 正在运行的 tasks 收到 abort signal；
   - Harness 关闭后应重新打开 Storage 恢复。
2. **无效读取只失败该读取。**
   - 如未知 conversation、错误 cursor、要求读取 document 未保存的历史，属于 `StorageRequestError`；
   - 不应造成持久化副作用，也不必关闭整个 Harness。
3. **commit callback 自己抛错会回滚本次 commit。**
   - 这和“Storage 后端写失败”不同；前者没有写入，通常是当前业务单元失败。

这样做看似严格，但避免了最危险的状态：内存以为任务进展了，Storage 却没有记住。由于 commits 是原子的，故障后重新打开仍会得到一致数据；调用方通过相同 `requestId` 重试可重新对齐提交结果。

对于自定义 Storage，短暂网络故障等应由 Storage 实现内部在其方法返回前完成重试；不能让 Harness 以不确定的写入结果继续运行。

## 15. 在本项目中的实际对应

本仓库对 Storage 的使用体现了“上层不私藏状态”的思路：

```ts
const storage = new MemoryStorage()
const host = await HarnessHost.open({ storage, models, registry })
const manager = await SessionManager.open({
  harness: host.harness,
  storage,
})
```

- `HarnessHost` 负责以固定顺序打开 Harness、`resume()`、确保 root 会话存在，并在关闭时关闭 Harness；
- `SessionManager` 使用 `harness` 执行会话动作，使用 `storage` 做会话列表和持久化记录查询；
- `manager.fork()` 之后，可以通过：

  ```ts
  await storage.conversation(forked.id, ctx)
  ```

  直接检查 fork record 的 `parent`；
- `manager.isBusy()` 不靠未完成的 Promise 猜测，而读取 `LiveDoc`：

  ```ts
  const live = await harness.snapshot(LiveDoc, conversationId, ctx)
  return live?.run !== undefined
  ```

也就是说，`SessionManager` 是操作 / 查询的便利层，但 Storage 中已提交的 record 和 document 才是最终依据。

## 16. 实践准则：设计自己的 durable 状态时怎么选

### 用 Entry，当你记录的是“发生过的事件”

适合：消息、回答、工具结果、用户可见注释、审计事件、上下文边界。

特征：追加后不修改；需要保留时间顺序；可能参与模型 context 或 UI transcript。

```ts
await conversation.submit({
  type: "write",
  entry: { kind: "app.note", data: { text: "用户打开了设置页" } },
}, context)
```

### 用 Document，当你保存的是“现在是什么状态”

适合：UI 设置、会话模式、当前进度、扩展配置、任务局部 journal、缓存的业务状态。

特征：当前值会变；需要 snapshot/watch；需明确 scope、fork 和历史语义。

```ts
const State = defineDoc({
  kind: "app.state",
  version: 1,
  scope: "conversation",
  history: "latest",
  fork: "initial",
  initial: () => ({ enabled: true }),
  checkpointWhen: () => false,
})
```

### 用 Submission，当你需要追踪“请求是否被处理”

适合：外部 API / UI 的输入动作，需要等待、取消、重试、幂等。

务必在不确定网络重试、IPC 重试等场景传稳定 `requestId`。

### 用 Task，当你需要“跨崩溃继续执行”

适合：模型 generation、工具、轮询、定时提醒、子 agent、长流程。

不要把必要进度只保存在局部变量；在每个可恢复边界把它写入 checkpoint 或 task document。

### 同一个业务动作涉及多项事实时，放在同一个 commit

例如创建任务并设置其可见状态、写 entry 并同步更新 document，都应通过同一个 `tx` 提交，避免 UI 与 scheduler 看到中间状态。

## 17. 一页总结

```text
Storage 是 pi-durable 的事实源。

Conversation：我是谁、从哪条历史分叉、由谁创建。
Entry       ：不可变的 transcript 事件；展示、模型消息、上下文边界分离。
Submission  ：一次外部提交从接纳到回答/终止的生命周期；requestId 保证幂等。
Task        ：持久化状态机；input + checkpoint 使执行能跨重启恢复。
Document    ：类型化、版本化 JSON 当前状态；驱动 agent/live/inbox/usage/扩展状态与 UI watch。
Commit      ：以上对象的一次原子事实变更；成功后才发布和调度。

因此：
不是“内存程序顺手存档”，而是“从已存事实重建并驱动程序”。
```

当你阅读 pi-durable 时，可以反复用下面三个问题定位任何 API：

1. **它改变的是 Entry、Submission、Task 还是 Document？**
2. **这些变化是否在同一个原子 commit 中？**
3. **进程在 commit 前后崩溃，重新打开 Storage 后系统分别会知道什么？**

能回答这三个问题，基本就抓住了 pi-durable 的存储思想与大部分运行机制。
