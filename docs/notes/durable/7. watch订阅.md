# watch 订阅

```ts
const watch = await root.watch(ctx);
```

`root` 是 `Conversation`（由 `harness.root(ctx)` 取得）。这一行的作用是：**注册一个会话视图观察者，拿到初始快照和一个订阅句柄**。

它不启动投递，也不重放历史。

## 调用链

```text
Conversation.watch(ctx)
  └─ ConversationViews.watch(id, ctx)
       └─ attach(id, …) → new CommittedWatch(value, detach, report)
```

`attach()` 通过 `readOnLine()` 在 Session 线上排队执行，保证注册原子性：**能看到注册之后的每一次提交，看不到之前的**。因此不会出现「先读快照、再装监听」之间的丢帧。

同一会话最多有一个视图挂载（mount），多个观察者共享；最后一个观察者离开时 mount 才被丢弃。

## 为什么是 await

`watch()` 不只是返回引用，它要：

1. 进入 Session 线；
2. 必要时从存储读 `ConversationRecord`、活跃 `entries`、五个内置文档；
3. 注册观察者。

这些是真实 I/O，所以返回 `Promise`。`await` 完成时你拿到的是句柄，不是「已经开始收帧」的状态。

## 返回值

```ts
type ConversationWatch = WatchHandle<ConversationView>;

interface WatchHandle<T> {
  readonly value: T;
  start(listener: (value, ops, ctx) => Promise<void>): void;
  stop(): Promise<WatchEnd>;
  readonly closed: Promise<WatchEnd>;
}
```

### `watch.value`

attach 时刻的完整视图快照，同步可读。它是副本的初值：

```ts
let replica = watch.value;
```

投递过程中它会更新为最新已投递帧的值，可作为重新同步的依据。

### `watch.start(listener)`

- 不内联调用：只登记 listener，随后 `queueMicrotask` 调度。
- 不重放历史：`start()` 之前的状态只能靠 `watch.value`。
- 只能调用一次，第二次抛 `Watch is already started`。
- 串行投递：内部 `await this.#listener(...)`，同一时刻只有一个回调在跑。

### 有界积压与整帧折叠

待投递帧上限为 `MAX_PENDING_WATCH_FRAMES = 100`。达到上限时，队列被清空，只投递一帧 `[["r", 最新完整视图]]`。这就是 `isBase(ops) === true` 的真实来源。

因此回调必须快：里面只做 `applyFrame` 和轻量判断，不做重活。

### `watch.stop()` 与 `watch.closed`

`stop()` 幂等，返回 `closed` 的 promise。停止时会 detach、清空待投递帧、结算 `closed`；已经在跑的那个回调不会被强行中断。

`WatchEnd` 的原因：

| reason | 含义 |
|---|---|
| `stopped` | 主动调用 `stop()` |
| `cancelled` | `ctx` 被取消 |
| `session_closed` | Harness 正常关闭 |
| `session_failed` | 存储失败等导致会话终止 |
| `listener_error` | 回调抛错，watch 随之结束 |
| `retired` | 视图退役（收到 `["r", null]`） |

## `ctx` 的作用范围

`ctx` 只影响 watch 的生命周期：

```ts
if (signal?.aborted) { observer.cancel(); throw signal.reason; }
if (signal !== undefined) observer.observeCancellation(signal);
```

- `ctx` 被取消 → watch 以 `reason: "cancelled"` 结束。
- 取消 watch 不会停止模型生成；停生成要用 `conversation.abort(ctx)`。
- 每帧投递时上下文经 `withoutAbortSignal` 处理，所以后续取消 `ctx` 不会中断单帧回调。

## 在阶段 1 中的顺序

```ts
const watch = await root.watch(ctx);   // 注册观察者，拿到快照与句柄
let replica = watch.value;             // 用快照初始化副本
watch.start(async (value, ops) => {    // 开始收帧
  replica = applyFrame(replica, ops) ?? value;
});
const submission = await root.submit({ … }, ctx);  // 提交
await submission.wait(ctx);            // 等提交结算
await watch.stop();                    // 停止并取结束原因
```

先 `watch` 再 `submit`，才不会漏掉第一帧；先 `wait` 再 `stop`，才不会丢掉最后一帧。

## 常见误解

| 误区 | 事实 |
|---|---|
| `await watch()` 就开始收帧 | 收帧要等 `start()` |
| 不 `start` 也能收到 | 帧会进队列，但无人消费 |
| `watch()` 会重放历史 | 不会，历史只有 `watch.value` |
| 有 `ops` 就只可能是增量 | 积压折叠会发整帧 |
| 取消 `ctx` 能停生成 | 不能，只结束 watch |
| `watch` 会驱动调度 | 不会，要显式 `harness.resume()` |
| `stop()` 可以省略 | 省略会一直持有 mount 与回调 |

## 与 `viewState()` 的区别

```ts
const state = await root.viewState(ctx);  // AttachedReplicatedState<ConversationView>
const watch = await root.watch(ctx);      // WatchHandle<ConversationView>
```

数据相同，唯一差别是：`viewState` 不给 `ops`。主进程内部订阅用 `viewState`；需要把变化同步到进程外时用 `watch`。
