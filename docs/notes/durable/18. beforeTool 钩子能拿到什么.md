# `beforeTool` 钩子能拿到什么，不能拿到什么

**结论**：`beforeTool` 只能**读已提交文档、读写本任务 memo、看模型目录**，然后返回「改参数」或「阻断」。
它拿不到 `env`、拿不到定时器、也**不能等待文档变化**——所以 Electron 那种「写一条 pending 审批，等 UI 改状态」的事件门，
不能直接写在 Hook 里。

依据（`node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts`）：

```ts
export interface HookApi extends DocumentReader {
  readonly taskId: TaskId
  readonly conversationId: ConversationId
  readonly models: Models
  memo<T extends JsonValue>(name: string, context: Context): Promise<T | undefined>
  memo<T extends JsonValue>(name: string, candidate: T, context: Context): Promise<T>
}

export type DocumentReader = Pick<Session, "snapshot" | "snapshotAsOf">
```

## 由此推出的三条

1. **没有 `watch`**。`DocumentReader` 只是 `Session` 的两个只读方法，`docWatch` / 观察者都在 `TaskRuntime` 上，
   而 Hook 拿不到 `TaskRuntime`。要等 UI 答复只能在宿主侧转发（CLI 用事件队列，Electron 用主进程自己的等待）。
2. **没有 `env`**。钩子里**不能**解析路径——`resolveInside` 需要 `ExecutionEnv.cwd` 与 `canonicalPath`。
   路径边界必须在工具内部（本项目做法）或 `wrapTool` 里做，不在审批钩子里做。
3. **没有 `setTimer`**。超时必须用普通 `setTimeout`，并且**不能 `unref()`**：事件循环空闲时被跳过的计时器等于没有超时
   （本项目踩过：加了 `unref()` 后测试直接挂在未决 Promise 上）。
4. **等待必须认 `context.abortSignal`**。`context` 是有的（`beforeTool(call, api, context)`），而关闭时
   `Scheduler.join()` 只 `abort()` 每个 invocation 再 `await invocation.done`（`dist/harness/scheduler.js`）——
   abort 只是信号，不认信号的 `await` 不会因此返回，`host.close()` 就只能等到超时。

## 返回值能做的事只有两件

```ts
beforeTool(call: ToolHookCall, api: HookApi, context: Context): HookResult<{
  readonly arguments?: JsonObject   // 替换参数，仍会按工具的 parameters 校验
  readonly block?: string           // 首个 block 生效；抛错等同于 block
}>
```

- 不能往结果里塞 `details` / `diagnostics`：要那种效果得用 `afterTool`（可替换整个 `ToolExecutionResult`）。
- `block` 的文案会变成模型看到的结果：`Tool call blocked: ${block}`。
- 嵌套调用（工具里 `executeTool()`）也走同一个钩子，`call.parent` 有父任务 id 与 callId。

## 边界

- 钩子来自**会话选中的扩展**（`Extension.hooks`），按注册顺序执行；不选中就不会做这次检查。
- 本项目只对自己的五个工具判档，其它扩展的工具一律放行——审批策略分层，不越界管别人的工具。
