# 为什么每次调用都新建 NodeExecutionEnv

**结论：因为 pi-durable 把「环境」定义成一个工厂（构建器），而不是一个可共享的对象。** `HarnessOptions.env` 的签名是
`(target, context) => ExecutionEnv | undefined | Promise<...>`，SDK 自己在每次需要时调用它；而 `NodeExecutionEnv`
的构造只做 4 个字段赋值，没有 IO、没有连接、没有后台句柄，所以「每次新建」既符合契约，也几乎不花钱。

`packages/core/src/agent/env.ts` 只是把这个契约包一层，并在注释里写死「不缓存、不做单例」。

## 一、契约：`env` 是工厂

```ts
// node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts:566
/** Builds a conversation's environment at each use. Never called on the Session line; may be async. */
readonly env?: (target: EnvTarget, context: Context) => ExecutionEnv | undefined | Promise<ExecutionEnv | undefined>;
```

`EnvTarget` 每次现算，包含三样东西（同文件 `:541`）：

| 字段 | 含义 |
|---|---|
| `conversationId` | 给哪个会话建环境 |
| `cwd` | **该会话 agent 当前的 `cwd`**（可能没有） |
| `read` | 已提交状态的只读句柄（`DocumentReader`），让宿主能在构建时查库决定建哪种环境 |

SDK 侧的目标值当场读取，不做缓存：

```ts
// dist/harness/harness.js:168
async buildEnv(id, context) {
  const build = this.#options.env;
  if (build === undefined) return undefined;
  const cwd = (await this.snapshot(AgentDoc, id, context))?.cwd;
  return build({ conversationId: id, ...(cwd === undefined ? {} : { cwd }), read: this }, context);
}
```

`cwd` 来自每次重新读的 `pi.agent` 文档——这就是「必须每次重建」的第一层原因（见第四节）。

## 二、一次调用发生在哪三个入口

| 入口 | 代码位置 | 频率 |
|---|---|---|
| 工具调用 | `dist/harness/tool.js:309`（`env = await runtime.env(context)`） | **每个工具调用一次**（重跑一次再建一次） |
| 请求准备（渲染 system prompt sections） | `dist/harness/generation.js:60` | 每个模型请求一次 |
| 任务/钩子主动取 | `TaskRuntime.env(context)`（`dist/types.d.ts:228`） | 谁调用谁触发 |

section 之所以需要 env，是因为提示词里的 `<cwd>` 之类片段要现读环境：`section("cwd", (input) => input.env?.cwd)`
（`pi-durable/README.md` 的 Prompt sections 一节）。

所以一轮对话里「建几个 NodeExecutionEnv」= 1（请求准备）+ N（工具调用数）。

## 三、新建成本很低：构造函数只有字段赋值

```js
// dist/env/node.js:559
constructor(options) {
  this.cwd = options.cwd;
  this.shellPath = options.shellPath;
  this.shellEnv = options.shellEnv;
  this.watchOptions = options.watch ?? {};
}
```

实例状态只有这几样（`:553-558`）：`id = "node:local"`、`cwd`、`shellPath`、`shellEnv`、`watchOptions`、
`activeChildPids = new Set()`。**没有 fd、没有 socket、没有定时器、没有 watcher**。
watcher 是 `watch()` 时新建并交给调用方 `close()` 的，不存在实例上；实例上唯一活的状态是 `activeChildPids`。

## 四、为什么不缓存：五种具体问题

### 1. `cwd` 会在会话中途变化

`conversation.configure({ cwd })` 之后，SDK 的意图是「下一次使用就按新 `cwd` 建」：

> The model, prompt, and offered tools of a request are fixed when it is prepared; … the environment is built from
> the current `cwd` at each use, so a `cwd` or extension change can reach calls the model already made.
> —— `pi-durable/README.md`

缓存一个实例（`cwd` 是可变字段）就要自己处理失效；不缓存这条语义天然成立。

### 2. 实例带子进程账本，跨会话共享会污染归因

`activeChildPids` 记录本实例 `exec` 起的 pid，`settle` 时 `delete`（`node.js:674`），`cleanup()` 时全部 `killProcessTree`
（`node.js:1168-1172`）。若一个实例跨会话复用，这个集合就是所有会话、所有历史调用的并集：
「abort 后进程还在跑」时你无法判断它是哪次调用的残留。每次新建则把账本范围压到一次调用。

### 3. 工具默认并行，共享实例就是共享可变状态

`toolExecution` 默认 `"parallel"`（`dist/harness/agent.js:53`），同一条 assistant 消息里的多个 tool call 会并发执行，
多会话与嵌套调用也在同一进程里。共享一个 `cwd` 会变的实例要么加锁，要么产生竞态；各自一个实例没有共享状态。

### 4. 崩溃恢复重跑时要拿「当时」的环境

```js
// dist/harness/tool.js:211
/** Built for this call, below, so a rerun after recovery gets the conversation's environment at that time. */
let env;
```

崩溃后重跑同一个工具调用，环境按那一刻的会话配置重建。缓存旧实例会把已失效的配置（旧 cwd、旧容器 id）带进重跑。

### 5. 环境允许「每会话一个容器」，框架不能假设进程内只有一个

官方支持 per-conversation 的环境：`env: ({ cwd }) => new NodeExecutionEnv(...)` 只是最简形态，
README 示例表里的 `29-sandbox-per-conversation` 用 `target.read` 从 app 文档里查容器 id 再建远程环境。
在这类实现里，每次新建拿到的是同一个容器的轻量句柄，身份由 `ExecutionEnv.id` 表达——缓存与否由宿主决定，
框架不该替它决定。

## 五、不缓存为什么不会破坏一致性

跨实例需要协调的只有一件事：同一文件的并发写。pi-durable 用的是**模块级队列 + 环境 id**，与实例对象无关：

```js
// dist/tools/file-mutation-queue.js
const queues = new Map();
async function mutationKey(env, path, context) {
  const absolutePath = getOrThrow(await env.absolutePath(path, context));
  return `${env.id}\0${await canonical(env, absolutePath, context)}`;
}
```

- `NodeExecutionEnv.id` 恒为 `"node:local"`（`node.js:553`），所以新建的实例在队列看来就是同一个文件系统。
- 本地环境读写的都是同一批磁盘文件，没有内存快照，新实例看得见旧实例写的东西。

README 也是这么说的：

> A fresh environment object per call is fine: `edit` and `write` serialize changes to one file by the environment's `id`
> and path.

## 六、两次失败语义不同

| 场景 | 行为 |
|---|---|
| 工具调用时 `env` 抛错 | 变成该次调用的错误结果（`tool.js:326` 的 catch → `isError`），任务按失败收尾 |
| 渲染 sections 时 `env` 抛错 | `runtime.report(error, { type: "host", callback: "env" })`，渲染继续，`input.env` 为 `undefined`（`generation.js:60-67`） |

同一工厂、两处失败处理不同，也说明它的定位是「按需取用的资源构建器」，不是有生命周期的单例。

## 七、生命周期归宿主，不归 Harness

`ExecutionEnv.cleanup()` 是给宿主关停环境用的；Harness 自己的清理代码里没有任何 `env.cleanup()` 调用
（`grep cleanup dist/harness/*.js` 只命中注释与任务收尾）。**如果 SDK 自己缓存实例，销毁责任就没人承担**；
让宿主决定要不要缓存、并在需要时自己 `cleanup()`，责任划分才闭合。本项目因此显式选择「不缓存、不做单例」。

## 八、一句话总结

`env` 是「什么时候用、什么时候建」的资源构建器：构造免费、状态含义窄（`cwd` + pid 账本），
而协调靠 `id` + 模块级队列而不是对象身份——所以每次新建是最省事且唯一正确的做法。
