# 流式文本存在哪里

用户看到的流式输出，来自**已提交的状态文档**，由 watch 逐帧推送，不是把模型网络流直接画到屏幕上。

## 两个阶段，两个位置

| 阶段 | 存在哪里 | 内容 |
|---|---|---|
| 正在生成 | `docs["pi.live"]` 文档 | `generation.message`，`stopReason: "pending"` |
| 生成结束 | `entries` 转录 | 一条 `pi.assistant` 消息，`stopReason: "stop"` |

结束时 `pi.live` 被清空，所以空闲时它是 `{}`。流式气泡与正式消息是两份数据，不能同时渲染。

## 物理位置由 storage 决定

`Harness.open(storage, ...)` 的 `storage` 参数决定数据写到哪里：

| Storage | 位置 |
|---|---|
| `MemoryStorage` | 进程内存，关掉即丢失 |
| `openNodeSqliteStorage(path)` | `session.sqlite`（配合 `-wal` / `-shm`） |
| 其它实现 | IndexedDB、JSONL、Cloudflare D1 等 |

SQLite 中的表（与实际 schema 一致）：

```text
entries              转录：用户问题、模型回答、工具结果
documents            文档索引：kind / scope_kind / owner_id / retired_at
document_revisions   文档内容：kind = 'base' | 'delta'，content 是 JSON
conversations        会话记录
tasks                任务（含 pi.generation）
submissions          submit 产生的提交记录
```

`pi.live` 是会话级文档：`scope_kind = 'conversation'`、`owner_id = 会话 id`、`kind = 'pi.live'`。

它声明了 `history: "latest"`，因此只保留最新修订：每次写入新的 base 都会删除旧修订，流式中间态不会在库里堆积。

## 实测证据

在「模型刚吐出一句话」的瞬间，同时读内存与数据库：

```text
【内存里读到的实时文本】 "数据库事务是数据库管理系统中的一组逻辑操作单元"
【数据库里的 pi.live 最新修订】 [["s",["generation","message"],{"role":"assistant",
  "content":[{"type":"text","text":"数据库事务是数据库管理系统中的一组逻辑操作单元","index":0}],
  "stopReason":"pending",...}]]
【此刻 entries 表里的条目】 pi.user
```

两处文本一致；此刻 `entries` 里只有用户问题，回答尚未成为正式消息。

查库注意：`documents.kind` 存的是 JSON 字符串（带引号），SQL 需写 `kind = '"pi.live"'`，或参数绑定 `JSON.stringify("pi.live")`。

## 为什么要先写入库再推

| 直接画网络流 | 先写入库再推 |
|---|---|
| 刷新后中间态消失 | 刷新后可从已提交状态重建 |
| 主进程与渲染进程可能不一致 | 双方都读同一份已提交数据 |
| 崩溃后已生成部分丢失 | 已提交部分仍在，可继续生成 |

## 与流式速度的关系

`progress.partialIntervalMs`（默认 100ms）控制的是**提交频率**，即多久把当前进度写一次盘并发一帧：

- 调大：写盘更少、帧更少、每帧字数更多。
- 调小：写盘更频繁、帧更密。

它不控制模型生成速度，也没有「每帧固定 N 字」的开关。细节见 [7. watch订阅.md](./7.%20watch%E8%AE%A2%E9%98%85.md)。

## 一句话

模型边生成，pi-durable 边把当前完整文本分批提交进 `pi.live` 文档（落到 SQLite 的 `document_revisions`）；watch 把这些已提交的帧推给前端；结束时再写成一条 `pi.assistant` entry 存进 `entries` 表。
