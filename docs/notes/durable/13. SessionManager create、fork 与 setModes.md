# SessionManager：`create`、`fork` 与 `setModes`

## `manager.create()` 与 `manager.fork()` 的区别

两者都会创建新会话，默认所有权都是 `ownerless`，也都**不会自动切换** `manager.conversationId`。差异在于新会话的历史和配置来源。

| 行为 | `create()` | `fork()` |
| --- | --- | --- |
| 对话历史 | 空白，无父会话 | 继承当前会话截至 fork 点的历史 |
| `ConversationRecord.parent` | `undefined` | `{ conversationId, at }` |
| 后续消息 | 完全独立 | 从父历史继续，但后续与父会话独立分叉 |
| Agent 配置 | 新会话默认配置，或使用传入的 `agent` | 继承父会话在 fork 点的 agent 配置，也可由传入的 `agent` 覆盖 |
| 是否需要已有 entry | 不需要 | 需要；没有历史会报错 |

### `create()`：空白会话

```ts
const created = await manager.create()
```

它相当于新开一个完全空白的聊天。底层会话记录没有 `parent`，因此 `created.entries()` 不会读到当前会话的任何 entry。

### `fork()`：从当前历史创建分支

```ts
const forked = await manager.fork()
```

`fork()` 默认先取得当前会话最新 entry 的 ID，再调用 durable 层的 `conversation.fork(entryId, ...)`。新会话保存的是父链引用，而不是复制 entries：

```ts
{
  id: forkedId,
  parent: {
    conversationId: currentConversationId,
    at: latestEntryId,
  },
}
```

读取 `forked.entries()` 时，底层先读取 fork 自己的 entries；随后沿着 `parent` 链读取父会话中 `entry.id <= at` 的记录。因此 fork 能看见分叉前历史，但看不见父会话分叉后新增的记录。

```text
父会话：A → B → C
                 ├─ 父会话继续：D
                 └─ fork 会话继续：E
```

fork 会话可见 `A → B → C → E`，不可见 `D`；父会话可见 `A → B → C → D`，不可见 `E`。

> durable 层可能复制部分会话文档状态（例如 agent/config），但对话 entries 的历史继承通过 `parent` 链按需解析，不复制记录。

## `manager.setModes({ steeringMode: "all" })`

```ts
manager.setModes({ steeringMode: "all" })
```

这会把**会话忙碌期间，`steer` 类型输入的排队策略**改为 `"all"`。

默认策略是：

```ts
{
  steeringMode: "one-at-a-time",
  followUpMode: "one-at-a-time",
}
```

`one-at-a-time` 表示每到一个可处理边界，队列中只取一条消息；`all` 表示在下一个边界将该类别中所有排队消息一次放入。

### `steeringMode` 的作用范围

它只影响调用时明确指定：

```ts
await manager.submit(content, ctx, { whenBusy: "steer" })
```

的输入。

`steer` 的含义是：模型当前正在执行时，不等待整个 run 回答结束，而是在**当前工具调用轮结束后**加入正在运行的工作，用于补充或纠正指令。

例如模型运行期间连续提交三条 `steer`：

```text
1. 改成深色主题
2. 不要修改 API
3. 顺便补测试
```

- `steeringMode: "one-at-a-time"`：每个边界只放入一条排队 steer。
- `steeringMode: "all"`：下一个边界将三条排队 steer 一起放入当前运行上下文。

### 不会修改 `followUpMode`

该调用只修改 `steeringMode`，`followUpMode` 仍保持原值。`followUp` 是 `manager.submit()` 的默认忙时策略：它等待当前 run 结束，再作为下一轮 run 的输入。

若两类队列都要批量放入：

```ts
manager.setModes({
  steeringMode: "all",
  followUpMode: "all",
})
```

要让修改实际影响 durable harness 的入队行为，创建 `HarnessHost` 与 `SessionManager` 时必须共享同一个 `modes` 持有者：

```ts
const modes = defaultQueueModes()

const host = await HarnessHost.open({
  storage,
  models,
  registry,
  settings: () => ({ ...modes }),
})

const manager = await SessionManager.open({
  harness: host.harness,
  storage,
  modes,
})
```

否则 `setModes()` 虽会改变 `manager.modes`，但 harness 不会读取该对象，实际的排队行为不会改变。
