# 终态生成失败从哪里读取

**生成终态应读取持久化的 `SubmissionRecord`，不能只读 `pi.live.generation.retry`。** SDK 结束 run 时会清除 `generation`、`tools` 和 `nestedTools`；成功或失败的提交记录仍在 Storage 中。

## 已提交结果

相关 SDK 签名：

```ts
interface Submission {
  status(context: Context): Promise<SubmissionRecord>
  wait(context: Context): Promise<SettledSubmissionRecord>
}

interface Storage {
  scanSubmissions(query: SubmissionQuery, limit: number, cursor: Cursor | undefined,
    context: Context): Promise<Page<SubmissionRecord, Cursor>>
}
```

来源：`node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts`、`dist/types.d.ts`。

用户输入成功时为 `done`；没有回答时为 `unanswered`，带 `reason` 和可选 `detail`：

- `no_model`：未配置模型或模型不可用，不能期待 `detail` 总有消息。
- `model_error`：最终模型错误，`detail` 是错误文本。
- `faulted`：任务异常，SDK 把错误消息存入 `detail`。
- `aborted`、`reset`：用户主动终止或上下文边界，不应当作模型生成失败。

来源：`dist/harness/generation.js:failNoModel/failModelError`、`dist/harness/live.js:endRun/settleSchedulerOutcome`。

## 持续观察

`Session.subscribeCommits(listener)` 在成功提交且采用状态后同步发布 `CommitPublication.changes`。其中 `{ type: "submission", value: SubmissionRecord }` 是已持久化的状态，适合推送终态；回调不能阻塞或调用 Session API。

来源：`dist/types.d.ts:Session/CommitPublication/TableCommitChange`。

后续排队输入还没有开始，不能遮住刚失败的当前输入；恢复读取也应跳过 `write` 提交。客户端初次读取与推送可能交错，不能让迟到的 `queued/placed` 覆盖同一提交的终态。

流式展示仍来自已提交 live 文档，见 [流式文本存在哪里](./9.%20流式文本存在哪里.md)。
