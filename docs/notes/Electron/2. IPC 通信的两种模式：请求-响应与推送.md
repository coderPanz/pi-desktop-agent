# IPC 通信的两种模式：请求-响应与推送

**通信是上位概念，「推送」只是它的一种模式**——不能说「推送和通信是两个概念」，应该说「推送和请求-响应是通信的两种模式」。

Electron 里主进程与渲染进程只有这两条路，区别在「谁发起」和「有没有回话」：

| 模式 | API | 发起方 | 有返回值 | 语义 |
|---|---|---|---|---|
| **请求-响应** | `ipcRenderer.invoke` / `ipcMain.handle` | 渲染进程 | 有（Promise） | 事务：必须有一个处理者，失败带错误码 |
| **推送** | `webContents.send` / `ipcRenderer.on` | 主进程 | 无（单向） | 广播：谁订阅谁收到，0 个订阅者也照发 |

底层是同一套 Electron IPC（消息 + 结构化克隆），所以**不是两种技术，是两种用法**。

## 本仓库的具体对应

| 方向 | 物理通道 | 逻辑通道 | 类型契约 | 白名单 |
|---|---|---|---|---|
| 渲染 → 主 | `pi:invoke`（唯一入口） | 14 个 | `IpcMap`（request/response 成对） | `CHANNEL_LIST` |
| 主 → 渲染 | 4 个推送名 | — | `PushMap`（只有 payload） | `PUSH_CHANNELS` |

```ts
// 14 个命令通道：app.info / app.status /
//   conv.list / conv.open / conv.submission / conv.create / conv.submit /
//   conv.abort / conv.fork / conv.reset / conv.compact /
//   doc.get / approval.list / approval.respond
// 4 个推送通道：view / submission / host.status / approval
```

preload 只暴露两个方法，正好一种模式一个：`window.pi.invoke(channel, request)` 与 `window.pi.subscribe(channel, fn)`（返回取消订阅）。**永远不暴露 `ipcRenderer`**，否则页面能往任意通道发消息，上面的白名单就形同虚设。

两处白名单是互补的两半：`PUSH_CHANNELS` 管订阅（`packages/shared-types/src/bridge.ts`），`CHANNEL_LIST` 管命令（`apps/desktop/src/main/ipc.ts`），且后者用 `Exclude<IpcChannel, …> extends never` 让「漏写一个通道」变成编译错误。

## 为什么必须区分

1. **谁决定时机**：请求-响应由用户动作触发（点发送 → `conv.submit`）；推送由主进程状态变化触发（流式文本、审批到达），界面无法预知，只能订阅。
2. **失败怎么回**：`invoke` 能把失败压成 `{ ok: false, error: { code } }` 交给界面按 `BUSY` / `SESSION_FAILED` 分支；推送没有回执，出错只能在主进程打日志（`FrameHub` 的 `onError`）。
3. **状态归属**：推送天然属于「主进程是唯一写者」，界面拿到的是副本补丁（`ViewFrame`），不需要也不允许自己改状态再去问主进程。

## 常见误解

- 「主进程和渲染进程之间就这 4 个通道」→ 这 4 个只是**推送方向**的全部，命令方向还有 14 个。
- 「推送是一种独立机制」→ 它和 `invoke` 共用同一套 IPC 传输，只是没有请求/应答那一半，所以类型上也拆成 `PushMap`（无 request）而不是塞进 `IpcMap`。
