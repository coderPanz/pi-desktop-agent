# ipcMain 与 ipcRenderer 的四种组合

Electron 的 IPC 只有两个模块：**`ipcMain` 只在主进程可用，`ipcRenderer` 只在渲染侧（渲染进程 / preload）可用**。两边靠**通道名（字符串）**对齐，凑出四种组合：

| 组合 | 发送方 API | 接收方 API | 方向 | 能拿返回值 | 本仓库用了吗 |
|---|---|---|---|---|---|
| 双向调用 | `ipcRenderer.invoke(name, …args)` | `ipcMain.handle(name, fn)` | 渲染 → 主 | 能（`Promise`） | ✅ 唯一命令入口 |
| 单向发送 | `ipcRenderer.send(name, …args)` | `ipcMain.on(name, fn)` | 渲染 → 主 | 不能（fire-and-forget） | ❌ 没用到 |
| 单向推送 | `webContents.send(name, …args)` | `ipcRenderer.on(name, fn)` | 主 → 渲染 | 不能 | ✅ 四个推送通道 |
| 同步取回 | `ipcRenderer.sendSync(name, …)` | `ipcMain.on(name, fn)` 里 `event.returnValue = …` | 渲染 → 主 | 能，但**阻塞渲染进程** | ❌ 不推荐也别用 |

关键事实：

- **没有「主进程 invoke 渲染进程」这一半**。主进程想做请求-响应，只能 `executeJavaScript` 或自己造一对通道 + 事件关联。
- 接收方的回调签名是 `(event, ...args)`，`event` 是 `IpcMainInvokeEvent` / `IpcRendererEvent`（带 `sender`、`senderFrame`、`ports` 等）。
- **`event` 不能穿过 `contextBridge`**（不可克隆），所以在 preload 里必须先剥掉再交给页面：`const handler = (_event, payload) => listener(payload)`。

## 本仓库只保留两种组合

```
渲染进程 → 主进程：  ipcRenderer.invoke("pi:invoke", 逻辑通道名, 请求体)   ← 一条物理通道，14 个逻辑通道
主进程 → 渲染进程：  webContents.send(推送名, 载荷)                      ← 4 个推送名
```

preload 只暴露两个方法，正好一手一个：

```ts
window.pi.invoke(channel, request)     // → ipcRenderer.invoke(IPC_INVOKE_CHANNEL, channel, request)
window.pi.subscribe(channel, listener) // → ipcRenderer.on(channel, handler)（先查 PUSH_CHANNELS 白名单）
```

**不暴露 `ipcRenderer` 本体**是硬约束：一旦暴露，页面就能对任意通道发消息，白名单等于不存在。

## 主进程那个 handler 只做三件事

`apps/desktop/src/main/ipc.ts` 的 `registerIpc()` 收敛得很窄：

1. **校验发送方**：`isTrustedSender(event)` 比对 `event.sender.id` 与 `mainWindow.webContents.id`，不是自己窗口发来的一律拒绝；
2. **限制通道**：`CHANNELS.has(channel)`，只放行 `CHANNEL_LIST` 里的 14 个名字（`IpcMap` 的 key 漏写一个就编译失败）；
3. **原样回结果**：业务全在 `runtime.router.handle()` 里，它永不抛错，只返回 `{ ok: true, value }` 或 `{ ok: false, error: { code, message } }`。

由它返回的注销函数负责 `ipcMain.removeHandler(...)`——同一通道重复 `handle` 会报错，所以注册过就必须能撤。
