# 阶段 8：工具自举闭环

> **目标**：让 Agent 写一个工具，自动验证，用户确认后安装，立刻可用；坏工具进不来，旧调用不被打断。
> **预计**：1–2 周。**产出**：一个 `tool_create` 流程 + 一个可持续加载的工具目录。

---

## 1. 前置概念

- **自举 = 生成 → 校验 → 测试 → 安装 → 热替换**。缺任何一环都不是闭环。
- **工具代码是特权代码。** 它跑在主进程里，能读工作区、能发网络请求。V1 不是沙箱，只是「有人确认 + 静态检查 + 子进程试跑」。
- **安装是注册表操作**：`registry.install(extension)` 同名替换，**运行中的调用继续用旧代码**。
- **工具源文件不属于数据库。** `app.toolbox` 只存索引与状态，源码在 `userData/tools/<slug>/`。
- **版本只增。** 每次安装 +1；旧文件保留，便于回滚。
- **默认不自动安装。** 模型可以生成，但必须由用户点「安装」。
- **失败要能回滚。** 安装失败时，注册表必须回到安装前的状态。

## 3. 架构位置与模块协作

```
packages/extensions/toolsmith/src/
├─ index.ts            扩展：tool_create / tool_list 工具 + 任务
├─ docs.ts             AppToolboxDoc（session scope）
├─ build-task.ts       app.tool.build：spec → generate → validate → test → install
├─ generator.ts        构造提示词、解析模型输出
├─ validate.ts         静态检查（大小、导入、危险标识符、schema）
├─ loader.ts           动态 import 工具模块，注入依赖
├─ tester.ts           子进程试跑
└─ installer.ts        registry.install / 回滚 / 禁用

userData/tools/
└─ <slug>/
   ├─ tool.v1.mjs      当前版本
   ├─ tool.v2.mjs      新版本（安装前）
   ├─ meta.json        slug、name、version、hash
   └─ fixtures/        测试输入（可选）
```

调用关系：

```
模型调用 tool_create(spec)
  └─ 创建 build 任务，返回 taskId（不等待）
        └─ 任务 phase 推进 → 生成源码 → 校验 → 子进程试跑
              └─ 状态 verified，等用户确认
用户点「安装」
  └─ IPC tools.toggle {slug, enabled:true}
        └─ installer：import → 验证 → registry.install → 写 app.toolbox
```

**为什么拆成「验证」与「安装」**：模型生成的代码不能因为「跑通了测试」就自动获得特权。用户的确认是协议的一部分。

## 4. API 清单

| 目的 | API | 注意 |
|---|---|---|
| 定义扩展 | `defineExtension({name, tools})` | 名字稳定，如 `user.<slug>` |
| 安装 / 替换 | `registry.install(ext)` | 同名替换，立即发布 |
| 卸载 | `registry.uninstall(ext)` | 按名字 |

| 观察 | `harness.watchTaskGraph(ctx)` | 构建进度 |

## 5. 手写任务

### 5.0 落地顺序与可手写代码

先以静态校验拒绝明显危险源码，再在子进程试跑；只有 IPC 的用户确认路径能够调用安装器。

```ts
const FORBIDDEN = [/\beval\b/, /new\s+Function\b/, /process\.exit\b/, /\bchild_process\b/, /\bimport\s*\(/]; // 集中声明 V1 明确拒绝的危险标识符。
export function validateSource(source: string, slug: string): ValidationResult { // 定义不执行用户代码的静态校验入口。
  if (!/^[a-z][a-z0-9-]{2,40}$/.test(slug)) return { ok: false, diagnostics: ["slug 格式非法"] }; // 先限制文件和注册名的组成。
  if (source.length > 100 * 1024) return { ok: false, diagnostics: ["源码超过 100KB"] }; // 防止超大源码拖慢校验和加载。
  if (!/export\s+default\s+function\s+create\s*\(/.test(source)) return { ok: false, diagnostics: ["缺少默认工厂导出"] }; // 强制生成模块遵循宿主注入依赖的契约。
  if (/^\s*(import|require)\s*[(`"']/.m.test(source)) return { ok: false, diagnostics: ["不允许导入模块"] }; // 禁止工具从用户目录加载任意依赖。
  const hit = FORBIDDEN.find((rule) => rule.test(source)); // 查找第一个命中的危险模式。
  if (hit) return { ok: false, diagnostics: [`包含禁止模式: ${hit}`] }; // 将危险源码挡在动态导入之前。
  return { ok: true, diagnostics: [] }; // 只把基础合规源码交给后续子进程测试。
} // 结束静态校验函数。
export async function loadToolModule(file: string, version: number) { // 定义按版本绕过 ESM 缓存的加载函数。
  const mod = await import(`${pathToFileURL(file).href}?v=${version}`); // 使用带版本查询串的 file URL 加载模块。
  if (typeof mod.default !== "function") throw new Error("默认导出必须是工厂函数"); // 再次确认动态模块的导出形状。
  return mod.default({ Type, defineTool }); // 仅向已通过验证的工厂注入受控依赖。
} // 结束工具加载函数。
```

### 5.1 工具源码契约（先定，再生成）

生成的模块**不 import 任何包**，只导出一个工厂：

```js
// tool.vN.mjs
export default function create({ Type, defineTool }) {
  return defineTool({
    name: "user.<slug>",
    description: "...",
    parameters: Type.Object({ /* ... */ }),
    replay: "unsafe",
    executionMode: "parallel",
    async execute(args, api, ctx) {
      // 只通过 api.env 访问文件；返回值遵循 ToolExecutionResult
      return { output: "...", details: { ... } };
    },
  });
}
```

理由：

- 从 `userData/tools/` 加载时，`@earendil-works/pi-durable` 不在它的 `node_modules` 查找路径上；注入依赖能绕开打包后的解析问题。
- `Type` 与 `defineTool` 由宿主提供，生成器不需要知道版本。
- 工具想访问文件就用 `api.env`，而不是自己 `import "node:fs"`；这样测试时能换成 mock 环境。

**待验证**：打包后从 `userData` 动态 import 的行为、asar 对 `import()` 的影响。先在开发模式验证，再打包冒烟（见 5.9）。

### 5.2 `validate.ts`

按顺序检查，任何一条失败都返回 `{ok:false, diagnostics}`：

1. **大小**：源码 < 100KB；单行 < 8KB。
2. **导出形状**：必须是 `export default function create(...)`（用正则 + 实际 import 双重确认）。
3. **禁止导入**：`import` / `require` 任何模块（除了类型注释）。V1 一律禁止，减少解析问题。
4. **危险标识符**：`eval`、`new Function`、`process.exit`、`process.binding`、`child_process`、`import(`（动态）。
5. **工具定义**：`name` 以 `user.` 开头；description 20–500 字；parameters 是 TypeBox 对象；`execute` 是函数。
6. **结果合同**：静态扫描 `return` 里是否只出现 `output/structuredOutput/isError/details/diagnostics/usage/control`。
7. **slug**：`^[a-z][a-z0-9-]{2,40}$`，不与内置工具、已有工具重名。

静态检查只能挡低级错误，**不能替代试跑**，也不能当作安全边界。

### 5.3 `tester.ts`

子进程协议：

```
父：spawn(node, [runner.mjs, modulePath])
父 → 子（stdin）：{ type:"run", args, fixture }
子 → 父（stdout）：{ type:"result", ok, result } | { type:"error", message }
```

要求：

- **超时 10 秒**，超时杀进程组。
- 子进程 `cwd` 指向临时工作区（`mkdtemp`），`env` 只保留 `PATH` 等必要变量。
- 注入的 `api` 是 stub：`env` 用 `NodeExecutionEnv({cwd:temp})`；`output/details/commit` 记录调用；`executeTool` 返回错误（测试里不允许嵌套）。
- 至少跑两个用例：正常输入、非法输入。
- 断言结果对象可 JSON 序列化、字段类型正确、大小 < 1MB。
- **不要在父进程里直接 `import` 未验证的模块。**

### 5.4 `build-task.ts`

`defineTask({ name:"app.tool.build", version:1, ... })`，phase：

```
spec       规范化 spec：slug、name、description、参数 schema；检查冲突
generate   调模型生成源码；写入任务状态（≤100KB）
validate   静态检查；失败 → terminal failed（带 diagnostics）
test       子进程试跑；失败 → terminal failed（带 stdout/stderr 摘要）
verified   commit 状态 verified；写 app.toolbox.status = "verified"
install    仅当输入带 approved:true：装载 → registry.install → 写 enabled
done       terminal {status:"completed", result:{slug, version}}
```

- **不自动进入 install。** 任务在 `verified` 停下，等 IPC 的安装命令（或另一个任务）。
- 生成阶段的提示词必须包含：现有工具名、允许的返回字段、源码契约、禁止事项。
- 模型输出可能带 Markdown 代码围栏：解析时只取 ```js / ```javascript 块，且必须恰好一个。
- 同一 slug 的版本从 `app.toolbox.tools[slug].version + 1` 取；任务状态里记住目标版本。
- `abort` 清理临时文件，不改变已安装版本。

### 5.5 `loader.ts` + `installer.ts`

`loader.ts`：

```ts
export async function loadToolModule(file: string, version: number) {
  const mod = await import(pathToFileURL(file).href + `?v=${version}`);
  const factory = mod.default;
  if (typeof factory !== "function") throw new Error("默认导出必须是工厂函数");
  return factory({ Type, defineTool });
}
```

`installer.ts`：

```
1. 记录旧扩展（如果已安装）
2. load 新模块 → 得到 ToolRegistration
3. 校验 name 与 slug 对应
4. registry.install(defineExtension({ name: `user.${slug}`, tools: [tool] }))
5. commit 写 app.toolbox（version、sourcePath、installedAt、lastVerifyOk）
6. 失败：registry.install(旧扩展)（若有），写 lastError
```

**热替换语义**：正在跑的调用持有旧代码；下一次调用解析到新代码。你不需要手动中止任何东西。

### 5.6 `docs.ts`（`app.toolbox`）

沿用 [数据模型 4.3](../01-架构/03-数据模型与Document设计.md)，补三个字段：

```ts
{
  ...,
  status: "draft" | "verified" | "installed" | "disabled" | "failed",
  lastError: string | null,
  buildTaskId: number | null
}
```

### 5.7 `index.ts`（toolsmith 扩展）

提供两个工具：

- `tool_create`：参数 `{slug, description, parametersJson, behavior}`；创建 build 任务，返回 `{taskId}`。`replay:"unsafe"`，`executionMode:"sequential"`（避免同时装两个工具）。
- `tool_list`：参数 `{}`；列出已安装/已验证工具与状态；`replay:"safe"`。

不要在 `tool_create` 里 `await` 整个构建。任务返回后，让 UI 的任务面板显示进度；模型下一轮可以 `tool_list` 查状态。

### 5.8 IPC

- `tools.list`：读 `app.toolbox` + registry 快照。
- `tools.create`：创建 build 任务（供 UI 里的「新建工具」使用，参数与 `tool_create` 相同）。
- `tools.verify`：对已有 slug 重跑 validate + test。
- `tools.toggle`：`enabled:true` → install/启用；`false` → uninstall/禁用。**这是唯一触发安装的入口。**

`tools.toggle` 必须要求用户手势（UI 按钮），并在主进程再校验一次 slug。

### 5.9 `scripts/08-toolsmith.ts` + 打包冒烟

脚本流程：

1. 用固定 spec 创建 build 任务，等它到 `verified`。
2. 打印生成的源码与测试结果。
3. 手动调用 installer 安装。
4. 用 `root.configure({ tools: [...内置, "user.xxx"] })` 后提交一个会用到它的任务。
5. 修改 spec，再构建 v2，安装，确认旧调用不报错、新调用用 v2。
6. 故意提交一个含 `process.exit(1)` 的源码，确认 validate 拦下。

打包冒烟（必须做）：

- `electron-builder` 打一次包。
- 在打包后的应用里安装一个工具，重启应用，确认它仍可用。
- 如果动态 import 失败，记录错误，改为「构建时打包 loader / 用 `createRequire` 从 app 路径解析」的方案。

## 6. 实现提示

- **不要用 `eval` 执行源码。** 用动态 `import()`，失败就是失败。
- **版本号进 URL** 才能绕过 ESM 缓存；不要依赖删文件。
- **安装前先 import 再 install。** import 失败时注册表还没动，回滚简单。
- **工具名与 slug 分离。** slug 是文件名，name 是注册名；两者都要稳定。
- **`app.toolbox` 的写入与 `registry.install` 不在同一个事务里。** 顺序：先 install（内存），再 commit（磁盘）；如果 commit 失败，下一次启动会从磁盘恢复，内存里的工具会消失——可接受，但要记录日志。
- **禁用 = uninstall**，不是跳过。禁用后模型不应再看到它。
- **测试用例要包含「工具抛错」**，确认框架会把它转成 `isError`，而不是杀会话。
- **子进程不是安全沙箱。** 工具仍能访问网络与磁盘；不要宣称「安全隔离」。V1 的安全来自「用户确认 + 代码可读 + 只在本地运行」。
- **构建任务可能很慢。** 给它 `background:true`，避免阻塞普通会话的 idle 判断。
- **模型生成的 schema 可能过宽**（例如 `Type.Any()`）。validate 里限制：不允许 `Any`、`Unknown`，参数必须有 description。
- **先只支持单文件工具。** 多文件、依赖安装、npm 包一律不做。

## 7. 调试方法

| 想知道 | 做法 |
|---|---|
| 生成失败 | 打印模型原始输出（截断）与解析错误 |
| 测试失败 | 子进程 stdout/stderr、退出码、超时 |
| 装上了但模型看不到 | `registry.snapshot()`、`agent.tools`、conversation 的 `configure` |
| 热替换没生效 | 打印两次 `registry.snapshot()` 的 tool 对象引用 |
| 重启后工具消失 | `app.toolbox` 是否 commit；启动时是否执行「恢复安装」 |
| 工具名冲突 | 启动时扫描 registry 与 app.toolbox |
| 动态 import 报错 | 路径、协议（`file://`）、打包后的 asar 路径 |
| 旧调用被中断 | 确认 installer 没有 uninstall 再 install 的间隙 |

**启动时的恢复安装流程**要单独写：读 `app.toolbox` 中 `enabled:true` 的项 → 逐个 load + install → 失败的标 `failed`，不影响启动。

## 8. 验收标准

- [ ] 固定 spec 能生成一个可用工具，测试通过后状态为 `verified`。
- [ ] 未点安装前，模型看不到该工具。
- [ ] 点安装后，下一轮对话模型能调用它。
- [ ] 安装 v2 时，正在执行的 v1 调用正常结束；之后的调用用 v2。
- [ ] 含 `process.exit` / `eval` / `import` 的源码被 validate 拦下，注册表不变。
- [ ] 测试超时的工具被标失败，主进程不卡死。
- [ ] 安装过程中 import 失败，注册表保持旧版本，`lastError` 有记录。
- [ ] 重启应用后，已安装工具仍可用（恢复安装流程生效）。
- [ ] 禁用后模型不再看到该工具；重新启用恢复。
- [ ] 同名 slug、与内置工具同名，都被拒绝。
- [ ] 打包后的应用能完成一次安装与重启恢复（或有明确记录的替代方案）。
- [ ] 构建任务中途 `kill -9`，重启后不会留下半个注册项。

## 10. 常见失败

| 现象 | 原因 | 修法 |
|---|---|---|
| 源码解析不到 | 模型输出带多余代码块 | 只取唯一代码块，否则失败 |
| import 报找不到包 | 工具目录不在 node_modules 解析链上 | 注入依赖，不让工具 import |
| 工具装上但不可调用 | 未加入 conversation 的 tools | `configure` 或默认工具集 |
| 旧调用报错 | installer 先 uninstall | 只 install，不 uninstall |
| 重启后全部消失 | 没做恢复安装 | 启动读 app.toolbox |
| 工具名重复 | 未校验 builtin 与 registry | 启动 + 安装双重校验 |
| 子进程挂住 | 没有超时/没杀进程组 | timeout + SIGKILL |
| 内存暴涨 | 工具输出无上限 | outputLimits + 结果大小检查 |
| 用户误点安装恶意代码 | 没有确认/没有展示源码 | 安装前 diff + 显式确认 |
| 打包后 import 失败 | asar / 路径问题 | 冒烟验证，准备 bundle 方案 |
