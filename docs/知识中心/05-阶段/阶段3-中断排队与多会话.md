# 阶段 3：中断、排队与多会话

> **目标**：把脚本变成一个可交互的会话管理器：能停止、能排队、能开多个会话、能分叉。
> **预计**：2–3 天。**产出**：一个 REPL + 一组可以复现的并发行为记录。

---

## 1. 前置概念

- **提交 ≠ 运行 ≠ 完成**。`submit()` 只是收件；忙碌时它会进入 `pi.inbox`，这是持久化状态，不是内存队列。
- **两种忙碌策略**：
  - `followUp`：等当前这一轮（含工具）全部结束再处理。
  - `steer`：在当前工具轮结束后、模型下一次请求前插入。
  - `reject`：直接抛 `ConversationBusy`，什么都不写。
- **`abort()` 取消的是任务，不是等待。** 取消 `ctx` 只让 `wait()` 提前返回，模型还在跑。
- **中断后部分回答不会消失**，它会作为一条 `pi.assistant` 留在转录里。
- **一个会话一条时间线。** 多会话是多个 `Conversation`，不是多个线程。
- **fork 复制历史与配置**，但产生新的 provider session；`reset` 不复制，只开新上下文。
- **压缩是任务**，不是同步函数；它会写一条 `pi.compaction`。

## 3. 架构位置与模块协作

```
scripts/03-cli.ts            交互循环：读一行 → 解析命令 → 调 manager
packages/core/src/session/manager.ts
   ├─ open(id)               取/建 Conversation，挂 watch
   ├─ submit(id, text, mode) 生成 requestId，按 whenBusy 提交
   ├─ abort(id)              conversation.abort(ctx)
   ├─ fork(id, entryId)      conversation.fork(...)
   ├─ reset(id, handoff)     conversation.reset(...)
   ├─ compact(id, hint)      conversation.compact(...)
   └─ inbox(id)              snapshot(InboxDoc, ...)
```

`manager` 是**纯 Node** 的，不依赖 Electron。阶段 5 的 `HarnessHost` 会复用同一套方法，只是把终端换成 IPC。

```
输入行 ──▶ 命令? ──是──▶ manager 对应方法
              │
              否
              ▼
        manager.submit(activeId, text, defaultMode)
              │
              ▼
        watch 回调打印（按 convId 前缀区分会话）
```

## 4. API 清单

| 目的 | API | 注意 |
|---|---|---|
| 忙碌策略 | `submit({whenBusy})` | 默认 `followUp`；`reject` 抛错 |
| 全局策略 | `settings.steeringMode` / `followUpMode` | `"all"` 或 `"one-at-a-time"` |
| 中断 | `conversation.abort(ctx, {background?})` | 返回时普通任务已 terminal |
| 撤回单条 | `harness.abortSubmission(id, ctx, convId?)` | 不影响已开始的 run |
| 看排队 | `session.snapshot(InboxDoc, convId, ctx)` | 返回 `undefined` 表示没有文档 |
| 分叉 | `conversation.fork(at, options, ctx)` | `at` 是可见 entry id |
| 新上下文 | `conversation.reset(handoff, ctx)` | 写 `pi.reset` |
| 压缩 | `conversation.compact(instructions, ctx)` | 返回 `TaskId<CompactionResult>` |
| 等空闲 | `conversation.waitForIdle(ctx)` | 只等普通所有权 |
| 找会话 | `harness.conversation(id, ctx)` | 不存在返回 `undefined` |
| 建会话 | `harness.createConversation({ownership, agent?, init?}, ctx)` | `ownership` 必填 |
| 多会话观察 | 每个 `conversation.watch(ctx)` 一个句柄 | 回调里带 `convId` 前缀 |
| 任务面板 | `harness.watchTaskGraph(ctx)` | 观察排队/运行/等待 |
| 出错 | `ConversationBusy` | 只在 `reject` 时出现 |

## 5. 手写任务

### 5.0 落地顺序与可手写代码

先把无副作用的会话管理 API 写成类，再由 CLI 负责输出；下面的类型名称以实际 Harness 导出为准。

```ts
import { randomUUID } from "node:crypto"; // 引入跨重启不重复的请求标识生成器。
export class SessionManager { // 定义不依赖终端输出的会话管理器。
  readonly watches = new Map<string, WatchHandle<ConversationView>>(); // 按会话保存订阅句柄。
  readonly ids = new Set<string>(); // 保存已知会话标识以便列举。
  activeId: string | null = null; // 记录当前由 CLI 选中的会话。
  constructor(readonly harness: Harness) {} // 通过构造函数注入唯一的 Harness。
  async submit(id: string, text: string, whenBusy: "followUp" | "steer" | "reject", ctx: Context) { // 提交一条可对账的输入。
    const conversation = this.harness.conversation(id, ctx); // 取得目标会话而不假设它存在。
    if (!conversation) throw new Error("会话不存在"); // 对错误会话 id 立即失败。
    const requestId = randomUUID(); // 为每一次提交创建全新的幂等键。
    const submission = await conversation.submit({ type: "input", content: text, requestId, whenBusy }, ctx); // 将忙碌策略交给 Harness 调度。
    return { requestId, submissionId: submission.id }; // 返回可写入日志的两个标识。
  } // 结束提交方法。
  async abort(id: string, ctx: Context) { // 定义真正取消运行任务的方法。
    const conversation = this.harness.conversation(id, ctx); // 重新读取会话以避免使用过期引用。
    if (!conversation) throw new Error("会话不存在"); // 阻止对不存在会话的取消。
    await conversation.abort(ctx); // 调用 Harness 的取消而不是取消 wait Promise。
  } // 结束取消方法。
} // 结束会话管理器定义。
```

### 5.1 `packages/core/src/session/manager.ts`

一个类，持有：

- `harness`
- `watches: Map<convId, WatchHandle>`
- `activeId`

方法：

| 方法 | 要做的事 |
|---|---|
| `ensureWatch(id, onFrame)` | 取 `watch.value`，`start()`，把 `(id, value, ops)` 交给回调 |
| `list(ctx)` | `harness.conversation` 只能按 id 取；列表要靠你维护的 id 集合，或后续从存储扫描 |
| `create(ctx)` | `createConversation({ownership:{kind:"ownerless"}})` |
| `submit(id, text, mode)` | `requestId = randomUUID()`；`whenBusy` 由参数决定 |
| `abort(id)` | 调 `abort()`，返回耗时 |
| `fork(id, entryId)` | 新会话 id 记录进集合，继承 watch |
| `reset(id, handoff)` | `handoff` 是一段字符串，说明为什么开新上下文 |
| `compact(id, hint)` | 拿到 `TaskId` 后 `waitForTask` |

要求：

- **不要在 manager 里打印。** 它只返回数据 / 抛错，打印由 CLI 负责。这样阶段 5 能直接复用。
- `requestId` 每次都新生成，并**返回给调用方**，便于日志对账。

### 5.2 `scripts/03-cli.ts`

用 `node:readline/promises`，实现命令：

```
/new                      新建会话并切换
/list                     列出会话：id、entry 数、是否忙碌
/switch <id>              切换
/abort                    中断当前会话
/fork <entryId>           从某条 entry 分叉并切换
/reset                    开新上下文（要求输入 handoff）
/compact [提示]           压缩
/inbox                    打印排队输入
/mode followup|steer      切换默认 whenBusy
/exit
```

其余输入一律视为消息，发到当前会话。

要求：

- 每行输入只创建**一个** submission。
- 打印帧时带 `[convId 前 6 位]` 前缀；只打印 assistant 文本与工具状态摘要。
- `/list` 的「忙碌」判断用 `inspect()` 或 `pi.live.run`，不要用「有没有未完成的 promise」猜。

### 5.3 行为实验（必须实际跑）

`scripts/03-scenarios.ts`：不交互，按脚本触发并记录结果。

1. **排队**：在回答进行中连发两条（默认 `followUp`），确认两条都在回答结束后按序处理。
2. **steer**：在工具执行中发一条 `steer`，确认它插在工具轮与下一次模型请求之间。
3. **reject**：忙碌时发 `reject`，捕获 `ConversationBusy`，确认 `entries` 没有新增。
4. **abort**：回答中途 `abort()`，确认：调用返回后无 running 任务；已生成部分保留为 assistant entry。
5. **fork**：分叉后各发一条不同消息，确认两条时间线互不污染。
6. **reset**：`reset` 后发消息，确认模型不再看到旧历史（看 `conversation.context(ctx)` 的 `messages`）。
7. **compact**：手动触发压缩，确认新增 `pi.compaction`，且 `context().messages` 变短。

每项记录：输入序列、关键时间点、`inspect()` 快照、最终 entry 列表。

## 6. 实现提示

- **默认用 `followUp`。** `steer` 会让模型的上下文在工具轮中途变化，调试成本高；把它留作显式选择。
- **`one-at-a-time` 更可预测。** `steeringMode` / `followUpMode` 先都设成 `"one-at-a-time"`，观察队列行为；再试 `"all"` 对比。
- **`abort()` 之前先打印 `inspect()`。** 你要能说清楚被取消的是哪个 task、哪个 submission。abort 之后不会留下「取消原因 entry」，所以证据只能来自运行前后的对比。
- **不要用 `Promise.race` 模拟中断。** 那只是不等了，任务还在跑。唯一正确的中断是 `abort()` / `abortTask()`。
- **fork 的 `at` 用可见 entry。** 从 `entries()` 拿 id；不要用 assistant 内部的消息 id。
- **fork 后立刻 `watch`。** 新会话的帧不会从旧 watch 来。
- **`reset` 的 handoff 写清楚「为什么」。** 它会进模型上下文；一句话比「重置」有用得多。
- **压缩 await 完成再继续。** `compact()` 返回的是 TaskId，任务没结束就发消息会排在它后面，看起来像卡住。
- **多会话的打印会交错。** 用 convId 前缀 + 单行摘要；不要跨行打印 JSON。
- **切换会话不销毁 watch。** 销毁后再建会丢掉「切换期间发生的变化」；V1 保持所有会话都订阅，帧率不高。

## 7. 调试方法

| 想知道 | 做法 |
|---|---|
| 当前有哪些任务 | `console.dir(await harness.inspect(ctx), {depth: 6})` |
| 排队里有什么 | `await session.snapshot(InboxDoc, convId, ctx)` |
| 为什么不动 | `harness.wake()`；`inspect()` 的调度判定 |
| abort 是否真的停了 | abort 前后各打一次 `inspect()` 的活任务数 |
| 分叉是否独立 | 两个会话各打 `entries()` 的 id 前缀 |
| 压缩是否生效 | `context().messages.length` 前后对比 |
| 队列顺序 | 每条 submission 打印 `requestId` 与创建顺序 |

**不要靠 setTimeout 猜时序。** 用 `waitForIdle()`、`waitForTask()`、`submission.status()` 做同步点。

## 8. 验收标准

- [ ] 忙碌时连发两条，按顺序处理，没有丢失。
- [ ] `steer` 的插入点确实在当前工具轮之后、下次模型请求之前（用工具日志证明）。
- [ ] `reject` 抛出 `ConversationBusy`，且会话内容不变。
- [ ] `/abort` 后 1 秒内会话 idle；已生成的部分回答仍在。
- [ ] 取消 `submission.wait()` 的 ctx，任务仍在跑（这是预期行为，你能解释）。
- [ ] `/fork` 后的两个会话互不影响；两边 `entries()` 有共同前缀、不同尾部。
- [ ] `/reset` 后 `context().messages` 不再包含旧消息。
- [ ] `/compact` 后 messages 变短，且有 `pi.compaction`。
- [ ] 切换会话时，后台会话仍能完成并打印。
- [ ] `manager` 里没有任何 `console.log`。

## 10. 常见失败

| 现象 | 原因 | 修法 |
|---|---|---|
| 第二条消息覆盖第一条 | 每次 `submit` 用了相同 `requestId` | 每次新生成 |
| 忙碌时直接报错 | 传了 `whenBusy:"reject"` | 改 `followUp` |
| abort 后任务还在 | 取消的是 `wait` 的 ctx | 调 `conversation.abort()` |
| abort 卡住 | 有后台任务未结算 | 试 `{background:true}`，并检查是谁创建的 |
| fork 后没有历史 | 用了 `reset` | 用 `fork(at, ...)` |
| fork 报错 | `at` 不是可见 entry | 从 `entries()` 取 id |
| 压缩后仍很长 | 等的是 `compact()` 返回，不是任务完成 | `waitForTask(taskId)` |
| 多会话输出串行 | 共用一个 watch 回调队列 | 每会话独立 watch，打印带 id |
| `InboxDoc` 为空 | 文档从未写过 | `undefined` 是正常值，不是 bug |
| 切换后旧帧丢失 | 切走时停了 watch | 保持订阅 |
