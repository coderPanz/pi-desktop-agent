# 存储、错误与恢复

> 「durable」不是「会自动保存」。它是一组明确的承诺：**提交原子、ID 单调、崩溃后从检查点继续、错误分级**。
> 这一篇讲这些承诺的边界，以及越界时会发生什么。

---

## 1. `Storage` 到底要提供什么

```ts
interface Storage {
  commit(writes: readonly StorageWrite[], context: Context): Promise<Seq>;
  mintId<I extends Id<string>>(): Promise<I>;
  conversation(id, ctx): Promise<ConversationRecord | undefined>;
  scanConversations(query, limit, cursor, ctx): Promise<Page<...>>;
  entry(...) / scanEntries(...) / findLatestHeadMarker(...)
  task(...) / scanTasks(...)
  submission(...) / scanSubmissions(...) / submissionByRequest(...)
  findDocument(...) / document(...) / scanDocuments(...)
  close(context): Promise<void>;
}
```

（已核实，`dist/types.d.ts`。）

你自己写 Storage 实现时，只要满足四条就能用：

1. `commit()` 原子：一批 writes 要么全可见，要么全不可见。
2. `commit()` resolve 之后，后续读取必须能看到这批写入。
3. `mintId()` 必须单调，**跨重开也成立**。Harness 用 ID 顺序当作创建顺序。
4. `close()` 之后所有操作必须 reject。

其它方法按签名实现即可；语义细节（分页、可见性、ancestry）比实现难，V1 不要自己写 Storage，用官方 SQLite。

## 2. 三种存储怎么选

| | `MemoryStorage` | SQLite | JSONL |
|---|---|---|---|
| 重启保留 | 否 | 是 | 是 |
| 原子性 | 进程内 | 事务 | 单条追加 |
| 性能 | 最快 | 好 | 差（全文件重写风险） |
| 适用 | 测试、阶段 0–3 | **生产** | 审计、导出、调试 |
| 打开 | `new MemoryStorage()` | `openNodeSqliteStorage(path, opts)` | `openNodeJsonlStorage(dir, ctx, {fsync})` |

V1 只用前两个。JSONL 留给「导出会话」功能，不要作为主存储。

### SQLite 打开参数（已核实）

```ts
await openNodeSqliteStorage(path, {
  busyTimeoutMs: 5000,             // 默认 5000
  walAutoCheckpointPages: 1000,    // 默认 1000；0 关闭自动 checkpoint
  prefix: "app_",                  // 表名前缀，默认无
});
```

`SqliteStorage` 用的是 Node 内置 `node:sqlite`（`DatabaseSync`），**没有原生模块编译**。这是它相对 better-sqlite3 的最大优势。

## 3. 单写者：一个文件，一个 Harness

框架**不提供跨进程锁**。两个进程同时打开同一个 SQLite 文件，WAL 会让它们都能写，然后状态分叉。

Electron 里必须做三件事：

1. `app.requestSingleInstanceLock()`，第二个实例直接退出并聚焦已有窗口。
2. Harness 只在主进程创建，渲染进程永远不 import pi-durable。
3. 开发时如果起了两个 `electron .`，先确认旧进程真的退出了（`lsof session.sqlite`）。

**读**可以多进程吗？SQLite 本身允许，但 Harness 的调度器会写任务状态，所以「只读进程」也不安全。V1 不做多进程。

同一个进程内开两个 Harness 指向同一个文件，同样是错的。要多个「会话」，用多个 `Conversation`，不是多个 Harness。

## 4. 提交边界与「最多丢多少」

| 内容 | 提交时机 | 崩溃最多丢 |
|---|---|---|
| 用户输入 | `submit()` 内 | 无（返回即已落盘） |
| 排队输入 | 写入 `pi.inbox` 时 | 无 |
| 部分回答 | 默认每 100ms | 最后一个窗口（~100ms 文本） |
| 工具意图 | 执行前 | 无 |
| 工具输出增量 | 默认每 100ms | 一个窗口 |
| 工具最终结果 | 工具结束时，一个 commit | 无（要么有要么没有） |
| 任务状态 | 每次 `rt.commit()` / 检查点 | 自上个检查点以来的阶段进度 |
| 文档修改 | 所在 commit | 与所在 commit 一致 |

可调：

```ts
settings: {
  progress: { partialIntervalMs: 100, outputIntervalMs: 100 },
}
```

**不要为了「不丢字」把间隔设成 0。** 每个 token 一次事务会把 SQLite 写满，且 UI 帧率反而下降。

## 5. 崩溃后到底恢复什么

```
进程被杀
  ↓
重启，打开同一个 Storage
  ↓
Harness.open(...)
  ↓
harness.resume()
```

恢复规则（已核实）：

- **已提交的**：全部在。转录、文档、任务记录、submission 状态。
- **`running` 的任务**：重新变为 `pending`，按定义重新调度。它从**最后一个检查点**继续，不是从头。
- **`replay: "safe"` 的工具**：重跑。
- **`replay: "unsafe"`（默认）的工具**：不重跑；模型看到「调用被中断」的结果。
- **排队输入**：仍在 `pi.inbox`，继续等。
- **`sleeping` 任务**：按 Harness 时钟到期后继续。
- **provider 会话（`pi.provider`）**：UUIDv7 保留，prompt cache / 会话亲和性不丢。
- **同一个 `requestId` 再提交**：返回已有 submission，不重复执行。

**不恢复的**：你在内存里维护的任何东西。包括「已发送但未 commit 的 UI 状态」「工具内部缓存的句柄」「`setTimeout`」。

## 6. 崩溃循环与 park

如果某个任务每次恢复都在下一个检查点前把进程搞崩，它会无限重启。框架的护栏：

- 每次崩溃/驱逐/重置给该任务计数 +1；正常 `close()` 不计；任务提交新状态后计数归零。
- 达到 `settings.restartLimit`（默认 **5**）后，任务被 **park**：状态 `blocked`，原因 `restart_limit`。
- `harness.inspect()` 与任务图都能看到。
- `onReport(error, {type:"task_parked", task})` 会收到一次。
- 用 `harness.retryTask(id, ctx)` 手动再跑一次。

UI 必须给 park 的任务一个入口（「重试」/「放弃」），否则用户会看到「永远卡住」。

`abortTask()` 仍会执行 abort 处理器；abort 处理器本身被中断到上限，任务以 `faulted` 结束。

## 7. 错误分级（再强调一次）

| 错误 | 范围 | 谁承担 | 应用该做什么 |
|---|---|---|---|
| Storage 失败 | 整个 Session | `SessionFailed`，Harness 关闭 | 监听 `harness.closed`，重建 |
| 非法读请求 | 单次调用 | `StorageRequestError` | 修正参数 |
| commit 内读写顺序错误 | 单次调用 | `ReadAfterWrite` | 改用 `tx` |
| 模型请求失败 | 当前 run | 任务失败/重试 | 提示用户，保留输入 |
| 工具抛错 | 单次工具调用 | 转成 `isError` 结果 | 无 |
| Hook 抛错 | 该 Hook | `onReport` 后跳过 | 记录并修 |
| 任务阶段抛错 | 该任务 | `task_faulted` | 展示失败原因 |
| 定义缺失/版本不兼容 | 该任务 | `blocked`（`missing_definition` / outdated） | 装回扩展，或迁移 |

`onReport` 的 `info.type`（已核实）：`session_failed`、`task_faulted`、`task_parked`、`migration_failed`、`task_outdated`、`task_error`、`extension_error`、`host_error`、`listener_error`。

**不要吞掉 `session_failed`。** 把它当普通异常 `catch` 掉，然后继续调用 Harness，只会得到更多 `SessionFailed`。

## 8. 重建流程（主进程）

```ts
async function openHarness(): Promise<HarnessHost> {
  const storage = await openNodeSqliteStorage(dbPath, { busyTimeoutMs: 5000 });
  const harness = await Harness.open(storage, options, ctx);
  harness.resume();
  const root = await harness.root(ctx);

  harness.closed.then(async (end) => {
    if (end.reason !== "failed") return;
    await rebuild();          // 只重建一次，带退避
  });

  return { harness, root, storage };
}
```

重建时必须：

1. `watch.stop()` 所有旧 watch。
2. 关闭所有窗口的推送，标记「重连中」。
3. 重新 open → resume → 重新 `conv.open` 推整帧。
4. 如果连续失败（比如磁盘满），退避并显示可操作的错误，不要静默重试。

**不要**在 `closed` 回调里直接 `await harness.close()`——已经关了。

## 9. 迁移与兼容

- SQLite 存储有自己的 schema（1.4.0 为 v2）。用 **1.3.0 打开 1.4.0 的库会失败**；反过来也不保证。
- Document 的 `version` 与 `migrate()` 是**应用层**迁移，与 SQLite schema 无关。
- Task 的 `version` 与 `migrate(input, checkpoint, fromVersion)` 同理；迁移失败会导致 `blocked`/`task_outdated`。
- Extension 被卸载后，它定义的任务无法运行，任务图里显示 blocked。装回去即可恢复。

升级 SDK 前：

```bash
# 先备份
cp session.sqlite session.sqlite.bak
cp -r session.sqlite-wal session.sqlite-wal.bak 2>/dev/null || true
```

WAL 模式下，**只复制主文件可能丢掉最近事务**。正确备份方式：

```sql
VACUUM INTO 'backup.sqlite';
```

或者先正常关闭 Harness（`close()` 会 checkpoint），再复制。

## 10. 怎么写「崩溃测试」

这是本阶段最重要的练习，不是可选项。

### 方法 A：`process.exit(1)` 注入

在工具或任务阶段里加一个环境变量开关：

```ts
if (process.env.CRASH_AT === "after-intent") process.exit(1);
```

跑一次，确认崩溃点；去掉开关，重启，观察恢复。

### 方法 B：`kill -9`

```
node script.mjs & echo $! > /tmp/pid
sleep 2 && kill -9 $(cat /tmp/pid)
```

`kill -9` 比 `SIGTERM` 更真实：没有清理机会，WAL 靠 SQLite 自己恢复。

### 必须覆盖的五个场景

| # | 崩溃点 | 期望 |
|---|---|---|
| 1 | `submit()` 返回后立刻 | 重启后用户消息还在，回答会继续 |
| 2 | 工具意图已写、执行中 | 重启后 safe 工具重跑，unsafe 得到中断结果 |
| 3 | 工具结果已写、模型还没收到 | 重启后模型看到结果，不重复执行 |
| 4 | 部分回答提交后 | 重启后能看到已生成的部分 |
| 5 | 任务两个检查点之间 | 重启后从上一个检查点继续，不从头 |

每个场景都要记录：**重启后第一次 `snapshot()`/`entries()` 看到了什么**。这是验收证据。

## 11. 诊断工具

```ts
// 当前调度状态：谁在跑、谁被 blocked、为什么
console.dir(await harness.inspect(ctx), { depth: 5 });

// 任务图：所有权、状态、是否 background
const graph = await harness.taskGraph(ctx);
console.dir(graph.value, { depth: 5 });

// 是否需要唤醒
console.log(harness.wake());
```

排查顺序：

1. `wake()` 是 `{}`？→ 没有可跑任务，检查输入是否真的进了 inbox。
2. `inspect()` 有 `blocked`？→ 看 reason：`missing_definition` / `restart_limit` / `migration`
3. 任务 `pending` 但不动？→ 忘了 `resume()`，或 Harness 已关闭。
4. `closed` 已 failed？→ 看 `SessionEnd.error`，通常是 Storage。

## 12. 常见失败

| 现象 | 原因 | 修法 |
|---|---|---|
| 重启后任务不继续 | 没调 `resume()` | 启动流程固定加一行 |
| 两个窗口状态不一致 | 各开了一个 Harness | 单实例锁 + 主进程单 Harness |
| 备份恢复后丢最近消息 | 只拷了 `.sqlite`，没拷 `-wal` | `VACUUM INTO` 或先 `close()` |
| 升级 SDK 后打不开 | schema 版本不兼容 | 备份 + 迁移 + 统一版本 |
| 磁盘满后应用假死 | `session_failed` 被吞 | 监听 `closed`，显示错误并停止写入 |
| 任务无限重启 | 没设 `restartLimit` 或 UI 无重试入口 | 用默认 5，展示 parked |
| `requestId` 重复导致消息丢失 | 用了固定字符串 | 每次用户输入生成新 UUID |
| 崩溃测试「通过」但数据不对 | 只检查了进程退出，没检查恢复后的状态 | 断言语义，不断言存活 |
