# 状态订阅与增量同步

> 渲染进程不需要「重新拉一遍数据」。它需要**一帧初始值**，然后**一串操作**。

---

## 1. 四种读状态的方式

| API | 形态 | 首次值 | 适用 |
|---|---|---|---|
| `session.snapshot(token, …)` | `Promise<T \| undefined>` | 一次性 | 命令处理、判断 |
| `conversation.viewState(ctx)` | `AttachedReplicatedState<ConversationView>` | `.value` 同步可用 | 主进程内部订阅 |
| `conversation.watch(ctx)` | `WatchHandle<ConversationView>` | `.value` = attach 时快照 | **跨 IPC** |
| `session.watchDoc(token, …)` | `DocumentWatch<T> \| undefined` | 文档不存在则 undefined | 只关心一个文档 |

`documentState()` 是 `AttachedReplicatedState<Readonly<T> | null>`，`null` 表示文档存在但当前值为空，`undefined`（整个状态对象）不会出现。

`viewState()` 与 `watch()` 的数据相同，区别只有一个：**`viewState` 回调不给 ops，`watch` 给。** 跨进程要 ops 来避免整包重传。

## 2. `watch()` 的真实时序

```ts
const watch = await root.watch(ctx);
// watch.value 已经是 attach 时刻的完整 ConversationView

watch.start(async (value, ops, ctx) => {
  // 只会在 start 之后的 commit 上被调用；不会 inline 调用
  await sendToRenderer(ops);
});

await watch.stop();          // { reason: "stopped" | "cancelled" | "retired" | ... }
```

已核实的四条语义：

1. **`start()` 不内联回调。** 不要依赖「start 之后立刻收到第一帧」。
2. **不重放历史。** 晚加入的客户端从 `watch.value` 开始，之后只收新帧。
3. **同一时刻只有一个回调在跑。** 回调是异步串行的。
4. **最多积压 100 帧。** 超过后，用**一整帧最新值**替换所有待发帧；客户端会看到 sequence 跳号。

第 4 条决定了协议设计：**渲染端必须能处理「整帧」而不只是「增量」**。整帧在 chord 里的形态是 `[["r", value]]`，用 `isBase(ops)` 判断。

`watch.value` 在投递后更新为最新已投递值。可以用它做兜底：回调抛错后，下次用 `watch.value` 重新同步。

`stop()` 是幂等的。`closed` 在终止时结算，可能带 `session_failed`、`listener_error` 等原因——**监听它**，不要假设 watch 永远活着。

## 3. `Op` 的语法

`Op` 是 JSON 元组（已核实，`chord/dist/delta`）：

| 操作 | 形状 | 含义 |
|---|---|---|
| `r` | `["r", value]` | **替换整个值**（唯一能作用于根的操作） |
| `s` | `["s", path, value]` | 设置某路径 |
| `d` | `["d", path]` | 删除某路径 |
| `a` | `["a", path, str]` | 在字符串末尾追加（流式文本的核心） |
| `t` | `["t", path, n]` | 把字符串截断到 n 个字符 |
| `p` | `["p", path, start, deleteCount, items]` | 数组拼接 |
| `m` | `["m", path, permutation]` | 数组重排：`new[i] = old[perm[i]]` |

`path` 是 `(string | number)[]`。`s/d/a/t` **不能**作用于根（类型禁止），`p/m` 可以。

流式文本长这样：

```
["a", ["s", 12, "content", 0, "text"], "你"]
["a", ["s", 12, "content", 0, "text"], "好"]
```

一次 commit 的 ops 是原子的：要么都应用，要么都不用。

### 两种词汇不要混

- `Op`：内存/应用用，路径内联。
- `WireOp`：线上/磁盘用，多了路径驻留（`["#", id, path]`）和短形式（复用上一个 path）。

`watch()` 给的是 `Op`（已解码）。`applyImmutable` 接受 `Op`。如果你自己设计传输层，用 chord 的 `encode`/`decode`，不要手写。

## 4. 应用一帧

```ts
import { applyImmutable, isBase } from "@earendil-works/chord/delta";

function onFrame(state: State, frame: { value: State; ops: Op[] }): State {
  if (frame.ops.length === 0) return state;
  if (isBase(frame.ops)) return frame.value;   // 整帧
  return applyImmutable(state, frame.ops);
}
```

要点：

- `applyImmutable` 返回**新对象**，不修改入参。所以可以直接丢给 React。
- 值是不可变的，但**没有 frozen**。任何 `state.entries.push()` 都会污染别人看到的值。
- `applyImmutable` 会做路径安全校验，`__proto__` / `constructor` / `prototype` 段会抛 `UnsafePathError`。不要绕过它手写 `obj[key] = value`。

`isBase(ops)` 是精确判断不是启发式：flush 保证 `r` 只可能在索引 0。

## 5. 跨 IPC 的帧协议

主进程：

```ts
type ViewFrame = {
  convId: number;
  seq: number;              // 主进程自增，用于发现丢帧
  ops: Op[];                // 可能为 [["r", value]]
};
```

- 用 `webContents.send("view", frame)`，不要用 `invoke`（推送不该有请求语义）。
- 窗口 `destroyed` 后立即 `unsubscribe`；`webContents.send` 到已销毁窗口会抛错。
- 多窗口时每个窗口一个 watch，或者一个 watch 分发给多个窗口。**不要**每个窗口各开一个 Harness。
- 帧里不要放 `undefined`、函数、类实例、`BigInt`。`Op` 是纯 JSON。

渲染端首次加载的顺序：

```
1. invoke("conv.open", {convId})  → 返回 { view, seq }   // 整帧
2. 建立 onView 监听
3. 应用后续 ops
```

顺序不能反：先监听再拉快照会丢帧。正确做法是主进程在 `conv.open` 里**原子地**拿到 `watch.value` 与当前 `seq`，渲染端从该 seq 开始应用。

更简单的做法（V1 推荐）：`conv.open` 返回快照后，渲染端如果发现下一帧的 `seq !== 上次 seq + 1`，直接丢弃本地状态并重新 `conv.open`。这样不需要复杂的补帧逻辑。

## 6. 首次渲染：hydrate 与 update

`AttachedReplicatedState.subscribe` 的回调第三个参数是：

```ts
{ kind: "hydrate" | "update", sequence: number }
```

- `hydrate`：第一次投递，给完整值。
- `update`：后续。

`watch()` 没有这个参数，因为 `watch.value` 已经承担了快照职责。

在 React 里：

```ts
const view = useSyncExternalStore(
  store.subscribe,
  store.getSnapshot,
  store.getSnapshot,   // 没有 SSR，第三参可同第二参
);
```

`store.getSnapshot` 必须返回**稳定引用**，直到状态真的变化。每次调用都 `applyImmutable` 会破坏 `useSyncExternalStore` 的相等性判断，导致无限重渲染。

## 7. 只订阅一个文档

```ts
const watch = await session.watchDoc(AppKbDoc, ctx);
if (!watch) return;              // 文档不存在；它不会替你创建

watch.start(async (value, ops) => {
  // value: Readonly<AppKbState> | null
});
```

什么时候用 `watchDoc` 而不是 `watch`：

- 主进程里有一个「知识库面板」，只关心 `app.kb`。
- 后台任务只关心 `app.settings`。
- 你不想把整个 `ConversationView` 序列化过去。

什么时候不要用：需要 entries 与 live 状态一起渲染时，`view` 更省事。

## 8. 文档值 vs 视图值

`ConversationView.docs` 只包含**内置文档**（`pi.agent` / `pi.live` / `pi.inbox` / `pi.usage` / `pi.provider`），按 `kind` 索引，值是 `JsonObject`。

你自己的 `app.*` 文档**不会**出现在 `view.docs` 里。已核实：`dist/harness/view.js` 的 `MOUNTED` 只包含 `AgentDoc / LiveDoc / InboxDoc / ProviderDoc / UsageDoc` 五个 token。

因此设计上不要依赖「从 view 里拿 app 文档」：

- 需要一起推送的，先在 `shared-docs` 里写类型守卫，再单独 `watchDoc`。
- UI 状态与对话帧必须同步时，把它们写进内置的 `pi.live`（通过工具 `details`），而不是新开文档。

## 9. 性能与写放大

三条硬约束：

1. **不要每个 token 一次 commit。** 默认 100ms 一批（`settings.progress.partialIntervalMs`）。调小会增加 SQLite 写入与帧数，收益很小。
2. **不要每帧重算派生数据。** 消息分组、markdown 渲染、token 统计，用 memo 并以 `entry.id` 为 key。
3. **不要把一个巨大数组放进 Document。** 每次改动都会 diff 整个数组。用 family（`defineDocFamily`）按 key 拆分。

调试写放大：

```sql
-- 观察 WAL 增长
SELECT page_count * page_size FROM pragma_page_count(), pragma_page_size();
```

如果一次 2 秒的回答让 WAL 涨了几十 MB，检查是不是把 `details` 当日志用了。

## 10. 常见失败

| 现象 | 原因 | 修法 |
|---|---|---|
| 界面偶尔整段闪一下 | 没处理 `isBase` 整帧 | 用 `isBase(ops)` 直接覆盖 |
| 文本重复/错位 | 同一条消息被应用了两次 | 检查 `conv.open` 与 `onView` 的顺序；用 seq 去重 |
| 内存持续增长 | watch 没有 stop | 窗口关闭时 `watch.stop()`，移除监听 |
| `UnsafePathError` | 自己构造了含 `__proto__` 的路径 | 不要手写 ops；检查输入 |
| 组件不更新 | `getSnapshot` 每次返回新对象 | 只在帧到达时替换引用 |
| 高频重渲染 | 每帧都 `JSON.parse(JSON.stringify())` | 直接使用不可变值 |
| 帧丢失 | 回调里做了长时间同步计算 | 回调只做入队，重活放 `requestAnimationFrame` / worker |
| 关闭窗口报错 | `webContents.send` 到已销毁窗口 | 发送前判 `isDestroyed()` |
