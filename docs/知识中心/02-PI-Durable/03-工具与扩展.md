# 工具与扩展

> 工具不是「函数」，是**模型能看到的契约 + 可重放的副作用边界**。
> 扩展不是「插件目录」，是**一组名字的集合**，而名字会写进存储。

---

## 1. 三个通道，先分清

工具结果有三个去处，写错一个就会出问题：

| 通道 | 类型 | 谁看 | 典型内容 |
|---|---|---|---|
| `output` | `ToolResultMessage["content"]` | **模型** | 「读到了 42 行」「文件不存在」 |
| `structuredOutput` | `JsonValue` | **程序**（`executeTool` 调用方） | `{ files: [...] }` |
| `details` | `JsonValue` | **UI**（`pi.live` 的工具槽位） | 进度、diff、命令输出、UI DSL |

判断方法：**这段内容如果进了模型上下文，会让它更聪明还是更困惑？**

**工具有三类结果，分别对应给模型看、给代码看、给人看**

- 让模型判断下一步 → `output`
- 只有代码要用 → `structuredOutput`
- 只有人要看 → `details`
- 三者都需要 → 各写一份，不要偷懒共用。

反例：把 2000 行日志塞进 `output`。模型读不完，还烧 token。正确做法是 `details` 全量、`output` 摘要 + 指路（「完整输出见 UI」或「用 offset 继续读」）。

## 2. 定义一个工具

```ts
import { defineTool } from "@earendil-works/pi-durable";
import { Type } from "typebox";

export const ReadFileTool = defineTool({
  name: "read_file",
  description: "读取工作区内的文本文件。返回带行号的内容。",
  parameters: Type.Object({
    path: Type.String({ description: "相对于工作区根目录的路径" }),
    offset: Type.Optional(Type.Integer({ minimum: 1 })),
    limit: Type.Optional(Type.Integer({ minimum: 1, maximum: 2000 })),
  }),
  async execute({ path, offset = 1, limit = 2000 }, api, ctx) {
    const env = api.env;
    if (!env) return { output: "当前会话没有文件系统环境", isError: true };
    // ...读文件，拼行号...
    return {
      output: text,
      details: { path, totalLines, truncated },
    };
  },
});
```

字段速查（全部已核实，见 `dist/harness/types.d.ts`）：

| 字段 | 用途 | 什么时候用 |
|---|---|---|
| `name` | 模型看到的工具名，也是 `tools` 配置里的名字 | 稳定、小写下划线、动词开头 |
| `description` | 模型决定是否调用它的唯一依据 | 写「什么时候用 / 什么时候不用」，不是写实现 |
| `parameters` | TypeBox schema，执行前校验 | 所有参数都写 description 与约束 |
| `execute` | 主体 | 见第 3 节 |
| `replay` | 崩溃后能否重跑 | 只读工具 `"safe"`；有副作用保持默认 |
| `executionMode` | 并行/串行 | 写文件、跑命令用 `"sequential"` |
| `prepareArguments` | 校验前修复参数 | 模型总把数字写成字符串时 |
| `structuredOutputSchema` | 程序调用的返回结构 | 会被别的工具 `executeTool` 时 |
| `callers` | `["model","tools"]` | 不让模型直接调、只给工具用：`["tools"]` |
| `deferred` | 延迟加载 | 工具很多时，先只给模型看核心几个 |
| `outputLimits` | 截断策略 | 输出可能很大时 |

### description 的写法

好的 description 回答三个问题：

```
读取工作区内的文本文件。返回带行号的内容。
用于查看代码、配置、文档。
大文件请用 offset/limit 分段读，不要一次读超过 2000 行。
不要用它读二进制文件或工作区外的路径。
```

差的 description：`读取文件。`——模型只能靠猜。

## 3. `execute` 里该做什么

```ts
async execute(args, api, ctx) {
  // 1. 取环境（可能没有）
  // 2. 做校验之外的安全检查（路径越界、命令白名单）
  // 3. 长任务：输出进度
  api.output("正在读取…\n");
  api.details({ phase: "reading", bytes: 0 }, ctx);
  // 4. 中途写业务状态
  await api.commit(async (tx) => { /* ... */ }, ctx);
  // 5. 返回结果
}
```

### `api` 里真正常用的成员

| 成员 | 用途 | 注意 |
|---|---|---|
| `api.env` | 文件系统 / shell | 可能 `undefined`，必须判空 |
| `api.output(chunk)` | 流向模型 | 会被 `outputLimits` 截断 |
| `api.details(v, ctx)` | 流向 UI | 有节流；不要放每秒变化的大对象 |
| `api.commit(fn, ctx)` | 中途落盘 | 与最终结果不是同一个 commit |
| `api.executeTool(name, args, ctx, {key})` | 嵌套调用 | 结果不进转录；`key` 保证重放幂等 |
| `api.createTask(task, input, opts, ctx)` | 起子任务 | 归本次调用所有 |
| `api.diagnostic(d)` | 给模型和 UI 的提示 | 用于「参数被修正」这类信息 |
| `api.now()` | Harness 时钟 | 不要用 `Date.now()`，否则回放不一致 |

### 报错的两种语义

```ts
// 业务失败：模型应当看到
return { output: `路径越界: ${path}`, isError: true };

// 代码缺陷：交给框架
throw new Error("unreachable");
```

被中断（`ctx.abortSignal` 触发）不是错误，不要 `catch` 后吞掉；让框架处理。

### 副作用的幂等

```ts
await api.executeTool("deploy", args, ctx, { key: `deploy:${args.sha}` });
```

`key` 的作用：崩溃重放时，同 key 同参数的调用不会真的执行第二次（框架层面记录）。**但外部系统仍要自己幂等**——框架保证「知道发生过」，不保证「对外只发生一次」。

## 4. 权限与审批：用 Hook，不要用工具内部弹窗

工具拿不到 BrowserWindow，也不该拿。审批放在 Hook 里：

```ts
hook(ToolTask, {
  async beforeTool(call, api, ctx) {
    if (call.tool !== "bash") return;
    const cmd = String(call.arguments.command ?? "");
    const risk = classifyCommand(cmd);        // 纯函数，可单测
    if (risk === "deny") return { block: `禁止执行: ${cmd}` };
    if (risk === "ask") {
      const approved = await requestApproval(api, cmd, ctx); // 通过 Document/UI 等待
      if (!approved) return { block: "用户拒绝执行" };
    }
  },
});
```

`requestApproval` 的两种实现：

- **V1 简单版**：在 `app.approvals` Document 里写一条 pending，然后 `api.createTask(ApprovalTask, …)` 等用户点击。UI 通过 IPC 写入结果。
- **单进程测试版**：直接 `readline` 询问。只用于阶段 2–4 的 CLI。

为什么不用工具内部 `await dialog.showMessageBox()`：这会让工具依赖 Electron，无法在 Node 里测试，也无法在崩溃后恢复「等待审批」这个状态。

## 5. 扩展（Extension）

```ts
import { defineExtension, section, hook, wrapTool } from "@earendil-works/pi-durable";

export const CodingExtension = defineExtension({
  name: "coding",
  tools: [ReadFileTool, WriteFileTool, ListDirTool, BashTool],
  sections: [
    section("app.environment", async (ctx) => {
      return `工作区: ${process.cwd()}\n平台: ${process.platform}`;
    }),
  ],
  hooks: [
    hook(ToolTask, { beforeTool: auditBeforeTool }),
  ],
  wraps: [
    wrapTool(ReadFileTool, (tool) => ({
      ...tool,
      async execute(args, api, ctx) {
        api.diagnostic({ level: "info", message: `read ${args.path}` });
        return tool.execute!(args, api, ctx);
      },
    })),
  ],
});
```

### 装配与热替换

```ts
const registry = createRegistry();
registry.install(CodingExtension);
registry.install(UiExtension);

// 替换同名扩展：旧调用继续用旧代码，新调用用新代码
registry.install(UpdatedCodingExtension);
```

语义（已核实）：

- `install` 是「按 `name` 覆盖式发布」，不是报错。
- 运行中的调用持有启动时解析到的注册表快照；替换不影响它。
- 卸载（`uninstall(name)`）只影响后续解析。

### 名字的兼容性

以下名字会写进存储或模型上下文，**上线后不要改**：

- Extension `name`
- Tool `name`
- Document `kind`
- Entry `kind`
- Task `name`

改名的代价：旧会话里的配置指向不存在的名字，模型看到的工具集变了，`pi.system` 会记录一次「工具集变化」——历史行为无法复现。

## 6. 提示词段落（section）

```ts
section("kb.rules", async (ctx) => `
只有当问题涉及知识库时才使用 kb_search。
引用时必须给出 wiki 页面路径。
`)
```

- 返回值会以 `<kb.rules>…</kb.rules>` 的形式进入系统提示词（可用 `{tag}` 改）。
- 每次请求前渲染，**必须快**。不要在里面读大文件或调网络。
- 段落内容变化会写一条 `pi.system` entry，记录「模型看到的提示词变了」。
- 需要动态数据的，先落到 Document，再在 section 里同步读。

## 7. Task 与 Tool 的分工

| | Tool | Task |
|---|---|---|
| 触发者 | 模型 / 其它工具 | IPC、Hook、其它任务 |
| 时长 | 秒级 | 分钟级，可跨重启 |
| 进度 | `api.output` / `details` | `phase` + 检查点 |
| 崩溃恢复 | 按 `replay` 重跑或中断 | 从最后一个检查点继续 |
| 结果 | 给模型 | 给业务 / 给 UI |
| 能否调用工具 | 能（`api.executeTool`） | **不能**（`TaskRuntime` 无此方法） |

经验法则：**模型需要看到结果的，做成 Tool；用户需要等它完成的，做成 Task。**

知识库 ingest 属于后者：它要读文件、调模型、写多个页面，中途崩溃很常见，必须能续跑。

## 8. 本项目的工具清单（规划，不是 SDK 内容）

| 工具 | 来源 | `replay` | `executionMode` | 备注 |
|---|---|---|---|---|
| `read_file` | coding | safe | 默认 | 带行号、分段 |
| `list_dir` | coding | safe | 默认 | 限制深度 |
| `write_file` | coding | unsafe | sequential | 写入前记录旧内容到 details |
| `bash` | coding | unsafe | sequential | Hook 审批；输出截断 |
| `kb_search` | kb | safe | 默认 | 读 wiki 索引 |
| `kb_read` | kb | safe | 默认 | 只读 wiki 目录 |
| `kb_ingest` | kb | unsafe | sequential | 实际是创建 Task，工具只负责入队 |
| `render_ui` | ui | safe | 默认 | 产出 DSL 到 `details.ui` |
| `tool_create` | toolsmith | unsafe | sequential | 写源码 + 校验 + 安装 |

`kb_ingest` 作为 Tool 存在，是为了让模型能发起收录；它的 `execute` 只做一件事：`api.createTask(KbIngestTask, …)` 然后立即返回 taskId。

## 9. 测试一个工具

工具不依赖 Electron，所以可以直接在 Node 里测：

```ts
// 伪代码：用 MemoryStorage 起一个最小 Harness，注册工具，用 executeTool 调它
const harness = await Harness.open(new MemoryStorage(), { models, registry }, ctx);
const conv = await harness.root(ctx);
const result = await SomeTool.execute(args, fakeApi, ctx);
```

对 `execute` 的测试分三层：

1. **纯逻辑**：路径校验、参数归一化，抽成独立函数单测。
2. **执行**：用临时目录 + fake `ExecutionEnv`，断言输出与副作用。
3. **契约**：`executeTool` 走一遍，断言 `structuredOutput` 与 `isError`。

不要为了测工具而启动 Electron。启动了就说明工具里混进了 UI 依赖。

## 10. 常见失败

| 现象 | 原因 | 修法 |
|---|---|---|
| 模型从不调用某工具 | description 没写「何时用」 | 补使用场景与反例 |
| 模型传错参数类型 | schema 太松 | 收紧 TypeBox，必要时 `prepareArguments` |
| 崩溃后工具重复扣费 | `replay: "safe"` + 无幂等键 | 改 unsafe，或外部幂等 |
| UI 卡顿 | `details` 每帧都变大对象 | 只放增量/摘要，全量放最后 |
| 工具在测试里跑不起来 | 依赖了 `app` / `BrowserWindow` | 依赖倒置，通过 `api.env` 或 Document |
| 改了工具名后旧会话行为异常 | 名字是契约 | 保留旧名做别名，或接受不兼容并升 major |
| 同轮多工具互相覆盖文件 | 并行执行 | 标 `executionMode: "sequential"` |
