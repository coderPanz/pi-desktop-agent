# 核心心智模型

> 这一篇不列 API。它只解决一件事：**当 Harness 做出一个「奇怪」的行为时，你能用哪条规则解释它。**

---

## 1. 一张图

```
Harness ── 在 pi 中的定义就是 一份存储 加 和基于存储的会话调度机制
│
├─ Session ── 存储写入的唯一入口，在 pi 中叫 commit；存储读取的唯一入口（snapshot/scan）
│
├─ Conversation ── 转录 + Agent 配置 + Documents
│  ├─ Entry（不可变，只追加）
│  ├─ Document（可变，带版本）
│  └─ Task（可恢复状态机）
│
├─ Registry ── 已安装的 Extension、Tool、Task 定义
│
└─ Models ── pi-ai 的模型目录与凭证
```

`Harness extends Session`。所以 `harness.commit(...)`、`harness.snapshot(...)` 都能直接用。

---

## 2. 七条规则

### 规则 1：提交是唯一的可见边界
在 pi-durable 中，一切可见的（llm 的回答、工具的调用结果、用户输入）都是从 存储 中获取的。

### 规则 2：Conversation 不是聊天窗口，是一个可配置的 Agent

`AgentState` 里存的是名字不是对象：

```ts
{
  model?: { provider, modelId },
  thinkingLevel?: "off" | ... | "max",
  extensions?: string[] | { add?, remove? },
  tools?: string[] | { remove },
  modelTools?: string[] | { add?, remove? },
  instructions?: string,
  cwd?: string
}
```

所以同一个 Harness 可以同时跑： 多个 agent 。它们只是配置不同的 Conversation。这就是 subagent 的原理，在 pi 中。

改配置用 `configure(change, ctx)`，它自己开一个 commit。也可以在 `createConversation({agent})` 时一次给定。

### 规则 3：Task 是状态机，不是线程

Task 有 `phase`、检查点、终态。它可能：

- `pending`：等待被调度
- `running`：某个进程正在跑
- `waiting`：等它拥有的其它任务
- `sleeping`：等到某个时刻（1.4.0 新增状态）
- `completing`：结果已产生，等子任务收尾
- `terminal`：结束

调度器只在**有进程跑 `resume()`** 时推进任务。只读的 `snapshot()` 不会唤醒任何东西。

**任务的所有权是一棵树**：

- 父任务结束前会等自己创建的任务。
- 取消先子后父。
- `background: true` 的任务不阻塞会话进入 idle，也不被普通 abort 带走。

子代理不是特殊物种：一个工具创建一条由自己拥有的 Conversation，向它提交问题并等待，这就是子代理。

### 规则 4：忙碌是一等状态，不是错误

忙碌时收到输入，有三种策略：

| `whenBusy` | 行为 |
|---|---|
| 省略 / `"followUp"`（默认） | 入 `pi.inbox`，当前 run 结束后作为下一轮 |
| `"steer"` | 在当前工具轮结束后插入，影响仍在进行的 run |
| `"reject"` | 直接抛 `ConversationBusy`，什么都不写 |

还有第四种提交：`type: "write"`。往这个会话的转录里追加一条记录，然后结束 —— 不创建 run、不调模型、不产生 token 消耗。 
- Entry = Conversation 转录里的一条不可变、只追加的记录
- 转录（transcript）= 这条 Conversation 的完整事件日志，即所有 entry 按顺序组成的那个只追加序列。它是"物理"的：写进去就永久存在、不可修改、不能删除。
- Session： 提供 commit / snapshot / watchDoc / closed，是存储读写唯一入口，进程级。
- Conversation：是无状态句柄，按 id 比较（02-API参考.md 2 节开头），代表存储里的 转录 + Agent 配置 + Documents + Tasks 那一坨，数据级。
一句话总结： Session 是「存储的门」，Conversation 是「存储里的一个东西」。 

- 什么是任务：Definition: Task = 一个可恢复的状态机，代表"要持续做完的一件事"。它是 durable 的核心：崩溃后从检查点继续，而不是从头。
- 三种东西的定位：Entry = 发生过什么（历史-只读）；Document = 当前状态（可变）；Task = 正在做且做完前可能要跨越进程重启的一段过程（状态机）。
- 内置任务：GenerationTask（模型轮）、ToolTask（工具调用）、CompactionTask（压缩）—— 都是任务，所以都能被 hook。这点很重要：pi-durable 里"模型的每一轮"本身就是一个任务，不是一段代码。

 Task = 一个可恢复的状态机，代表「要持续做完的一件事」。 它不像函数那样从头跑到尾，而是跑一段 → 存检查点 → 崩了从检查点接着跑。

### 规则 5：上下文会压缩，但历史不会删除

压缩把较早内容总结成摘要，作为后续请求的起点。原始 entry 仍在存储里。

- 手动：`conversation.compact(instructions, ctx)`
- 自动：按 token 阈值（`settings.compaction`）
- 后台：阈值以下先开始生成，不阻塞

**推论：不要把关键事实只留在聊天历史里。** 压缩后模型可能看不到细节。要保留的事实写进 Document，再用工具或提示词段落读回来。

### 规则 6：重放策略只保护「调用意图」，不保护副作用

工具在执行前会持久化调用意图。崩溃后：

| `replay` | 行为 |
|---|---|
| `"safe"` | 自动重跑（检索、读文件、纯计算） |
| `"unsafe"`（默认） | 不重跑，模型看到「调用被中断」 |

即使标了 `safe`，扣款、部署、发通知这类外部动作也必须带幂等键。框架保证的是「知道发生过」，不是「只发生一次」。

### 规则 7：错误按范围分级

| 错误 | 范围 | 结果 |
|---|---|---|
| Storage 出错 | 整个 Session | `SessionFailed`，Harness 关闭，必须重开 |
| 请求非法 | 当前调用 | 抛出，其它不受影响 |
| 工具抛异常 | 该工具调用 | 转成模型可见的错误结果 |
| 任务阶段抛异常 | 该任务 | 任务失败，其它继续 |
| Hook 抛异常 | 该 Hook | 多数情况报告后跳过 |

所以：**永远不要 catch 掉 Storage 错误继续用**。Session 已经不可信了。

## 3. 一次 run 里到底发生了什么

```
submit(input)
  → 写 user entry + submission（一个 commit）
  → 调度 generation task
      phase: prepare
        - 解析 agent 配置
        - 若提示词/工具集变了，写一条 pi.system
        - 组装上下文（可能触发压缩）
      phase: request
        - 调 pi-ai
        - 每 ~100ms 提交部分回答
      phase: tools（如果有 tool_calls）
        - 每个 call 一个 tool task
        - 工具意图先落盘 → 执行 → 结果落盘
      phase: finish
        - 提交最终 assistant entry
        - settle submission
```

几个容易误解的点：

- **`submit()` 返回的是收件凭据，不是回答。** 要回答用 `submission.wait(ctx)`，但 UI 不该等。
- **一个 run 可能有多次模型请求。** 每次工具轮之后都会再请求一次。
- **`pi.system` 不是系统提示词本身**，而是「提示词/工具集发生变化」的标记，用来在重放/分叉时还原当时模型看到的东西。
- **部分回答也是提交。** 所以中断后你能看到已生成的部分。

## 4. Document 与 Entry 的分工

| 问题 | 答案在哪 |
|---|---|
| 用户说过什么？ | Entry（`pi.user`） |
| 模型答了什么？ | Entry（`pi.assistant`） |
| 现在有哪些待办？ | Document（你的 `app.todo`） |
| 当前工作目录？ | Document（`app.workspace`）或 AgentState.cwd |
| 这个工具调用成功了吗？ | Entry（`pi.tool-result`）+ `pi.live` 槽位 |
| 这个任务进行到哪一步？ | Task 的检查点 |
| 这次回答花了多少 token？ | `pi.usage` Document |

判断方法：**「如果进程现在崩溃，重启后还需要知道吗？」** 需要，就不是内存状态；「它是历史事实还是当前状态？」历史进 Entry，当前状态进 Document。

## 5. Extension / Tool / Task 的关系

```
Extension（命名包）
├─ tools[]        模型或其它工具可调用
├─ sections[]     每次请求前渲染的系统提示词片段
├─ hooks[]        在任务/工具/压缩前后插入逻辑
├─ wraps[]        包装已有工具或提示词段落
└─ tasks[]        自定义持久化任务
```

- 一个 Registry 可以装多个 Extension。
- 同名 Extension 再 install 会**原地替换**：运行中的调用继续用旧代码，后续调用用新代码。
- 场景持久化的是**名字**，不是对象。所以名字是兼容性契约。

工具的三条通道、`callers`、`deferred`、`executionMode` 见 [03-工具与扩展.md](03-工具与扩展.md)。

## 6. 上下文（Context）到底是什么

每个异步调用都带一个 `Context`（来自 chord）。它有两个作用：

1. **取消等待**：`withCancel(ctx)` 得到 `{context, cancel}`。cancel 只让等待者 reject，不会杀后台任务。
2. **传递遥测父节点**。

`BACKGROUND_CONTEXT` 是一个**不会主动取消的上下文**，适合「必须完成」的后台工作。

常见错误：以为 cancel 了 `wait()` 就停了任务。没有。要停任务用 `conversation.abort(ctx)` 或 `harness.abortTask(id, ctx)`。

## 7. 与 pi-coding-agent 的关系（避免混淆）

你可能见过 `@earendil-works/pi-coding-agent` 的 `createAgentSession`。那是**已组装好的编码 Agent**；本项目用的是更底层的 `pi-durable`：

| | pi-coding-agent | pi-durable（本项目） |
|---|---|---|
| 定位 | 开箱即用的编码 Agent | 可恢复运行时底座 |
| 会话持久化 | JSONL 会话树 | 任意 Storage，含 SQLite |
| 任务 | Agent 内部循环 | 显式、可恢复的 Task |
| 业务状态 | 无 | Document |
| UI 集成 | 事件流 | `watch` + 增量 ops |

两者不冲突，但**不要混用两套会话/持久化模型**。本项目只依赖 pi-durable + pi-ai + chord。
