# 模块交互

> 这一篇是时序图合集。每个场景都回答两个问题：**谁调用谁**，以及**哪一步必须先落盘**。

---

## 1. 模块清单

| 模块 | 文件（规划） | 依赖 | 被谁调用 |
|---|---|---|---|
| HarnessHost | `main/harness/host.ts` | pi-durable, pi-ai, chord | `main/index.ts` |
| Registry 装配 | `main/harness/registry.ts` | extensions/* | HarnessHost |
| IpcRouter | `main/ipc/router.ts` | HarnessHost | preload 暴露的 invoke |
| WatchHub | `main/ipc/watch-hub.ts` | HarnessHost, BrowserWindow | IpcRouter |
| Lifecycle | `main/lifecycle.ts` | HarnessHost, app | Electron 事件 |
| replica store | `renderer/store/conv.ts` | chord/delta | React 组件 |
| ChatView | `renderer/views/chat` | replica store, preload API | 用户 |
| ToolRenderer | `renderer/views/chat/tool-card` | `pi.live` | ChatView |
| UiRenderer | `renderer/ui/tokui.tsx` | TokUI | ChatView |

**依赖方向只能向下**：renderer → preload 契约 → main → pi-durable。反向依赖（工具里 import renderer）一律禁止。

## 2. 场景 A：发送一条消息

```
User
 │ Enter
 ▼
ChatView ──▶ replica 乐观态？（不！）
 │            渲染进程不预先插入消息，避免与提交顺序冲突
 │
 ├─ ipc.invoke("conv.submit", {convId, text, requestId})
 ▼
IpcRouter
 ├─ 参数校验（长度、requestId 格式）
 ├─ conversation.submit({type:"input", content:text, requestId}, ctx)
 │     └─ 忙碌时自动入 pi.inbox（默认 followUp）
 │
 ├─ 返回 {submissionId}
 ▼
渲染进程：只记录 submissionId，等 watch 帧
```

设计理由：

- **不做乐观插入。** 提交是异步的，且可能排队。乐观插入会让「用户看到的消息」与「实际顺序」不一致。等 watch 帧最多晚 100ms。
- `requestId` 用 ULID 或 crypto.randomUUID。重连/重试时同一个 requestId 会命中同一条 submission，不会重复执行。

失败分支：

| 情况 | 表现 | 处理 |
|---|---|---|
| `whenBusy: "reject"` 且忙 | `ConversationBusy` | 提示「正在运行」并转为排队或禁用发送 |
| 存储失败 | `SessionFailed` | 触发 Lifecycle 重建 |
| 参数非法 | 路由层错误 | 直接提示，不进入 Harness |

## 3. 场景 B：流式回答如何出现

```
Harness 内部 generation task
 │ 每 ~100ms 提交一次 part
 ▼
commit 发布 ──▶ conversation.watch 的 listener(value, ops)
 │
 ▼
WatchHub
 ├─ 检查窗口是否还活着
 ├─ 合并同一 tick 的多个 conv（可选）
 ├─ webContents.send("view", {convId, ops})
 ▼
preload：contextBridge 暴露 onView(cb)
 ▼
replica store
 ├─ state = applyImmutable(state, ops)
 ├─ 若 ops 以替换开头（积压折叠）→ 直接采用 value
 └─ emitChange()
 ▼
React useSyncExternalStore → 重渲染文本节点
```

**首字延迟**由三件事决定：模型首 token、`progress.partialIntervalMs`（默认 100ms）、IPC 调度。不要为了「更顺滑」把间隔改成 0，那会把每次 token 变成一次数据库写。

**帧的三种形态**：

| 形态 | 判定 | 渲染端动作 |
|---|---|---|
| 空 ops | `ops.length === 0` | 无变化，跳过 |
| 增量 | 不含根替换 | `applyImmutable` |
| 整帧 | `isBase(ops)` 为 true，或积压折叠 | 直接用 `value` 覆盖 |

`isBase` 来自 `@earendil-works/chord/delta`。

## 4. 场景 C：一次工具调用

```
model 返回 tool_calls
 │
 ▼
generation task 为每个 call 创建 pi.tool 任务
 │
 ├─ 1. 记录调用意图（commit）
 │       └─ 崩溃后据此判断 replay
 ├─ 2. beforeTool hooks（可 block / 改参数）
 ├─ 3. 参数校验（TypeBox schema）
 ├─ 4. execute(args, api, ctx)
 │       ├─ api.output(chunk)   → 给模型
 │       ├─ api.details(v)     → 给 UI（pi.live.tools）
 │       ├─ api.commit(...)    → 中途写业务状态
 │       └─ api.executeTool()  → 嵌套调用
 ├─ 5. afterTool hooks（可改写结果）
 └─ 6. 提交 tool-result entry + pi.live 更新
 │
 ▼
模型下一轮看到工具结果
```

**为什么意图要先落盘**：如果进程在「已发起部署、还没写结果」时崩溃，重启后框架知道这次调用存在但未完成。`replay: "safe"` 的工具会重跑；未声明的不会，模型会看到「调用被中断」。业务侧仍应使用幂等键，框架只保证意图不丢。

**三通道不要混用**：

| 通道 | 去处 | 误用后果 |
|---|---|---|
| `output` | 模型上下文 | 把 UI 数据塞进去 → 浪费 token、干扰推理 |
| `structuredOutput` | 程序（`executeTool` 调用方） | 没有 schema 时程序只能拿到 output 文本 |
| `details` | UI（`pi.live`） | 把大段调试信息塞进去 → 每 100ms 提交一次，写放大 |

## 5. 场景 D：中断

```
User 点「停止」
 │
 ├─ ipc.invoke("conv.abort", {convId})
 ▼
conversation.abort(ctx)
 ├─ 撤回排队中的输入
 ├─ 标记当前 run 的普通任务
 ├─ 等待它们进入 terminal
 └─ resolve（此时会话已 idle）
 ▼
UI：按钮恢复可用；已生成的部分回答保留在转录里
```

容易误解的点：

- 取消 `wait()` **不等于**终止任务。`Context` 的 cancel 只影响等待者。
- `abort({background:true})` 才会连后台任务一起处理。
- 中断后已产生的部分回答不会消失；它作为一条 assistant entry 留在历史里。

## 6. 场景 E：崩溃恢复

```
kill -9
 │
 ▼
重启
 ├─ 单实例锁
 ├─ Storage 重新打开（SQLite WAL 自动恢复到最后一个完整事务）
 ├─ Harness.open(...)
 ├─ harness.resume()          ← 必需，否则任务不会继续
 │    ├─ running → pending 的任务重新调度
 │    ├─ replay:"safe" 的工具重跑
 │    ├─ unsafe 的工具得到 interrupted 结果
 │    ├─ 排队输入仍在 pi.inbox
 │    └─ sleeping 任务按 Harness 时钟恢复
 ├─ root conversation
 └─ 窗口加载后重新 watch（拿当前整帧，不重放历史 ops）
```

**恢复不是「重放所有操作」**，而是「从最后提交的状态继续」。所以不要在 commit 之外维护任何「只存在内存里的事实」。

`settings.restartLimit` 默认 5：同一任务连续被崩溃打断 5 次会被 park 为 blocked，避免无限崩溃循环。`harness.retryTask(id)` 可以手动再跑。

## 7. 场景 F：知识库 ingest

```
用户拖入文件 / 点「收录」
 │
 ├─ ipc.invoke("kb.ingest", {path})
 ▼
kb extension 的工具 ingest 被调用？（不，这一步由谁触发？）
```

V1 的选择：**ingest 是一个 Task，不是 Tool**。

```
IpcRouter
 └─ tx.createTask(KbIngestTask, {sourcePath}, {ownership:{kind:"conversation"}})
      │
      ├─ phase "read"     读 raw 文件，commit 摘要草稿
      ├─ phase "summarize" 调模型（可用嵌套工具或直接 models）
      ├─ phase "write"     写 wiki 页面
      ├─ phase "index"     更新 index.md / log.md
      └─ phase "done"      terminal
```

理由：ingest 是分钟级、多阶段、可能中断的工作。用 Task 才能在中途崩溃后续跑；用 Tool 只能整体重来。

任务状态通过 `harness.watchTaskGraph()` 或 `pi.live` 展示；具体在阶段 7 落地。

## 8. 场景 G：智能 UI 点击

```
模型调用 render_ui(dsl)
 │
 ├─ 工具 details.ui = { dsl, handlers:["choose","confirm"] }
 ├─ afterTool hook 把 output 改写为 "[UI 已渲染]"
 ▼
watch → pi.live.tools[i].details → UiRenderer
 ├─ startStream() + feed(增量后缀)
 └─ registerHandler("choose", …)
 ▼
用户点击
 │
 ├─ ipc.invoke("ui.action", {convId, uiId, handler, payload})
 ▼
IpcRouter
 └─ conversation.submit({
      type:"input",
      content: "[UI 交互] choose: …",
      entry: {kind:"app.ui_action", data:{uiId, handler, payload}},
      requestId: `ui:${uiId}:${actionId}`,
      whenBusy: "followUp"
    })
```

幂等是关键：用户双击、网络重试、渲染进程重放，都必须落到同一条 submission。`actionId` 是**渲染进程在每次点击时生成的 UUID**（`crypto.randomUUID()`），同一次点击的重试复用它。不要用自增序号或时间戳：前者在渲染进程重启或「提交成功、文档未写」后会撞号，后者不能区分重试与新点击。

安全边界：

- DSL 只能使用白名单组件和 5 个固定 handler。
- handler 名字是固定的，点击结果只是数据，不能变成可执行代码。
- 外部链接走白名单，不在应用内直接打开。

## 9. 模块之间不要做的事

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 渲染进程自己拼 `Ops` 发给主进程 | 渲染进程不是写者，状态会分叉 | 只发命令，状态由主进程 commit 产生 |
| 工具里直接 `webContents.send` | 扩展应可脱离 Electron 测试 | 通过 `details` / Document 暴露，由 WatchHub 推送 |
| 在 `commit` 回调里 `await conversation.submit` | 会排在当前事务所在的行上，可能永不返回 | 只通过 `tx` 读写 |
| 每个窗口各开一个 Harness | 破坏单写者 | 一个 HarnessHost，多窗口共享 |
| 用 `watchEvents` 做 UI 同步 | 传输开销大、信息有损 | 用 `watch` + `applyImmutable` |

最后一条对应的 `commit` 死锁细节（已核实）：`commit` 回调内只能通过 `tx` 读取；调用 `snapshot()`、`watchDoc()`、`getTask()` 等 Session 读操作会排在当前持有的行后面，**永远不会返回**。
