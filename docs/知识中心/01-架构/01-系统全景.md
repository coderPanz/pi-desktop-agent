# 系统全景

> 读这一篇只需要带一个问题：**一次「用户按下回车」到「屏幕上出现回答」，中间经过了哪些进程、哪些对象、哪几次落盘？**

---

## 1. 一句话架构

**Electron 主进程持有一个 Harness，独占一个 SQLite 文件；渲染进程只持有它的只读副本，通过 IPC 请求写操作。**

```
┌─────────────────────────────────────────────────────────────────────┐
│ Electron Renderer（React 19 + Tailwind + TokUI）                      │
│                                                                     │
│  chat view / kb view / tools view                                   │
│         │  只读：ConversationView 副本                                 │
│         │  写入：ipc.invoke("conv.submit", …)                         │
│         ▼                                                            │
│  replica store  ◀── ipc.on("view", {ops}) ───────────────────┐        │
└──────────────────────────────────────────────────────────────┼───────┘
                    ▲ invoke（请求/响应）                        │ 单向推送
                    │                                            │
┌───────────────────┴──────────────────────────────────────────┴───────┐
│ Electron Main（Node 22，ESM）                                          │
│                                                                     │
│  HarnessHost                                                        │
│   ├─ Harness（唯一写者）                                             │
│   │   ├─ Conversation(root)  ← submit / watch / viewState           │
│   │   ├─ Registry            ← extensions / tools / tasks           │
│   │   └─ Models              ← pi-ai provider 与凭证                  │
│   ├─ IpcRouter               ← 把 invoke 翻译成 Harness 调用          │
│   ├─ WatchHub                ← watch 帧 → webContents.send           │
│   └─ Lifecycle               ← 启动恢复 / 关闭 / 失败重建              │
│                                                                     │
│  Storage: node:sqlite 单文件（userData/session.sqlite，WAL）           │
│  Env: NodeExecutionEnv(cwd = 工作区)                                  │
└─────────────────────────────────────────────────────────────────────┘
```

三个不可动摇的约束：

1. **单写者**：同一份 Storage 同一时刻只能有一个 Harness 打开。框架不提供跨进程锁。
2. **先提交后展示**：渲染进程收到的任何一帧都来自已落盘的 commit。
3. **名字是契约**：Extension / Tool / Document kind / Entry kind 写进存储，改名会破坏旧会话。

---

## 2. 分层与职责

| 层 | 位置（规划） | 职责 | 不该做的事 |
|---|---|---|---|
| 渲染 UI | `apps/desktop/renderer` | 展示、输入、局部交互状态 | 不直接读文件、不持有 Harness、不在本地改对话副本 |
| IPC 契约 | `packages/shared-types` | 类型化的通道定义 | 不写业务逻辑 |
| HarnessHost | `apps/desktop/main/harness-host.ts` | 打开/关闭 Harness、持有 root conversation、恢复 | 不拼 UI 文案 |
| Document 定义 | `packages/shared-docs` | `defineDoc`、类型、初始值 | 不在渲染进程注册 |
| 扩展 | `packages/extensions/*` | 工具、提示词段落、Hook、任务 | 不直接操作 Electron API |
| 存储 | `pi-durable/storage/sqlite` | 原子提交、ID、扫描 | 不写业务校验 |

**为什么 Harness 必须在主进程：**

- Storage 是单写者的，渲染进程一旦也开一个，就会出现两个写入者。
- 工具执行需要真实文件系统和 shell，渲染进程（沙箱）没有。
- 主进程生命周期比窗口长：窗口关闭后后台任务仍应继续。这是「durable」的意义。

## 3. 五个核心对象

```
Harness            一个存储上的运行总控；也是 Session（提交/读取/订阅的底座）
└─ Conversation    一条会话：转录 + Agent 配置 + 一堆 Document
   ├─ Entry        不可变记录（用户消息、模型回复、工具结果、压缩摘要…）
   ├─ Document     与会话共存的结构化 JSON（pi.live、pi.inbox、app.workspace…）
   └─ Task         可恢复的状态机（生成回复、执行工具、ingest…）
```

| 对象 | 一句话 | 生命周期 |
|---|---|---|
| Harness | 打开存储后的一切入口 | 应用启动到退出 |
| Conversation | 一条可持续的对话 | 创建后长期存在，可 fork |
| Entry | 只追加、不可改的历史 | 永久 |
| Document | 可修改的业务状态，随 commit 一起原子落盘 | 与会话/任务同寿 |
| Task | 带检查点的工作单元 | 创建→运行→terminal |
| Extension | 工具 + 提示词 + Hook + Task 的命名包 | 可热替换 |

## 4. 一次提问的完整链路

```
渲染进程                    主进程                                  Storage
   │                          │                                       │
   │ invoke conv.submit       │                                       │
   ├─────────────────────────▶│ conversation.submit(draft)            │
   │                          ├──────────────────────────────────────▶│ 写入 user entry
   │                          │◀──────────────────────────────────────┤ + submission 记录
   │◀──── {submissionId} ─────┤                                       │
   │                          │ 调度 generation task                  │
   │                          ├──────────────────────────────────────▶│ 任务创建
   │                          │ 请求模型（pi-ai）                       │
   │                          │ 每 ~100ms 提交部分回答                  │
   │◀── view(ops: 增量) ───────┤◀──────────────────────────────────────┤ partial assistant
   │  apply(副本, ops)         │                                       │
   │                          │ 模型要求调用工具 → tool task            │
   │                          ├──────────────────────────────────────▶│ intent 先落盘
   │                          │ 执行工具（NodeExecutionEnv）            │
   │                          │ 工具结果提交                            │
   │◀── view(ops: 工具卡) ─────┤                                       │
   │                          │ 再次请求模型 → 最终回答                  │
   │                          │ 提交最终 assistant entry                │
   │                          │ settle submission                     │
   │◀── view(ops: 完成) ───────┤                                       │
```

关键点：

- `submit()` 只负责**可靠收件**，立即返回 `Submission`。它不等回答。
- 想等回答用 `submission.wait(ctx)`，但 UI **不应该**等——UI 靠订阅。
- 流式文本不是每个 token 一次 commit，而是默认每 100ms 一次（`settings.progress`）。崩溃最多丢这一窗口的「显示进度」，不丢已提交状态。
- 工具调用的**意图**先落盘，再执行。这是崩溃后能判断「该重试还是该报中断」的前提。

## 5. 状态如何到达界面

有三条路，作用不同：

| API | 拿到什么 | 适合 |
|---|---|---|
| `conversation.viewState(ctx)` | `AttachedReplicatedState<ConversationView>`，可 `subscribe` | 主进程内部、调试面板 |
| `conversation.watch(ctx)` | 每帧 `(value, ops)`，最多积压 100 帧 | **跨 IPC 同步给渲染进程** |
| `watchEvents()` | coding-agent 风格事件流 | 接入已有的外部消费者，开销更大 |

`ConversationView` 的形状（已核实）：

```ts
{
  conversation: ConversationRecord;       // id / parent / owner
  entries: readonly EntryRecord[];        // 当前活跃转录
  docs: Record<string, JsonObject>;       // 内置文档，按 kind 索引
}
```

内置文档的 kind：`pi.agent`、`pi.live`、`pi.inbox`、`pi.usage`、`pi.provider`。

渲染进程**不要**去猜 `docs` 里有什么类型；它拿到的是 `JsonObject`。要么在 `shared-docs` 里定义校验函数，要么只读你真正需要的字段。

详见 [02-PI-Durable/04-状态订阅与增量同步.md](../02-PI-Durable/04-状态订阅与增量同步.md)。

## 6. 进程边界上的数据

| 数据 | 方向 | 形态 | 注意 |
|---|---|---|---|
| 命令 | renderer → main | `ipcRenderer.invoke(channel, args)` | 参数必须可结构化克隆；不要传函数/类实例 |
| watch 帧 | main → renderer | `{convId, ops}` | `ops` 是 chord 的 `Op` 元组数组，可序列化 |
| 整帧重置 | main → renderer | 积压超限后的单帧 | 不要假设每帧都是小增量 |
| 错误 | main → renderer | `{code, message}` | 不要把原始异常对象直接扔过去 |
| 文件内容 | renderer → main（请求） | 字符串 | KB 读写一律走主进程 |

**ID 是数字品牌类型**（`ConversationId`、`EntryId`、`TaskId` 都是 `number & {...}`）。跨 IPC 时按 number 传，渲染进程用 `String(id)` 做 key。

## 7. 工作区布局

V1 建议的磁盘结构：

```
<userData>/                      # Electron app.getPath("userData")
├─ session.sqlite                # Harness 存储（WAL）
├─ session.sqlite-wal
├─ workspace/                    # NodeExecutionEnv 的 cwd
│  ├─ raw/                       # 知识库原始资料（只读）
│  └─ wiki/                      # LLM 维护的 wiki
│     ├─ index.md
│     └─ log.md
└─ tools/                        # 用户工具 TS 源码
   └─ <slug>/tool.ts
```

**为什么 raw 与 wiki 分开：** raw 是事实来源，永不修改；wiki 由 Agent 维护，可以随时重建。这是 LLM Wiki 模式的核心约定，也是知识库工具的安全边界。

## 8. 启动与关闭

启动顺序（细节见 [03-Electron/01-主进程与HarnessHost.md](../03-Electron/01-主进程与HarnessHost.md)）：

```
app.whenReady
 → 单实例锁
 → 打开 Storage（node:sqlite）
 → createModels + 注册 provider
 → createRegistry + install 内置扩展
 → Harness.open(storage, options, context)
 → harness.resume()            // 继续未完成任务
 → 取 root conversation
 → 创建窗口，等 did-finish-load 后再开始推送
```

关闭顺序：

```
window close → 停止接受新命令 → watch.stop()
 → harness.close(context)      // 结算已接收的提交
 → 退出
```

**不要**在 `before-quit` 里 fire-and-forget 地 `close()` 然后立刻 `app.exit()`，否则提交可能没结算。

## 9. 失败模型

| 失败 | 影响范围 | 处理 |
|---|---|---|
| Storage 读写出错 | **整个 Harness 关闭**（`SessionFailed`） | 监听 `harness.closed`，重新 open，重建 root 与 watch |
| 请求参数错误 | 当前调用 | 返回错误给渲染进程 |
| 工具抛异常 | 该次工具调用 | 转成模型可见的错误结果，会话继续 |
| 任务阶段异常 | 该任务 | 任务失败，其它任务继续 |
| 渲染进程崩溃 | 只影响窗口 | 主进程与任务不受影响，重开窗口重新 watch |

最后一条是架构红利：**把 Harness 放主进程，UI 崩了不丢工作。**
