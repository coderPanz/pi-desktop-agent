# V1 开发路线

> 目标：从零手写出一个可用的桌面 Agent。每个阶段都能独立跑通、独立验收，验收不过不进下一阶段。
>
> 基线版本：[README.md](README.md) 的版本表。所有 API 以 `pi-durable@1.4.0` 的类型定义为准。

---

## 1. 路线设计原则

1. **先 Node，后 Electron。** 前 5 个阶段全部在普通 Node 脚本里完成。Harness 的行为与 UI 无关，先把运行时吃透，再套壳。
2. **每阶段只引入一个新概念。** 阶段 0 只学 Harness 生命周期；阶段 1 只学订阅；阶段 2 只学工具。不要在第一周就同时碰 SQLite、IPC、React。
3. **每个阶段都有「可观察的证据」。** 不是「代码写完了」，而是「能看到 X 现象、能复现 Y 故障、能在重启后恢复」。
4. **不写用不到的抽象。** 没有第二个存储后端就不要写 `StorageFactory`；没有第二种 UI 就不要写渲染器接口。
5. **风险前置。** 最大的未知（Electron 里的 `node:sqlite`）放在阶段 5 的第一天验证，而不是最后打包时才发现。

## 2. 阶段总览

| 阶段 | 主题 | 产出 | 验收关键词 | 预计 |
|---|---|---|---|---|
| 0 | 工作区与最小 Agent 调用 | 一个能跑一次问答的 Node 脚本 | 拿到完整回答；进程正常退出 | 0.5–1 天 |
| 1 | 流式输出与状态订阅 | 终端里逐字打印，并打印 `pi.live` 状态 | 增量帧、100ms 节流、最终帧一致 | 1–2 天 |
| 2 | 工具调用与可视化 | 一个自定义工具 + 工具卡片式日志 | 参数校验、三通道输出、错误不炸会话 | 2–3 天 |
| 3 | 中断、排队与多会话 | 命令式交互：发送/中断/切换会话 | steer/followUp、abort、fork 行为正确 | 2–3 天 |
| 4 | SQLite 持久化与崩溃恢复 | 可重启续跑的 CLI | kill -9 后恢复、replay 策略生效 | 2–4 天 |
| 5 | Electron 主进程与 IPC | 空窗口 + 一条 IPC 往返 | `node:sqlite` 门禁通过；单写者成立 | 2–4 天 |
| 6 | 渲染进程 replica 与聊天 UI | 可用的聊天界面 | ops 应用后与主进程一致；首字延迟 | 1–2 周 |
| 7 | 知识库 | raw/wiki 目录 + 4 个 kb 工具 + ingest 任务 | ingest 可恢复；index/log 正确 | 1 周 |
| 8 | 工具自举闭环 | 生成→测试→安装→热替换 | 坏工具被拦下；同名替换不影响运行中调用 | 1–2 周 |
| 9 | 智能 UI | TokUI DSL 流式渲染 + 点击二次会话 | 大 DSL 被拒；点击不重复提交 | 1–2 周 |

预计总量与参考资料的技术方案（M0–M5，约 11 周）接近，但这里的顺序把「持久化」提前到了 UI 之前，因为恢复语义会反过来影响 UI 的状态模型。

## 3. 依赖关系

```
阶段0 ──▶ 阶段1 ──▶ 阶段2 ──▶ 阶段3
                              │
                              ▼
                           阶段4 ──▶ 阶段5 ──▶ 阶段6 ──▶ 阶段9
                                                   │
                                        阶段7 ◀────┤
                                        阶段8 ◀────┘
```

- 阶段 7（知识库）只依赖阶段 4 的工具与存储，**可以和阶段 6 并行**。
- 阶段 8（工具自举）依赖阶段 2 的工具模型 + 阶段 5 的文件写入通道，**不依赖 UI**。
- 阶段 9 依赖阶段 6 的 replica 和阶段 1 的流式渲染。

参考资料中的 M0–M5 与本路线的映射：

| 技术方案里程碑 | 本路线阶段 |
|---|---|
| M0 Spike | 阶段 0–1 + 阶段 4 的 SQLite 冒烟 |
| M1 聊天骨架 | 阶段 5–6 |
| M2 工具箱 | 阶段 8 |
| M3 知识库 | 阶段 7 |
| M4 智能 UI | 阶段 9 |
| M5 打磨 | 阶段 6/9 的验收项 + 打包 |

## 4. 每个阶段的固定结构

阶段文档统一包含 10 节，顺序不变：

1. 前置概念
2. 要读的知识中心文档
3. 架构位置与模块协作
4. API 清单（函数/类型/事件）
5. 亲手编写的代码（文件与函数）
6. 实现提示（关键步骤、设计理由、易错点）
7. 调试方法
8. 验收标准
9. 阶段产出
10. 常见失败与排查

## 5. 里程碑与「可演示」定义

| 里程碑 | 包含阶段 | 演示时你要能现场做到 |
|---|---|---|
| **D0 能对话** | 0–1 | 终端输入问题，逐字输出，`pi.live` 状态同步变化 |
| **D1 能干活** | 2–3 | 模型调用你写的工具；中途 Esc 能停；连发两条消息按预期排队 |
| **D2 不怕崩** | 4 | `kill -9` 后重启，未完成的回答继续，工具不重复执行副作用 |
| **D3 有界面** | 5–6 | 窗口里发消息、看流式、看工具卡、重启后历史都在 |
| **D4 有知识** | 7 | 把一篇笔记 ingest 进 wiki，提问能引用，lint 能报问题 |
| **D5 能自举** | 8 | 让 Agent 写一个工具，自动跑测试用例，安装后立刻可用 |
| **D6 有智能 UI** | 9 | 模型生成一张选择卡片，点击后对话继续，刷新页面状态不丢 |

## 6. 风险登记

| 风险 | 影响 | 何时处理 | 对策 |
|---|---|---|---|
| Electron 内置 `node:sqlite` 不可用 / 版本过低 | 阶段 5 卡住 | **阶段 5 第一天**做门禁实验 | 用 better-sqlite3 实现 chord 的 `SqliteDatabase` 门面，再 `SqliteStorage.open(db)`（接口 6 个成员：`exec/run/get/all/transaction/close`，已核实） |
| `node:sqlite` 在打包后路径/ABI 异常 | 发布阻塞 | 阶段 5 末尾做打包冒烟 | 优先保持纯 JS 依赖；不引入原生模块 |
| pi-durable 是 experimental，1.5 可能破坏 API | 升级成本 | 全程 | 锁精确版本；把「SDK 用法」收敛到 `main/harness/` 一层；写回归脚本 |
| 渲染进程 apply 后与主进程不一致 | UI 幻觉 | 阶段 6 | 每次 watch 帧后校验 `hash(副本) === hash(主进程 view)`（仅开发模式） |
| 模型生成的 TokUI DSL 幻觉/超限 | 白屏 | 阶段 9 | 组件白名单 + 大小/深度上限 + 渲染失败降级并回灌错误 |
| 工具代码是任意 TS，能读整个磁盘 | 安全 | 阶段 8 | 静态校验 + 隔离 cwd + 首次安装人工确认 + 权限三档 |
| 上下文压缩导致「模型忘了」 | 体验 | 阶段 3/7 | 把关键事实写进 Document，不依赖聊天历史 |

## 7. V1 明确不做

- 多窗口同时操作同一会话（单写者下要额外做租约，V1 只支持一个窗口写）。
- 云端同步、多设备。
- 多进程/多实例打开同一 SQLite 文件。
- 插件市场、远程安装工具包。
- 自定义模型协议（除 OpenAI 兼容的 tokenplan provider 外）。
- 移动端。

这些不是「以后再说」的托词，而是为了让你在前 6 个阶段不被架构分叉拖住。
