## 0. 一期产品功能定位与本文档定位

### 0.1 一期产品功能定位

**一句话定位**

> **Pi Agent Desktop 一期 = 一个「关得掉、崩得起、查得到」的本机 Agent 工作台**：对话、工具执行、知识沉淀、界面状态全部落在本机一个可恢复的数据库里，让模型在你自己的文件与命令上干活，而你能随时打断、重启、追溯。

**三句展开**

1. **它不是聊天外壳。** 每次回答、每次工具调用、每个任务都是已写入库的状态；进程被杀之后能接着跑，副作用不会静默重复。
2. **它不是通用 RPA，也不是云端 Agent。** 一期只做三件事：本机文件、本机 shell、本地知识库。重活交给模型，副作用交给你审批。
3. **它不是封闭产品。** 一期就留出三个定制面——扩展（工具/Task/Hook）、文档（`app.*` 业务状态）、UI（模型生成的 TokUI 卡片），自己改的成本低。

**目标用户（一期只服务一类人）**

- 主用户：愿意读代码、想长期用一个**可改**的 Agent 来读仓库 / 写文件 / 整理笔记的开发者。
- 次用户：要求数据主权（历史不出本机、不落云端）的技术型用户。
- 明确不服务：只要「套个壳的 ChatGPT 网页版」的非技术用户——一期的价值在可恢复与可审计，不在开箱体验。

**四条主线场景（一期必须顺畅）**

| 场景 | 用户动作 | 一期必须给的承诺 |
|---|---|---|
| **干活** | 「读 README 总结三点，再建个 hello.txt」 | 工具真实执行；结果可在转录里审计；文件在磁盘上真实存在 |
| **打断与排队** | 生成中按停止；连发两条 | 停止后 1s 内 idle 且保留已生成部分；第二条排队而不是丢弃 |
| **不怕崩** | 直接 `kill -9` / `Cmd+Q` | 重启后消息在、回答继续、有副作用的工具不重跑 |
| **沉淀与自举** | 把笔记放进 `raw/` 让它收录；「帮我造个工具」 | wiki 可检索、回答带引用；工具经我确认后即装即用 |

**一期交付的能力清单（七项）**

1. **对话与流式**：部分回答每 100ms 上屏、thinking 可折叠、停止、排队、多会话切换、fork / reset / compact。
2. **工具执行**：4 个文件/shell 工具 + 三通道结果 + 三档审批（allow / ask / deny）+ 工具卡可视化。
3. **本地持久化**：单写者 SQLite，五类崩溃可恢复，可备份、可迁移。
4. **桌面界面**：聊天、工具卡、历史分页、状态条（运行中/排队/恢复中）、设置。
5. **本地知识库**：`raw/` → `wiki/`，可恢复的 ingest 任务、4 个 kb 工具、lint 死链。
6. **工具自举**：生成 → 静态校验 → 子进程试跑 → 人工安装 → 热替换 → 重启后仍在。
7. **生成式 UI**：模型生成 TokUI DSL 卡片，点击即一次幂等提交，刷新/重启后状态不丢。

**一期明确「不是」（硬边界）**

| 不是 | 理由 |
|---|---|
| 多用户 / 协作 / 团队空间 | 单写者 + 本地库；协作要重做权限与同步模型 |
| 云端同步、多设备、移动端 | 与数据主权定位冲突；一期先把本地恢复语义做对 |
| 插件市场 / 远程安装工具包 | 工具是特权代码；一期只做「本地生成 + 人工确认」 |
| 沙箱 / 权限隔离 | 一期安全来自人工确认 + 代码可读 + 只在本地跑，**不宣称隔离** |
| 向量检索 / 大规模语料 | 一期语料百页级，词法检索足够 |
| 多窗口同时写同一会话 | 需要额外做租约；一期单窗口写 |
| 通用 RPA / 浏览器自动化 | 一期只做文件、shell、知识三件事 |

**一期成功判据（从产品角度）**

- **可演示**：七项能力都能现场走通，不靠录屏。
- **可恢复**：五类崩溃 100% 恢复，副作用不重复；备份能被新实例打开。
- **可解释**：任一时刻能回答「谁在写、写到哪、崩了会丢什么、为什么会变慢」。
- **可控成本**：单机、单进程、无云端依赖；一期代码量控制在可通读范围（目标 < 15k 行 TS，不含生成物与依赖）。

**形态与交付**

- 主形态：macOS 优先的单窗口桌面应用（Electron），Windows 一期只保证能跑（不承诺细节）。
- 副形态：`apps/cli` 无 Electron 终端入口，用于排障、自动化验收与「不启动 UI 就能复现问题」。
- 不做服务端：没有账号、没有后端 API、没有遥测上传。

### 0.2 本文档的定位

| 维度 | 说明 |
|---|---|
| 覆盖范围 | V1 范围：能对话 → 能干活 → 不怕崩 → 有界面 → 有知识 → 能自举 → 有智能 UI |
| 不覆盖 | 打包上架、自动更新、多窗口写入、云端同步、插件市场、向量检索 |
| 与路线图的关系 | 路线图回答「做什么、先做什么」；本文档回答「工程怎么搭、模块怎么切、契约怎么定」 |
| 交付物 | 一个 pnpm workspace：`apps/{desktop,cli}` + `packages/*`，由 `pnpm typecheck / lint / test / smoke` 与 CI 把关 |

阅读顺序建议：第 2 章（架构）→ 第 4 章（文件结构）→ 第 5 章（决策）→ 第 6 章（数据模型）。契约细节看代码，不在本文。

## 1. V1 目标与范围

> §0.1 回答产品的「为什么/给谁/到什么程度」；本章把同一件事翻译成工程约束，后面所有架构与取舍都以这里为准。

### 1.1 一句话目标

**一个单写者的桌面 Agent：主进程独占 SQLite 上的 Harness，渲染进程只持有只读副本；任何一帧上屏前都已写入库。**

### 1.2 五条必须成立的承诺

| # | 承诺 | 校验方式 |
|---|---|---|
| 1 | 主进程是唯一写者 | 单实例锁 + 渲染进程禁止 import `pi-durable` + `lsof session.sqlite` |
| 2 | 先提交后展示 | 渲染进程无乐观插入；帧来自 commit；崩溃重启后内容一致 |
| 3 | 崩溃可从检查点继续 | 五类崩溃场景（`PI_CRASH_POINT`）全部有恢复证据 |
| 4 | 名字是契约 | Extension / Tool / Document kind / Entry kind / Task name 上线后不改 |
| 5 | 错误按范围分级 | `SessionFailed` 必须重建，工具异常只影响单次调用 |

### 1.3 范围表

| V1 做 | V1 不做 |
|---|---|
| 单窗口写入、多会话切换、fork / reset / compact | 多窗口同时写同一会话、会话租约 |
| 本地模型网关 + OpenAI 兼容 provider | 自定义模型协议、移动端 |
| coding / kb / toolsmith / smartui 四个扩展 | 插件市场、远程安装 |
| 词法检索的 LLM Wiki（raw → wiki） | 向量库 / embedding 索引 |
| 工具自举（生成→校验→试跑→人工安装→热替换） | 工具沙箱、多文件工具、npm 依赖安装 |
| TokUI DSL 流式渲染 + 幂等点击回传 | 模型生成任意 React 组件 |

## 2. 架构总览

### 2.1 进程与职责

```
┌──────────────────────────────────────────────────────────────────────┐
│ Renderer（React 19 + Vite）                                           │
│   views/chat · views/kb · views/tools · ui/TokUiBlock                 │
│   store/conv-store（ConversationView 副本）                            │
│   store/doc-store（app.* 文档副本）                                    │
│        │ 只读：applyFrame(prev, ops)      │ 写：window.pi.*.invoke      │
│        ▼                                 ▼                            │
│   preload: contextBridge 白名单（无 ipcRenderer 裸暴露）               │
└──────────────────────────────────┬───────────────────────────────────┘
                 push: view / doc / task.graph / host.status │ invoke
┌──────────────────────────────────┴───────────────────────────────────┐
│ Main（Electron，Node ≥ 22.19，ESM）                                    │
│  index.ts → lifecycle.ts                                              │
│   ├─ gate.ts            node:sqlite 存储门禁（已实测通过）             │
│   ├─ HarnessHost        持有 Harness / root / storage / close()        │
│   │    ├─ Harness       唯一写者                                      │
│   │    ├─ Registry      coding / kb / toolsmith / smartui             │
│   │    └─ Models        gateway(anthropic-messages) + tokenplan        │
│   ├─ FrameHub           watch → seq → sink（无 Electron 依赖）          │
│   ├─ WatchHub           FrameHub 的 WebContents sink 实现              │
│   ├─ DocHub             app.* 文档 watch → sink                        │
│   └─ IpcRouter          校验 → 业务 → 错误映射                          │
│  Storage: node:sqlite 单文件 userData/session.sqlite（WAL）            │
│  Env: (target) => new NodeExecutionEnv({ cwd: target.cwd ?? workspace })│
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 分层与依赖方向

```
renderer ──▶ shared-types（契约 + 纯函数 + 守卫）──▶ （无）
preload  ──▶ shared-types
main     ──▶ core ──▶ shared-docs / shared-types ──▶ extensions/*
core     ──▶ pi-durable / pi-ai / chord（禁止 import electron）
```

规则（用 ESLint `no-restricted-imports` 固化）：

1. `renderer` 不得 import `@earendil-works/pi-durable`、`electron`、`node:*`；只允许 `@earendil-works/chord/delta`（纯函数）与 `shared-types`。
2. `packages/core` 不得 import `electron`；这样 CLI 与 Electron 主进程共用同一套代码。
3. `extensions/*` 不得 import `electron`，也不得 `webContents.send`；对外只通过 `details` / Document 暴露状态。
4. 依赖只能向下，不允许 extensions 反向 import main。

### 2.3 一次提问的写入顺序（关键：每一步都先提交）

```
renderer  invoke conv.submit {convId,text,requestId}
   │
main  IpcRouter → 校验 → conversation.submit({type:"input",...}, ctx)
   │                    └─ commit#1：pi.user entry + submission 记录
   │  ◀── {submissionId}（立即返回，不等回答）
   │
   │  GenerationTask：prepare → request → tools → finish
   │    ├─ commit#2..n：partial assistant（默认每 100ms，pi.live.generation.message）
   │    ├─ commit#k：工具意图（pi.tool 任务 + pi.live.tools[slot]）
   │    ├─ commit#k+1：工具结果（pi.tool-result entry + slot.entry + details）
   │    └─ commit#last：pi.assistant 最终 entry，清 pi.live.run
   │
   └─ FrameHub：每次 commit 发布 (value, ops) → seq++ → send("view",{convId,seq,ops})
renderer  applyFrame(副本, ops) → useSyncExternalStore → 重渲染
```

**推论（工程约束）**：

- 渲染进程不做乐观插入：提交可能排队或被拒，等帧最多 100ms。
- 帧可能整帧（`isBase(ops)`），必须能覆盖；seq 跳号只做 resync，不补帧。
- 存储失败 → `SessionFailed` → Harness 关闭 → 只能重建，不能 catch 后继续用。

### 2.4 三条不可动摇的约束

1. **单写者**：一个 SQLite 文件同时只允许一个 Harness。框架不提供跨进程锁。
2. **先提交后展示**：渲染进程看到的每一帧都来自已提交状态。
3. **名字是契约**：见 §15.2 命名契约表。

## 3. 技术选型与版本基线

### 3.1 依赖基线（精确版本，不用 `^`）

| 包 | 版本 | 用途 | 说明 |
|---|---|---|---|
| `@earendil-works/pi-durable` | `1.4.0` | 运行时底座 | experimental，升级即破坏；锁死 |
| `@earendil-works/pi-ai` | `1.4.0` | 模型目录 / 请求 / 凭证 | 与 pi-durable 同版本，禁止重复实例 |
| `@earendil-works/chord` | `1.4.0` | `Op` / `applyImmutable` / `SqliteDatabase` | 渲染进程也用 `chord/delta` |
| `typebox` | `1.3.27` | 工具参数 + IPC 校验 | pi-durable 的固定依赖，复用到 IPC |
| `@jboltai/tokui` | `0.2.8`（npm 已到 0.2.9，需锁 0.2.8 或验证 0.2.9） | 生成式 UI DSL 渲染 | 只在渲染进程用 |
| `react` / `react-dom` | `19.x` | 渲染进程 | `useSyncExternalStore` |
| `electron` | 门禁决定（当前 45.x） | 桌面壳 | **必须实测 `node:sqlite`**，见 §14 G2 |
| `typescript` | `5.9.x` | — | `moduleResolution: bundler` |
| `tsx` | `4.x` | 脚本执行 | `node --import tsx` |
| `vite` | `7.x` | 渲染进程构建 | ESM only |
| `esbuild` | 最新 | main / preload 构建 | main=ESM，preload=CJS |
| `electron-builder` | 26.18.0 | 打包 | 打包后启动冒烟（未验证） |
| `react-markdown` + `remark-gfm` | 最新 | 消息渲染 | 默认不注入 HTML，避免 XSS |
| `tailwindcss` + `@tailwindcss/vite` | `4.x` | 样式 | 出问题退回纯 CSS 变量，不影响架构 |

运行环境：Node `>=22.19.0`（pi-durable `engines`），pnpm `10.x`，本地 Node 22.23.4 已验证 `pnpm test` / `pnpm smoke` / `pnpm build` 通过。

### 3.2 选型理由与备选

| 决策点 | 选择 | 理由 | 备选（触发条件） |
|---|---|---|---|
| 存储驱动 | `node:sqlite`（内置） | 零原生模块，打包最省事 | 门禁失败 → better-sqlite3 适配 `SqliteDatabase` 六方法（`exec/run/get/all/transaction/close`） |
| 状态管理 | 手写 store + `useSyncExternalStore` | 副本模型只有一个写入口，引入 Redux/Zustand 会隐藏引用稳定性问题 | 只在出现跨模块共享需求时再评估 |
| 消息渲染 | `react-markdown` | 不发生 HTML 注入；流式文本可增量 re-parse 单条 | 需要自定义标签时加插件，不换库 |
| 富 UI | TokUI 核心类 + 自写 React 包装 | 官方 React 适配器不在基线内；核心类足以支撑 `render/feed` | 适配器可用时再评估 |
| 构建 | Vite（renderer）+ esbuild（main/preload） | 显式、可解释；避免 electron-vite 的隐式约定 | 团队规模扩大后再考虑 electron-vite |
| 测试 | `node:test` + `tsx` | 零依赖；纯模块可直测 | 需要 DOM 断言时再加 vitest（仅 renderer） |
| IPC 校验 | TypeBox `Value.Check` | 与工具参数同一套 schema 语法，少一个依赖 | — |

### 3.3 版本策略

- 依赖写精确版本；`pnpm-lock.yaml` 入库。
- 升级 `pi-durable` 必须走「备份库 → 跑全量测试与冒烟 → 手测终端主线」三步。
- SQLite schema 与 Document `version` 是两套迁移：前者归 SDK，后者归应用（`migrate()`）。
- 1.3.x 的库不能与 1.4.x 互开（schema v2）。

## 5. 关键设计决策（ADR）

### D1 单写者与单实例（不可协商）

- `app.requestSingleInstanceLock()` 必须在 `app.whenReady()` **之前**；`second-instance` 只聚焦已有窗口。
- Harness 只在主进程创建；`renderer` 与 `preload` 都不 import `pi-durable`（ESLint 拦截）。
- 同一个 SQLite 文件不允许第二个 Harness，即使是「只读」进程——调度器会写任务状态。
- 开发期起两个 `electron .` 前先 `lsof userData/session.sqlite` 确认旧进程已退出。

### D2 先提交后展示：禁止乐观更新

- `Composer` 只发 `conv.submit`，**不**在本地插入用户消息；最多显示「发送中」的输入框状态。
- `abort` 后不本地标记「已停止」，等 `pi.live.run` 消失，以及最后一条 assistant 消息写进库。
- 理由：提交可能排队（`followUp`）或被拒（`reject`），乐观插入会让「用户看到的消息」与「实际顺序」不一致。

### D3 `app.*` 文档如何到达渲染进程（本方案的关键决策）

**事实（已核实）**：`ConversationView.docs` 只挂载 5 个内置文档（`pi.agent` / `pi.live` / `pi.inbox` / `pi.provider` / `pi.usage`），见 `dist/harness/view.js` 的 `MOUNTED`。自定义 `app.*` 文档**不会**出现在 view 里。

因此：

1. **物化**：`HarnessOptions.conversationCreated`（已核实签名 `(tx, conversation) => void | Promise<void>`）在每次创建/分叉会话的同一个 commit 内写入 `app.workspace` / `app.smartui` 的初值；启动时再补一次 session 级 `app.settings` / `app.toolbox` / `app.kb`（`snapshot()` 为 `undefined` 才写）。
   - 原因：`watchDoc()` 对不存在的文档返回 `undefined` 且**不会创建**它；物化之后 watch 才稳定。
2. **推送**：新增 `doc` 推送通道，`DocHub` 用 `watchDoc()` 为每个已物化文档建立 watch，帧格式 `{scope, kind, convId?, seq, ops}`。
3. **不做的**：不把 app 文档塞进 `pi.live`（会污染内置语义、放大写）；不在渲染进程 `docs[kind] as T` 强转（`JsonObject` 无运行时校验，必须在 `shared-types/guards.ts` 写守卫）。

### D4 帧协议：seq / isBase / resync

```ts
// shared-types/src/frame.ts（帧协议的唯一定义处）
export type Frame<T> = { seq: number; ops: Op[]; value?: T };
export function applyFrame<T>(prev: T | undefined, ops: readonly Op[]): T | undefined {
  if (ops.length === 0) return prev;
  return isBase(ops) ? applyImmutable<T>(undefined, ops) : applyImmutable(prev, ops);
}
```

规则：

1. **seq 由 FrameHub 自增，与 Storage 的 `Seq` 无关**，两者混用会让重连判断永远失败。
2. `conv.open` 必须**原子地**返回 `{view: watch.value, seq}`（attach 时取值同时记 seq）；实现成「先 `viewState()` 再 `watch()`」会错位。
3. 渲染端判定顺序固定：`convId` 匹配 → `seq` 重复则忽略 → `seq !== last+1` 则 resync（保画面） → `isBase` 覆盖 → 增量应用。
4. resync 同一时刻只允许一次，避免跳号时连发多次重连。
5. 开发模式加 `debug.viewHash`：主进程对当前 view 做稳定序列化 hash，渲染端逐帧（节流）比对，不一致即 resync 并记日志。

### D5 IPC 信封与错误码

- 命令一律 `invoke`；推送一律 `webContents.send`。**写操作不允许 fire-and-forget**。
- 返回值统一 `{ ok: true, data } | { ok: false, error: IpcError }`；`preload` 里再转成 throw，渲染端写 `try/catch`。
- 错误码：`INVALID_ARGUMENT` / `NOT_FOUND` / `BUSY` / `SESSION_FAILED` / `UNSUPPORTED` / `INTERNAL`。
- 不把原始 Error 序列化过去（丢栈、可能泄露路径与 key）。
- 不暴露通用 `doc.write` / `ipc.send`：commit 语义必须留在主进程。

### D6 工具三通道与审批

| 通道 | 去处 | 铁律 |
|---|---|---|
| `output` | 模型上下文 | 只放模型判断下一步所需；大日志不放这里 |
| `structuredOutput` | 程序（`executeTool` 调用方） | 声明了 `structuredOutputSchema` 就必须给（除 `isError`） |
| `details` | UI（`pi.live.tools[i].details`） | 受 progress 节流；不放每秒变化的大对象 |

审批放在 Hook，不放在工具内部：

```ts
hook(ToolTask, {
  async beforeTool(call, api, ctx) {
    const verdict = classify(call);          // 纯函数，可单测
    if (verdict === "deny") return { block: `禁止执行：${describe(call)}` };
    if (verdict === "ask") {
      const ok = await requestApproval(call, api, ctx);  // 见下
      if (!ok) return { block: "用户拒绝执行" };
    }
  },
});
```

`requestApproval` 的两级实现：

- **CLI**：`node:readline` 询问；`process.stdin.isTTY === false` 时一律拒绝（保证脚本可无人值守复现）。
- **Electron（已实现）**：`@pi/core` 的 `ApprovalBroker` 生成 id，把 pending 写进 `app.approvals`（审计镜像）并推送 `approval` 通道，然后 `await` 一个**内存里的 Promise**；UI 走 `approval.respond` → 这个 Promise 结算 → 再写回 `latest` 终态。
  - 为什么等待放在内存而不是文档：`HookApi` 只有 `snapshot` / `snapshotAsOf`，**没有 `watch`**，钩子无法「等文档变化」。同进程的那个 Promise 是唯一能立刻解除阻塞的东西；文档只做审计，以及重启后清理残留（`ApprovalBroker.list()` 会顺手清掉没人在等答复的 pending）。
  - 等待必须同时带**超时**（默认 120s）与**取消信号**（`context.abortSignal`）：`Scheduler.join()` 关闭时只发 abort 信号，不认信号的 await 不会返回，`host.close()` 就会一直等。

工具命名与重放策略（写进代码，不靠记忆）：

| 工具 | name | replay | executionMode | 备注 |
|---|---|---|---|---|
| 读文件 | `read` | `safe` | 默认 | SDK `createReadTool`：offset/limit + 截断续读 + 图片按模型能力降级 |
| 列目录 | `list_dir` | `safe` | 默认 | 自建：深度上限 3（默认 1）、忽略 `node_modules`/`.git`、最多 400 条 |
| 写文件 | `write` | `unsafe` | `sequential` | SDK `createWriteTool`：自动建父目录，同路径写入串行 |
| 改文件 | `edit` | `unsafe` | `sequential` | SDK `createEditTool`：`oldText`/`newText` 多段替换 |
| 跑命令 | `bash` | `unsafe` | `sequential` | SDK `createBashTool`：输出走 `outputLimits` / 内置 spill |
| 知识检索 | `kb_search` | `safe` | 默认 | 只搜 wiki |
| 知识读取 | `kb_read` | `safe` | 默认 | 只读 wiki/index/log/AGENTS |
| 收录 | `kb_ingest` | `unsafe` | `sequential` | 只 `createTask` 后立即返回 |
| 自检 | `kb_lint` | `safe` | 默认 | 死链 / 缺 frontmatter / 索引漂移 |
| 造工具 | `tool_create` | `unsafe` | `sequential` | 只创建 build 任务 |
| 工具清单 | `tool_list` | `safe` | 默认 | 读 `app.toolbox` |
| 渲染 UI | `render_ui` | `safe` | 默认 | 校验后把 DSL 放 `details` |

前五个已实现在 `packages/extensions/coding`。**为什么复用 SDK 的四个工具而不是重写**：截断后「用 offset 继续读」的语义、图片按模型能力降级、输出超限写到临时文件、写文件按路径串行、读完重读确认没被并发改动——这些都容易写错且 SDK 已有实现，重写只会得到一份更弱的版本。扩展只做 SDK 没做的三件事：补 `list_dir`、路径边界、审批。


### D7 路径边界与 cwd

- 工作区根固定为 `app.getPath("userData")/workspace`，**永不用 `process.cwd()`**（打包后是 app 目录）。
- `env` 是工厂：`env: (target) => new NodeExecutionEnv({ cwd: target.cwd ?? workspaceRoot })`；不缓存实例（`cwd` 随会话变化）。
- 所有相对路径校验统一走一个函数，用 `path.resolve` + `path.relative` 判断是否以 `..` 开头；**不用字符串 `startsWith`**（`/root2` 会被 `/root` 误判）。
- 词法判定不够：工作区里放一个指向外面的软链，词法上完全合法。所以 `createPathGuard` 再加一层真实路径判定：目标（或它最近的已存在祖先，给新建文件用）与工作区根**两边都 `canonicalPath` 后**再比较；只归一化一侧会把 macOS 的 `/var` → `/private/var` 全部判成越界。
- `bash` 的 cwd 在 `prepare` 里查：cwd 落到工作区外说明装配错了，直接失败而不是硬跑。shell 自身的 `cd` 挡不住（也不该挡），那是审批该管的事。
- `NodeExecutionEnv` 的方法返回 `Result`（`{ok:true,value} | {ok:false,error}`），失败不抛异常；工具里统一处理错误码（`not_found` / `permission_denied` / `is_directory` …）。

### D8 Task 与 Tool 的分工

| | Tool | Task |
|---|---|---|
| 触发 | 模型 / 其它工具 | IPC、Hook、其它任务 |
| 时长 | 秒级 | 分钟级，可跨重启 |
| 崩溃恢复 | 按 `replay` 重跑或中断 | 从最后检查点继续 |
| 能否调工具 | 能（`api.executeTool`） | **不能**（`TaskRuntime` 无此方法，已核实） |

经验法则：**模型要看结果的做 Tool；用户要等它完成的做 Task。** kb ingest、tool build 属于后者。

### D9 知识库：raw 只读、wiki 可重建

- `raw/` 是事实来源，永不修改；`wiki/` 是生成物，可随时重建。
- ingest 按 phase 推进，每 phase 一个 `rt.commit()`；`abort` 必须提交终态。
- 幂等靠内容 hash：同 hash 跳过，变 hash 覆盖同一页面（不是新建）。
- 写入用「临时文件 + rename」，避免半截文件被检索到。
- `index.md` 是**重建**而不是增量拼接；并发 ingest 用 `app.kb.indexVersion` 做写入前比对，冲突则重跑 index phase。
- 模型只读 wiki，不读 raw（引用稳定 + 不把半成品喂给模型）。
- 检索 V1 用词法（标题权重 + 词项命中），语料 > 500 页再考虑倒排索引，不做向量。

### D10 工具自举：工厂注入 + 版本化 import

工具源码契约（先定死，再让模型生成）：

```js
// userData/tools/<slug>/tool.v<N>.mjs —— 不 import 任何包，只导出工厂
export default function create({ Type, defineTool }) {
  return defineTool({
    name: "user.<slug>",
    description: "...",
    parameters: Type.Object({ /* ... */ }),
    async execute(args, api, ctx) {
      /* 只通过 api.env 访问文件；返回值遵循 ToolExecutionResult */
      return { output: "...", details: { /* ... */ } };
    },
  });
}
```

理由：从 `userData/tools/` 加载时 `@earendil-works/pi-durable` 不在其解析链上；注入依赖能同时解决打包后的解析问题，并让测试时替换 `Type`/`defineTool`。

- 加载：`import(pathToFileURL(file).href + "?v=" + version)`（版本进 URL 才能绕过 ESM 缓存）。
- 顺序：先 `validate`（静态）→ 子进程 `test` → 用户确认 → `loader` import → `registry.install` → commit 写 `app.toolbox`。
- 热替换语义：运行中的调用持旧代码，后续调用用新代码；**安装只 install 不 uninstall**（避免空档）。
- 启动时执行「恢复安装」：读 `app.toolbox.enabled === true`，逐个 load + install，失败的标 `failed` 但不阻塞启动。

### D11 智能 UI：DSL 是不可信输入

- `render_ui` 只做校验与打包，把 `{v, uiId, dsl, handlers, summary}` 放 `details`；`output` 只回 `[UI 已渲染]`。
- `uiId = "ui:" + callId`（重放稳定）；DSL 不复制进 `app.smartui`（entry 里已有，避免两份真相）。
- 校验：≤64KB、深度 ≤32、标签闭合、组件/属性白名单、handler ∈ 5 个固定名、URL 只允许 `https:`、`id` 唯一、拒绝 `<script` / `javascript:`。
- 交互幂等：**一次点击生成一个 `crypto.randomUUID()`**，`requestId = "ui:" + uiId + ":" + actionId`；同一次点击的重试复用；不用自增序号（重启撞号）或时间戳（无法区分重试与新点击）。
- 点击后不本地标记「已处理」，等 `app.smartui` 或 `app.ui_action` entry 回来。
- `TokUiBlock` 一个 `uiId` 一个实例；`feed` 只喂后缀；前缀变化时全量 `render()`；卸载 `disconnect()`；`ErrorBoundary` 包住，单条消息失败不影响整页。

### D12 凭证存储

- `CredentialStore` 四方法（`read` / `list` / `modify` / `delete`）；`modify` 是唯一写路径，必须按 provider 串行。
- Electron 实现：`safeStorage.encryptString()` → base64 → `userData/credentials.json`。
- `safeStorage.isEncryptionAvailable() === false`（Linux 无 keyring）时：拒绝保存并提示改用环境变量，**不静默降级明文**。
- 现在用 `envApiKeyAuth` + 环境变量即可，不要提前写加密层。

### D13 模块格式

| 产物 | 格式 | 原因 |
|---|---|---|
| `main/index.mjs` | ESM | Electron ≥28 支持 ESM main；与 workspace 的 `"type":"module"` 一致 |
| `preload/index.cjs` | **CJS** | `sandbox: true` 下 preload 不支持 ESM；必须打包成 CJS |
| renderer | ESM（Vite） | 标准 |
| `packages/*` | 源码直连（workspace exports 指 `src`） | 免构建步骤；由 esbuild/vite 统一打包 |

### D14 日志与 `onReport`

- `HarnessOptions.onReport(error, info)` 按 `info.type` 分级：`session_failed` 必须触发重建；`task_parked` / `task_faulted` 只告警 + UI 可重试入口；`listener_error` 记录帧回调 bug。
- 记录：启动（db 路径、workspace、Electron/Node 版本、门禁结果、扩展清单）、每次 submit（requestId/convId/submissionId）、每次 `closed`（reason/error）、退出是否成功 close。
- 不记录：消息全文、API key、工具输出全文。
- 开发期打 console；生产写 `userData/logs/`（按天滚动，保留 7 天）。

## 6. 数据模型

### 6.1 Entry kinds

内置 kind 的常量定义在 `packages/shared-types/src/frame.ts`（`EntryKind` / `DocKind`），是唯一真相。
约定：

- `pi.*` 是 SDK 写入的条目；`app.*` 是应用自己的条目（定义在 `packages/shared-docs/src/entries.ts`）。
- 带 `model` 字段的条目会进模型上下文；应用条目默认不带，只用于界面与审计。
- 条目 kind 与文档 kind 都是写入库契约，改名等于旧会话读不出来。

### 6.2 `app.*` 文档

定义在 `packages/shared-docs/src/`：`kind`、`scope`、`history`/`fork`、`version` 与字段以代码为准。
本节只留决策：

- 只存**用户偏好与索引**，不存运行策略：压缩阈值这类放 `HarnessOptions.settings`，因为它每次使用都会重读。
- 不存大对象：工具源码在磁盘，DSL 在 entry 的 `details`，日志在文件。
- `checkpointWhen` 用保守策略：攒够一批增量再落一次整帧，避免每次小改动都写完整 base。
- `version` 决定 `migrate`：改字段必须升版本并写迁移，否则旧数据读不出来。
- 已实现：`app.settings`（session）、`app.approvals`（conversation / latest）、`app.workspace`（conversation / rewindable / asOf）。
- 未实现且用到再写：`app.kb`、`app.toolbox`、`app.smartui`——现在写就是猜。

### 6.3 Task 定义

| name | version | phase 链 | 说明 |
|---|---|---|---|
| `app.kb.ingest` | 1 | `read → summarize → write → index → done` | 每 phase 一次 `rt.commit`；`abort` 提交终态并回写来源状态 |
| `app.tool.build` | 1 | `spec → generate → validate → test → verified →(人工)install → done` | 在 `verified` 停下等安装命令，不自动装 |

- `phase` 名一旦发布不改（写进任务状态）。
- 任务状态保持小：正文类中间产物设上限（如 64KB），超限截断并记 `truncated`。
- 时间一律用 `rt.now()`（Harness 时钟），不用 `Date.now()`。
- 长等待用 `rt.sleepUntil(until, checkpoint, ctx)`（1.4.0 无 `sleep()`）。

### 6.4 磁盘布局

```
<userData>/                                   # app.getPath("userData")
├─ session.sqlite                             # Harness 存储（WAL）
├─ session.sqlite-wal / -shm
├─ credentials.json                           # safeStorage 加密后的凭证

```

### 6.5 SQLite 与备份

- 打开：`openNodeSqliteStorage(dbPath, { busyTimeoutMs: 5000, walAutoCheckpointPages: 1000 })`（已核实签名）。
- 备份必须 `VACUUM INTO 'backup.sqlite'`（目标文件需先删除）或先 `close()` 再拷；**只拷主文件会丢最近事务**。
- 升级 SDK 前：备份 + 单脚本回归；1.3 ↔ 1.4 schema 不兼容。
- 磁盘满 / 存储抛错 = `SessionFailed` = 会话关闭，必须走重建（§11）。

## 7. IPC 契约

契约定义在 `packages/shared-types/src/ipc.ts`（命令通道 `IpcMap`）与 `push.ts`（推送通道 `PushMap`），
错误码与映射在 `errors.ts`。**本节不重复类型定义**——两边各写一份必然漂移。

只留三条决策：

### 7.1 信封

主进程一律返回可判别的封套（`IpcResult`）：渲染进程不做异常穿透，拿到的是
`{ok:true, value}` 或 `{ok:false, error:{code, message}}`。

### 7.2 错误码

`INVALID_ARGUMENT`（参数或状态不满足前提，不重试）、`NOT_FOUND`、`BUSY`（可转排队后重试）、
`SESSION_FAILED`（存储失败：页面进入恢复态并禁用输入）、`UNKNOWN`。

### 7.3 推送与丢帧重连

推送按会话各自的 `seq` 单调递增。渲染进程发现跳号即重新 `conv.open` 取整帧，
不要试图从中间补齐——这是「先提交后展示」的一部分。

## 8. 构建、运行与打包

### 8.1 根脚本

```json
{
  "scripts": {
```

### 8.2 开发循环（`apps/desktop/build/build.ts --dev`）

1. 启动 Vite dev server（renderer，`server.port` 固定 5173）。
2. esbuild watch 两产物：`dist/main/index.mjs`（ESM，`external:["electron"]`）、`dist/preload/index.cjs`（CJS，`external:["electron"]`）。
3. 两个产物首轮构建完成后 `spawn(electron, [appPath], { env: { PI_DEV_SERVER_URL } })`。
4. main 侧：`PI_DEV_SERVER_URL` 存在 → `win.loadURL(url)` + 打开 DevTools；否则 `loadFile(dist/renderer/index.html)`。
5. 主进程改动重启 electron；preload 改动需重启窗口（改 URL 参数避免缓存）。
6. renderer 改动走 HMR（`Cmd+R` 强制刷新时，`did-start-navigation` 清理旧 sink）。

### 8.3 打包（`electron-builder.yml`）

- `files`: `dist/**`、`package.json`；`asar: true`。
- **`asarUnpack`**: 不含原生模块（若引入 better-sqlite3 则必须 unpack + 重建）。
- `extraResources`: 无（`workspace/` 与 `tools/` 都在 `userData`，不入包）。
- `mac`: `target: dmg`，`hardenedRuntime`；`win`: `nsis`。
- 打包后必须冒烟：① 启动 + `node:sqlite` 门禁；② 提交一条消息；③ 安装一个工具并重启；④ 关窗/退出不丢消息。

### 8.4 tsconfig 要点

- `target: ES2022`、`module: ESNext`、`moduleResolution: bundler`、`strict: true`、`verbatimModuleSyntax: true`、`noUncheckedIndexedAccess: true`。
- 各包用 `references` 组合；`packages/*` 的 `exports` 指向 `./src/index.ts`（工作区内免构建）。
- `apps/desktop` 单独 tsconfig（`types: ["electron"]`、`jsx: react-jsx`）。

## 10. 安全模型

| 面 | 措施 |
|---|---|
| 进程隔离 | `contextIsolation:true`、`nodeIntegration:false`、`sandbox:true`、`webSecurity:true`；只加载本地文件；开发期 `PI_DEV_SERVER_URL` 才联网 |

| IPC 输入 | TypeBox 校验 + 归属校验 + `assertTrustedSender` |

| 凭证 | `safeStorage` 加密；不可用时显式拒绝而非明文 |

| 渲染数据 | `details` / `docs` 一律视为不可信 JSON，先守卫；不 `eval`、不 `innerHTML` |
| 日志 | 不写消息全文、key、工具输出全文 |

## 11. 失败与恢复模型

| 失败 | 范围 | 应用行为 |
|---|---|---|
| Storage 抛错 | 整个 Session（`SessionFailed`） | 监听 `harness.closed` → `host.status=recovering` → 停 FrameHub/DocHub → 重建（1s/2s/4s，最多 3 次）→ 重新 open/resume/root → 全部重开 watch → 推整帧 |
| 非法读请求 | 单次调用（`StorageRequestError`） | 修正参数，不重建 |
| commit 内先写表后读表 | 单次调用（`ReadAfterWrite`） | 改为只通过 `tx` 读 |
| 模型请求失败 | 当前 run | 任务重试 / 失败提示；保留用户输入 |
| 工具抛错 | 单次工具调用 | 转成 `isError` 结果，会话继续 |
| 任务 panic | 该任务（`task_faulted`） | UI 展示原因 + 允许 `retryTask` |
| 任务反复崩 | 该任务被 park（`restart_limit`） | UI 必须给「重试 / 放弃」入口 |
| 定义缺失 | 该任务 blocked | 提示装回扩展或迁移 |
| 渲染进程崩溃 / 刷新 | 只影响窗口 | 主进程与任务继续；重开窗口重新 `conv.open` + `doc.get` |
| 帧回调抛错 | 该 watch（`listener_error`） | 记日志；再用 `watch.value` 重新同步一次 |

重建清单（顺序固定）：`stopAll hubs` → `close host` → `open storage` → `Harness.open` → `resume` → `root` → `materialize docs` → `start hubs` → 推整帧 → `host.status=ready`。**不复用旧的 storage/root/watch 句柄。**

## 12. 性能预算与写放大

| 指标 | 目标 | 手段 |
|---|---|---|
| 首字延迟 | < 1.5s（含模型首 token） | 拆三段计时：模型首 token / `partialIntervalMs` / IPC+渲染；先排除 resync 风暴 |
| 部分提交间隔 | 100ms（默认） | 不调到 0：每 token 一次事务会写满 SQLite 且 UI 更卡 |
| 帧数 | 200 字回答 10–30 帧 | 超过上千帧说明间隔被调小 |
| 单帧大小 | < 数 MB | `conv.open` 只给最近 N 条（默认 50），历史用 `conv.entries` 游标 |
| 渲染重绘 | 每帧只重渲「当前流式气泡」 | 拆分 `MessageList` / `StreamingBubble`；`useMemo` 依赖 `entries` 引用 |
| 写放大 | 一个 2s 回答 WAL 增长 < 5MB | `details` 只放摘要/增量；数组大变动用 family |
| 长会话 | 1000 条可用 | 分页加载 → 虚拟列表（key 用 `entry.id`） |

调试写放大：`SELECT page_count * page_size FROM pragma_page_count(), pragma_page_size();` 观察 WAL。
