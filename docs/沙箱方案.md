# 沙箱方案

> 本文只写**已验证的事实**与**要落地的设计**；未核实的部分标「待验证」，策略上还等拍板的标「待定」。
>
> 状态：**Phase 1 已实现**（`packages/core/src/agent/{sandbox,env}.ts`，用例 `agent/sandbox.test.ts`）；
> Phase 2 仍是计划（§8）。

## 1. 结论

用 **macOS 原生 Seatbelt（`/usr/bin/sandbox-exec`）** 包住每一个 `bash` 子进程：

- 写：只允许工作区（+ 临时目录），其余一律 `Operation not permitted`；
- 网络：默认拒绝，可用开关放行；
- 整棵子进程树继承同一份策略（`sh -c 'sh -c ...'` 也逃不出去）；
- 不引入任何原生依赖，不改工具实现——只在 `ExecutionEnv` 外面套一层装饰器。

理由：所有 shell 执行都收敛在 `ExecutionEnv.exec()` 一个入口（`packages/core/src/agent/env.ts` 建的 `NodeExecutionEnv`），
一处拦截即可全覆盖；Node 自带的 `--permission` 因为 bash 必须 `--allow-child-process`，一开就失去意义。

## 2. 现状与缺口

| 能力 | 现在 | 缺口 |
|---|---|---|
| `read` / `write` / `edit` / `list_dir` | 进程内实现，已有工作区边界：词法判定（`path.resolve` + `path.relative`）+ 真实路径判定（挡软链），见 `packages/extensions/coding/src/{paths,guard}.ts` | 边界只在「工具参数」这一层；工具本身写盘不经过随包沙箱 |
| `bash` | 只有起点 `cwd` 校验 + 三档审批（allow / ask / deny） | 命令里可以 `cd` 出去、写任何路径、联网、起后台进程 |
| 审批 | 120s 超时、超时按拒绝 | 审批是**软边界**：人点错就没了，不能当沙箱用 |

`README.md` 的「已知限制」现状：「`bash` 本身可以 `cd` 到工作区外（边界检查只管 cwd 的起点），靠审批阑住；V1 不宣称沙箱。」本文就是要消掉这一条。

## 3. 方案对比

| 方案 | 拦 spawn 子进程 | 写边界 | 网络边界 | macOS | 落地成本 | 结论 |
|---|---|---|---|---|---|---|
| **Seatbelt（`sandbox-exec`）** | ✅ 整棵进程树 | ✅ | ✅ | ✅ | 低：一个装饰器 + 一段 profile | **本次采用** |
| Linux `bwrap`（bubblewrap） | ✅ | ✅ | ✅ | ❌ | 中 | 同一套装饰器，换 profile 生成器；后续 |
| Lima / `container` / 容器 VM | ✅ | ✅ | ✅ | ✅ | 高：镜像、文件同步、启动时长 | 面向「跑不可信代码」，后续 |
| Node `--permission`（Permission Model） | ❌ | 弱 | ❌ | 部分 | 低 | 不采用：bash 必须放子进程，一放就失效 |
| 仅审批 | — | 软 | 软 | ✅ | 0 | 保留，作为叠加的「人确认」，不是替代 |

## 4. 推荐方案：Seatbelt 装饰器

### 4.1 拦截点

```
HarnessOptions.env(target)  →  createNodeEnvFactory(options)        packages/core/src/agent/env.ts
                            →  NodeExecutionEnv.exec(cmd)           @earendil-works/pi-durable/env/node
                            →  spawn(shell)
```

所有 shell 执行（`bash` 工具、嵌套调用、将来任何新工具）都走 `exec`。所以在 `createNodeEnv` 返回前包一层：

```ts
// packages/core/src/agent/sandbox.ts（新增）
export function wrapSandboxed(env: NodeExecutionEnv, profile: SeatbeltProfile): ExecutionEnv
```

装饰器只重写 `exec`，其余方法（`readTextFile` / `writeFile` / `watch` / `cleanup` …）原样转发给内层：

```ts
exec(command, options, context):
  typeof command === "string"
    ? inner.exec([SANDBOX_EXEC, "-f", profilePath, shell, "-lc", command], options, context)
    : inner.exec([SANDBOX_EXEC, "-f", profilePath, ...command], options, context)
```

为什么要走 argv 形式：`NodeExecutionEnv` 对 argv 不做 shell 解析、直接 `spawn(program, args)`，
所以我们把「`sandbox-exec -f profile <shell> -lc "<原命令>"`」当成一条普通 argv 交回去即可，
超时、`cwd`、输出 spill、`killProcessTree`、abort 全部沿用 SDK 已有实现，不重写进程管理。

`cleanup()` 时删掉临时 profile 文件（`os.tmpdir()` 下，权限 0600）。

### 4.2 profile（按工作区现生成）

```
(version 1)
(allow default)

; 写：只放开工作区、临时目录、必要设备节点
(deny file-write*)
(allow file-write*
  (subpath "<workspace>")
  (subpath "<tmpdir>")
  (subpath "/private/var/folders")     ; macOS 自己的临时目录
  (literal "/dev/null")
  (literal "/dev/stdout")
  (literal "/dev/stderr"))

; 网络：按策略生成（deny 时加这一行）
(deny network*)
```

`<workspace>` 必须是 `realpath` 之后的绝对路径（与现有 `canonicalPath` 判定保持一致，否则软链会让例外条件错位）。

### 4.3 已实测结果（macOS 26.2 / build 25C56，`/usr/bin/sandbox-exec` 存在）

| 用例 | 结果 |
|---|---|
| `echo ok > <workspace>/a.txt` | 成功 |
| `echo bad > /private/tmp/outside.txt`（工作区外） | `sh: ...: Operation not permitted`，退出码 1 |
| `rm -f <workspace>/a.txt` | 成功（写权限已放开） |
| `cat /etc/hosts`（读工作区外） | 成功（当前 profile 不动读） |
| `curl -m2 http://example.com`（deny network） | 被拦（退出码 28 / 连接失败） |

`bash -c '...'` 里再 `sh -c '...'` 也受限——Seatbelt 的沙箱随 `fork/exec` 继承，这一点是它相对「包装命令字符串」的根本优势。

## 5. 策略（待定项）

| 项 | 建议默认 | 备选 | 影响 |
|---|---|---|---|
| 网络 | `deny`，`PI_SANDBOX_NET=allow` 放行 | 默认 allow | `pnpm install` / `git fetch` / `curl` 需要网络；被拦时应给出明确报错并提示这个开关 |
| 读 | 全放行 | 额外屏蔽 `~/.ssh`、`~/.aws`、`~/Library/Application Support` | 屏蔽会连带影响 `git push`、`gh` 登录态；作为第二档开关更合适 |
| 沙箱不可用（老系统 / 被移除 / 非 macOS） | **明确失败**并在界面提示 | 静默降级为「仅审批」 | 静默降级最危险：用户以为有沙箱 |
| 开关 | `PI_SANDBOX=seatbelt`（macOS 默认）｜`off` | — | 与现有 `PI_*` 环境变量风格一致 |

`off` 只应出现在排障场景；线上（打包后）默认 `seatbelt`，且当 `sandbox-exec` 缺失时拒绝执行 `bash`，而不是无沙箱执行。

## 6. 与审批的关系

两者叠加，不互相替代：

- **沙箱是硬边界**：即使审批通过（人点了「允许」），写工作区外、联网仍然会被内核拒绝；
- **审批是意图确认**：`rm -rf`、`git push --force` 这类「在工作区内也可能造成损失」的命令，仍走三档策略；
- 审批文案可以顺带说明当前沙箱策略（“写：仅工作区 / 网络：拒绝”），避免用户误以为批准后为所欲为。

## 7. 落地步骤（Phase 1）

1. `packages/core/src/agent/sandbox.ts`：`SeatbeltProfile`（生成 profile 文本 + 落盘临时文件）+ `wrapSandboxed(env, profile)`；
2. `createNodeEnv`（`agent/env.ts`）按 `PI_SANDBOX` 决定是否包装；非 macOS 或 `sandbox-exec` 探测失败时按 §5 的策略处理（默认明确失败）；
3. `apps/desktop/src/main/runtime.ts` / `apps/cli/src/main.ts` 把工作区路径传进 env 工厂（已有 `workspace` 参数，无需新参数）；
4. 测试（`packages/core/src/agent/sandbox.test.ts`，真文件系统，非 macOS 跳过）：
   - 工作区内写成功、工作区外写失败；
   - `sh -c 'sh -c "echo > /etc/x"'` 同样失败（验证进程树继承）；
   - 网络被拒（连接失败/超时）；
   - `exec` 的 argv 形式（`["echo", "hi"]`）也被包住；
   - profile 里的工作区路径是真实路径（软链无法绕过）。
5. 文档：`README.md` 的「已知限制」改成实际边界描述（含 `sandbox-exec` 是 deprecated API 这一事实与探测策略）、`CHANGELOG`、`docs/知识中心/技术方案.md` 的边界一节。

## 8. 后续（Phase 2）：tools worker —— 让文件工具也进内核边界

### 8.1 为什么需要

Phase 1 只把 `bash` 放进内核沙箱。进程内的 `read` / `write` / `edit` / `list_dir` 仍由应用层路径边界看守
（`paths.ts` 词法 + `guard.ts` realpath），强度是「应用级」，有两个缺口：

1. **fail-open 依赖代码正确性**：少归一化一次路径、漏掉一层软链判定，边界就穿了——它不是内核保证。
2. **TOCTOU**：`guard.ts` 先 `canonicalPath` 校验、再由 SDK 的 `writeFile` 落盘，中间有窗口。
   工作区里放一个软链，校验时指向工作区内、写入前换成指向 `~`，就写出去了。而这个动作模型自己能编排
   （它手里有 `bash`）：

   ```bash
   ln -sfn /tmp/evil ./a      # 让校验看到工作区内的目标
   # 紧接着 write/edit 命中 ./a
   ```

   Seatbelt 没有这个窗口：路径判定发生在内核、就在那次 `open` 上。

### 8.2 怎么搬

所有工具调用本来就收敛在一个接口上——`ExecutionEnv`（`readTextFile` / `writeFile` / `exec` / `watch` …，
见 `node_modules/@earendil-works/pi-durable/dist/env/index.d.ts`）。文件操作与 shell 都在这个接口上，
所以把**工具执行整体**搬到一个沙箱化的子进程里，接口不用改：

```
Electron main / CLI（不沙箱：联网调模型、写 .data）
  └─ IPC（请求/响应 + 输出分片 + abort）
       └─ tools worker：sandbox-exec 启动，profile 同 Phase 1
            ├─ ExecutionEnv 实现：fs 读写在 worker 内做
            └─ exec：worker 内 spawn（进程树继续受限）
```

父进程把 `ExecutionEnv` 的每个方法代理给 worker；`HarnessOptions.env` 仍返回同一个接口的实现，
`@pi/ext-coding` 与 SDK 的工具代码**一行都不用改**。

### 8.3 收益

- 文件读写也变成内核判定：与应用层是否写错无关（仍然保留 `guard.ts` 作为可读的错误提示与第一道闸）；
- TOCTOU 消失：校验与写入在同一个进程、同一份策略下；
- 一条边界覆盖全部工具，Phase 1 的 profile 直接复用；
- 为将来的「只读模式」「影子文件系统」「写操作审计」留出单点。

### 8.4 代价与要做对的地方

| 事项 | 说明 |
|---|---|
| 进程生命周期 | worker 跟随 Harness 会话创建/关闭；崩溃要 fail closed（工具失败，不是静默重试） |
| fs 走 IPC | `readBinaryFile` / `writeFile` 的大载荷要分片或共享内存；`openDirReader` / `openTextLineReader` 是**流式**接口，需要反向拉取协议 |
| 文件监视 | `watch` 是长期回调，要在 worker 里做并把 change 事件推回来（`NodeWatchOptions` 语义不能变） |
| 取消/超时 | `context.abortSignal` 要能穿过 IPC 传到 worker，并保证 `killProcessTree` 仍然生效 |
| 临时目录 | `createTempDir/createTempFile` 必须落在 profile 允许的 TMPDIR 里 |
| 启动成本 | worker 用 `sandbox-exec` 启动一次、随会话复用；不能每次工具调用起一个进程 |
| 调试 | 工具报错要带上「沙箱拒绝」还是「工具本身失败」的区分，否则排障会很难 |

### 8.5 验收（Phase 2 落地时必须新增）

- 软链竞态用例：校验后替换目标软链，写入必须失败（Phase 1 下这条会失败，正好证明缺口存在）；
- `write` 到工作区外 → EPERM 且错误文案可读；
- 大文件（如 20MB）读写不 OOM、不整段塞进 IPC 单帧；
- `watch` 的文件变更事件延迟与 Phase 1 相当（同量级）；
- abort 后 worker 里没有残留子进程（`ps` 校验）。

## 9. 风险与限制（写清楚，别夸大）

- `sandbox-exec` 是 Apple 的 **deprecated** API，只是**仍然可用**（macOS 26.2 实测）。将来若被移除，方案退化为 §3 的容器/VM 路线；因此探测与失败策略必须一开始就写对。
- Seatbelt 只管**子进程**；进程内工具（`write`/`edit`）的边界仍是应用自己的路径判定，两者要一起测。
- 只拦写与网络时，**读仍然是全局的**：密钥目录可以被 `cat`。要真正挡住，需要 §5 的第二档规则（会连带影响 git/gh 等工具）。
- 沙箱不防「工作区内的破坏」：`rm -rf .` 依然能删掉工作区。这属于审批 + 版本控制（git 快照）的职责。
- Apple Silicon / Intel、不同 macOS 版本上 Seatbelt 规则的支持面可能有差异，需在 CI 或本地至少各跑一次 §4.3 的用例。
