# 子应用构建方案：开发步骤计划

> 关联设计：[子应用构建方案](子应用构建方案.md)
>
> 目标：按 **M1（本机确认的只读能力）→ M2（受控 DSL 界面）→ M3（正式执行隔离）** 的顺序交付。任何阶段都不能把 M1 的静态规则或 smoke 测试描述为安全沙箱。

---

## 0. 实施原则与完成定义

### 0.1 不可突破的边界

- M1 仅接受当前用户在本机对话中生成、并经用户手势确认的候选包；不支持导入、下载、同步或分享第三方 `tool.mjs`。
- M1 只接受只读分析工具：拒绝 `writePaths` 非空、`network=true`、`runsCommands=true` 的候选包；装载器仅注入只读 API。
- M1 正式工具仍会在主进程执行。静态检查、依赖注入和受限 smoke 只降低误用与失败率，**不是** JavaScript 隔离。
- 只有 M3 的 tools worker + Seatbelt capability profile 才能作为权限强制边界。
- 所有 renderer → main 操作都经 `IpcMap`、`IpcRouter`、IPC 白名单以及可信 sender 校验；安装调用只提交一次性 token。

### 0.2 每一阶段的完成条件

| 阶段 | 可交付物 | 不应提前做的事 |
|---|---|---|
| P0 | 已验证的底层 API 与测试尖峰 | 不写正式 manifest 或 UI |
| M1 | 可生成、预览、确认、安装、调用、升级、启停、删除、恢复的只读工具 | 不开放写入、网络、命令、第三方包或子应用 UI |
| M2 | 侧栏入口、受控 DSL 页面、完整 DSL 刷新 action | 不加载外部 React/HTML/JS，不做表达式或 patch 协议 |
| M3 | worker 内正式执行与能力 profile 强制 | 不让未隔离主进程执行成为长期兼容路径 |

## 1. P0：先做四个验证尖峰

> 产出是测试或最小实验，结论回填主设计的“已核实 / 待验证”。P0 未通过，不开始 M1 正式开发。

### P0.1 动态 registry 装卸与下一请求可见性

**涉及代码**

- `packages/core/src/harness/registry.ts`
- `apps/desktop/src/main/runtime.ts`

**步骤**

1. 在测试中创建 registry、安装一个临时 extension、读取 snapshot、卸载 extension、再次读取 snapshot。
2. 用真实 Harness 发两次请求：第一次之前安装，第二次断言工具定义已出现；卸载后断言工具消失。
3. 确认 extension 名冲突、工具名冲突时的实际错误与回滚语义。

**通过标准**

- `Registry.install/uninstall` 会立即反映到新的 snapshot。
- 有明确且可捕获的冲突错误。
- 若同一会话下一请求无法看到新工具，M1 验收文案改为“下次重建 snapshot 后可用”。

### P0.2 durable session 文档的定义、提交与读取

**涉及代码**

- `packages/shared-docs/src/`
- `packages/core/src/harness/`
- 现有 `doc.get` 路由与文档定义

**步骤**

1. 定义一个临时 session 级 kind，验证首次写入、提交、重启后读取和 schema 校验。
2. 验证写入失败时 Harness commit 的错误形式与是否会部分发布。
3. 确认 `app.subapps` 是否能够保存所需结构：`version`、`previousVersion`、`status`、`requestedCapabilities`、`smoke`、`enforcement`。

**通过标准**

- `app.subapps` 的 kind、作用域和读取 API 有明确实现路径。
- 失败行为可被 installer 补偿，不依赖猜测。

### P0.3 `tool.mjs` 在开发态与打包态的导入

**涉及代码**

- `apps/desktop/src/main/runtime.ts`
- Electron 打包配置

**步骤**

1. 从应用数据目录创建最小 `tool.mjs`，采用 `pathToFileURL(file).href + "?v=<version>"` 导入。
2. 验证导出的默认工厂、错误堆栈、升级版本绕过 ESM 缓存。
3. 打包桌面应用，在真实安装包目录外的数据根重复验证，特别检查 asar 路径和文件权限。

**通过标准**

- 开发态、生产打包态都可加载数据目录中的 `.mjs`。
- 失败时只标记当前子应用为 failed，不阻断 `DesktopRuntime.open()`。

### P0.4 smoke 隔离尖峰

**涉及代码**

- `packages/core/src/agent/sandbox.ts`
- `packages/core/src/agent/env.ts`

**步骤**

1. 用临时工作区启动 smoke 子进程，确认能读取该目录、能输出受限结果。
2. 验证网络默认拒绝；验证不能写入工作区外路径。
3. 记录平台差异：现有 Seatbelt 仅覆盖 macOS 时，其他平台必须“失败即不支持 smoke”，不能静默变成无隔离运行。

**通过标准**

- smoke 在隔离不可用时显式失败/跳过并展示原因。
- M1 安装页不将 smoke 成功标为“安全”。

### P0 当前执行记录

可重复执行命令：`pnpm p0:subapps`（实现位于 `packages/core/src/dev/subapp-p0.ts`）。

| 尖峰 | 当前结论 | 状态 |
|---|---|---|
| P0.1 registry | `Registry.install/uninstall` 同步发布新 snapshot；SDK 类型明确工具名可跨 extension 重复，因此“不同子应用工具名不可重复”必须由 SubappLoader 主动校验，不能依赖 registry 拒绝。 | 本地 registry 验证完成；真实 Harness 的下一请求可见性留在装载器接入时 E2E 验证。 |
| P0.2 durable | session 级 `defineDoc` 经 Harness commit 写入 SQLite，关闭后重开可读回。 | 持久化路径已验证；installer 的失败补偿在 M1-3 集成测试验证。 |
| P0.3 ESM | 开发态与真实未签名 macOS 目录安装包均可从 asar 内主进程导入数据目录外 `.mjs`；版本 query 可绕过缓存，语法错误与缺失文件会返回可展示错误。 | 完成；命令：`pnpm p0:subapps:package`。 |
| P0.4 Seatbelt | 通过 `env.exec` 的工作区外写入与网络均被拒绝；但 `ExecutionEnv.writeFile` 在主进程直接成功。 | 完成；结论是 smoke 必须以实际受限子进程执行，绝不能把现有 `api.env` 文件方法当隔离。 |

P0 的本机验证已揭示并固化两个 M1 前置条件：**Loader 必须自己做工具名冲突检测**，且 **smoke runner 必须采用子进程协议**。生产安装包 ESM 验证已经通过，P0 的实现前置验证完成，可以进入 M1-1。

## 2. M1-1：先冻结类型、文件与状态机（进行中）

### M1-1 当前执行记录

已完成基础落点：

- `packages/shared-types/src/subapps.ts`：候选/安装后 manifest、能力申请、状态、预览与版本文件契约；
- `packages/shared-docs/src/subapps.ts`：session 级 `app.subapps` 文档；
- `packages/core/src/paths.ts`：数据根新增 `subapps/`；
- `apps/desktop/src/main/subapps/files.ts`：slug、版本目录、checksum、临时目录原子发布与清理；
- `apps/desktop/src/main/subapps/install-state.ts`：无副作用安装状态机；
- 回归命令：`pnpm m1:subapps:foundation`。

尚未开始：`SubappService`、CandidateStore、静态校验、smoke、registry 装载和 IPC。这些进入 M1-2 / M1-3 / M1-4 后再接入，避免基础契约未冻结前出现跨层调用。

### 2.1 建立公共类型

**建议新增**

- `packages/shared-types/src/subapps.ts`
- 在 `packages/shared-types/src/index.ts` 导出

**定义内容**

- `SubappManifestDraft`：模型候选包允许提供的字段；不接受最终 `version`、`createdAt`、`checksum`、`enforcement`。
- `InstalledSubappManifest`：由安装器补齐最终版本、时间、hash 与 enforcement 后写盘的格式。
- `RequestedCapabilities`、`SubappStatus`、`SubappSmokeResult`。
- `AppSubapp`、`AppSubapps` durable 文档值。
- `SubappPreview`、`SubappListItem`、安装和 action 的 IPC view 类型。

**验收**

- manifest、durable 记录、IPC 返回值没有各自复制一份相似但不同的类型。
- `requestedCapabilities` 与 `enforcement` 分离：前者是申请，后者是实际执行保障。

### 2.2 固定不可变版本目录和 checksum

**建议新增**

- `apps/desktop/src/main/subapps/files.ts`

**实现要点**

1. 目录固定为 `subapps/<slug>/versions/<version>/`。
2. 只允许 slug：`[a-z0-9-]{2,40}`；拒绝内置 extension 名。
3. 安装器分配 `nextVersion`、`createdAt`、`checksum`，不信任 renderer 或模型提交的最终值。
4. hash 算法固定为 `sha256(tool.mjs bytes + "\0" + ui.json bytes-or-empty)`。
5. 写入临时目录后执行同文件系统内 rename；版本目录一经写入不可修改。
6. 实现启动清理：只清理临时目录与不被 durable 记录引用的候选版本，不能误删可回退版本。

**测试**

- slug 路径穿越、非法文件名、文件缺失、hash 不匹配、重复版本、崩溃残留目录。

### 2.3 明确 installer 状态机

```text
idle
  → previewed
  → confirmed
  → staged
  → smoke-passed | smoke-failed-confirmed
  → version-written
  → registry-switched
  → durable-committed
  → ready

任一失败 → compensate → previous-ready | failed
```

**要求**

- 升级时先安装新 extension，成功后才卸载旧 extension。
- durable 记录写入新 `version` 时同步保存 `previousVersion`。
- 文件、registry、durable 不是单事务；每个转移都要有可测试的反向补偿。

## 3. M1-2：候选生成、校验与 smoke（已完成）

### M1-2 当前执行记录

已实现：

- `apps/desktop/src/main/subapps/candidates.ts`：候选内容 hash、内存 TTL、绑定候选 hash / sender / 过期时间 / 单次消费的安装 token；
- `apps/desktop/src/main/subapps/static-validator.ts`：M1 manifest、命名空间、只读能力申请、文件大小、常见高风险标识符与 UI 拒绝；静态规则明确不是安全沙箱；
- `apps/desktop/src/main/subapps/smoke-runner.ts`：临时工作区内的 Seatbelt Node 子进程，执行 factory 创建和最小 `execute` 调用；无 Seatbelt 时明确返回 `skipped`，不降级执行；
- 回归命令：`pnpm m1:subapps:candidate`。

### 3.1 CandidateStore 与 preview

**建议新增**

- `apps/desktop/src/main/subapps/candidates.ts`
- `apps/desktop/src/main/subapps/validator.ts`
- `apps/desktop/src/main/subapps/service.ts`

**实现要点**

1. 主进程接收受结构校验的“候选包”并写入内存 CandidateStore，不直接安装。
2. `preview` 执行 manifest 校验、源码静态检查、规范 checksum 计算及 smoke。
3. 生成随机 `installToken`，并绑定：候选内容 hash、slug、可信 sender 身份、过期时间（60 秒）、一次性使用状态。
4. `install` 只接收 token，主进程按 token 取回 CandidateStore 内容；禁止 renderer 回传 tool 源码或 manifest 覆盖预览。
5. 候选超时、用户取消、安装完成或进程重启后清理。

### 3.2 StaticValidator

**规则**

- 无任何 `import`；单文件不超过 256 KB。
- 拒绝常见高风险标识符：`process`、`require`、`eval`、`Function`、`import(`、`child_process`、`globalThis.process`。
- 工具名必须在 `user.<normalized-slug>.*` 命名空间，且与 manifest 声明一一匹配。
- M1 拒绝写入、网络和命令执行申请。
- 仅把结果描述为“规则检查”，不产生任何安全通过结论。

**注意**

- 静态检查须基于解析器/AST 或保守词法规则实现，不能用脆弱的单个正则替代完整语法处理。
- 即使所有规则通过，安装确认 UI 仍须显示“主进程执行，尚未隔离”。

### 3.3 smoke runner

**实现要点**

1. 在新的临时目录中运行，网络拒绝，30 秒超时。
2. 从临时版本目录导入工厂，校验返回 `{ tools, actions }`。
3. M1 要求 `tools` 非空、`actions={}`；用最小合法参数调用一次工具。
4. 截断输出和错误，保存结构化结果：`passed | failed | skipped`、耗时、简短摘要。
5. smoke 失败默认阻止；二次明确确认才能强制安装，并持久化 `smoke: failed`。

**测试**

- 语法错误、工厂非函数、返回形状错误、工具名不一致、超时、超大输出、最小参数执行异常。

## 4. M1-3：安装、恢复、工具调用与提示词同步（核心后端完成）

### M1-3 当前执行记录

已实现：

- `loader.ts`：启动前复核 checksum / 静态规则，动态导入版本目录 `tool.mjs`，校验 `{ tools, actions }`，并主动拒绝 registry 工具名冲突；
- `installer.ts`：目录发布 → registry 热替换 → durable commit 的切换顺序及失败补偿；
- `service.ts`：预览、确认安装、启停、启动恢复的串行服务；
- `DesktopRuntime.open()`：启动时恢复 `enabled && ready` 的子应用，单项失败标记 failed 而不阻塞应用；
- 回归命令：`pnpm m1:subapps:installer`、`pnpm m1:subapps:service`。

仍待 M1-4：IPC、安装确认 UI、`subapp.changed` 推送，以及基于 registry snapshot 的系统提示词小节。

### 4.1 SubappLoader 与 registry 适配

**建议新增**

- `apps/desktop/src/main/subapps/loader.ts`
- `apps/desktop/src/main/subapps/installer.ts`

**实现要点**

- 使用版本化 URL 动态导入：`import(pathToFileURL(file).href + "?v=" + version)`。
- 通过注入的 `Type` / `defineTool` 创建工具，禁止依赖解析。
- 组装 `createExtension({ name: "subapps:<slug>", tools })`。
- 启动时读取 `app.subapps`：对每项重新校验文件 hash 后再 install；失败写 `status=failed` 和错误摘要，但继续应用启动。
- enable/disable 只能装卸对应 extension；enable 前重新检查 checksum。

### 4.2 接入 DesktopRuntime 和 durable 文档

**修改点**

- `apps/desktop/src/main/runtime.ts`：在 registry 与 Harness 初始化顺序满足依赖后创建 `SubappService`；启动恢复成功后记录 registry 摘要。
- `packages/shared-docs/`：注册 `app.subapps` session 文档定义。
- `packages/core/src/ipc/router.ts`：注入 service 并处理 subapp 路由。

**验收**

- 安装后工具能出现在 registry snapshot。
- 重启后状态为 ready 的版本会恢复；损坏文件进入 failed。
- 升级、禁用、删除都不会影响其他扩展或会话。

### 4.3 系统提示词同步

**建议新增**

- `packages/extensions/coding/src/subapps-context.ts`，或独立的 `@pi/ext-subapps` prompt extension。

**实现要点**

1. 将 `subapps` 与 `projectContextSection` 分开实现和缓存。
2. 渲染时同时读取：`enabled && status=ready` 的 durable 记录，以及当前 `RegistryReader.snapshot()` 中实际存在的工具。
3. 缓存键 = `app.subapps` 内容 hash + registry 工具名 hash。
4. 只输出工具名、标题和简短用法，不复制工具 JSON schema。
5. 安装、升级、启停、删除后失效缓存。

**验收**

- 工具实际存在时才进入 prompt。
- 禁用/装载失败后不会诱导模型调用不存在的工具。

## 5. M1-4：IPC、安装确认和最小前端（已完成）

### M1-4 当前执行记录

已实现完整的“模型提议、用户安装”分离链路：

1. 内置 `subapp.propose` 工具由 Agent 提交候选包；它只能触发静态检查与 smoke，绝不安装；
2. 主进程将 proposal 经 `subapp.proposed` 推送给 renderer；
3. renderer 以 `candidateId` 调 `subapp.preview`，由主进程按可信 sender 签发一次性 token；renderer 不回传源码；
4. `SubappInstallDialog` 展示主进程执行风险、能力申请、规则、smoke 结果与 `tool.mjs` 源码；smoke 失败须再次点击确认；
5. `subapp.install` / `setEnabled` / `remove` 全部经 IPC 类型、白名单与 `IpcRouter` 参数校验；状态变更以 `subapp.changed` 推送；
6. `subapps` 内置 extension 提供独立 PromptSection，以 `app.subapps + RegistryReader.snapshot()` 的交集生成已安装能力摘要。

### 5.1 先扩展类型与 IPC 白名单

**修改点**

- `packages/shared-types/src/ipc.ts`：新增 `subapp.list`、`subapp.preview`、`subapp.install`、`subapp.setEnabled`、`subapp.remove`。
- `apps/desktop/src/main/ipc.ts`：加入 `CHANNEL_LIST`，保持 `MissingChannel` 编译期穷尽检查。
- `packages/core/src/ipc/router.ts`：增加 request schema 校验和 service 调用。
- 推送类型中增加 `subapp.changed`。

### 5.2 Renderer 最小界面

**修改点**

- `apps/desktop/src/renderer/src/`：增加候选预览与安装确认弹层。

**必须展示**

- title、slug、工具名、requested capabilities、源码 diff；
- 静态规则结果与 smoke 结果；
- M1 的“主进程执行，正式执行尚未隔离”固定风险提示；
- smoke 失败时的二次确认；
- 仅由真实点击生成 install 调用，不能由模型文本或页面初始化触发。

### 5.3 M1 端到端验收

1. 用户提出“统计工作区 Markdown 文件数”。
2. Agent 生成符合契约的 `user.md_count.count` 候选包。
3. 用户在预览中看到权限和风险并点击安装。
4. 下一请求中 registry / prompt 均能看到工具；模型可调用它。
5. 重启应用，工具仍被恢复。
6. 禁用后工具从 snapshot 与 prompt 同时消失；再次启用后恢复。
7. 损坏 `tool.mjs` 后重启，子应用标记 failed，不影响主应用启动。

## 6. M2：受控 DSL 界面

### 6.1 先实现 DSL schema 与纯校验器

**建议新增**

- `packages/shared-types/src/subapp-dsl.ts`
- `apps/desktop/src/renderer/src/subapps/dsl-validator.ts`
- 主进程侧复用的同一份 schema 校验器

**规则**

- 组件仅：`card`、`heading`、`text`、`table`、`list`、`button`、`input`、`divider`。
- 属性仅：`type`、`children`、`text`、`columns`、`rows`、`label`、`action`、`placeholder`、`value`、`tone`。
- 最大 64 KB、深度 16、节点 500。
- 不接收 HTML、URL 执行协议、表达式、函数值或未知属性。
- 校验器先于渲染器完成；渲染器永远只接收已验证 DSL。

### 6.2 侧栏、路由与页面

**修改点**

- `apps/desktop/src/renderer/src/` 的应用顶层 view：增加 `subapp:<slug>`。
- 侧栏仅展示 `enabled && status=ready` 的子应用。
- `SubappPage` 通过 `subapp.ui` 获取初始 DSL，再由固定组件集渲染。

### 6.3 action 协议

**实现要点**

1. M2 才允许 `tool.mjs` 返回非空 `actions`。
2. `subapp.action { slug, action, payload, actionId }` 只允许调用当前版本 actions 表中存在的名称。
3. 主进程执行 handler，限制输入、时长和返回大小。
4. handler 只能返回**完整 DSL**；主进程校验成功后推送/响应，renderer 整体替换页面。
5. 使用 `actionId` 去重；动态 DSL 默认仅内存保存，不写 `app.subapps`。

**验收**

- 标签统计子应用出现在侧栏。
- 点击“重新统计”后表格由新的完整 DSL 刷新。
- 未声明 action、超限 DSL、HTML 注入都被主进程拒绝。

## 7. M3：正式执行隔离

### 7.1 建立 tools worker 协议

- 主进程只做调度、超时、结构化日志和结果中转。
- worker 接收固定的工具标识、参数、上下文和有效 capability profile。
- worker 在 Seatbelt 下运行，不能继承主进程的完整 Node 权限。
- worker 崩溃、超时和协议错误必须转换为可观察的 tool error，不重放 `replay: unsafe` 操作。

### 7.2 Capability profile

```text
requestedCapabilities
  + 用户确认
  + 平台支持情况
       ↓
effective capability profile
  ├─ readPaths
  ├─ writePaths
  ├─ network
  └─ runsCommands
```

- worker profile 是唯一可称为“强制”的权限来源。
- M3 才允许申请写入、网络、命令执行。
- 写工作区必须接入既有改动卡片、审查与撤销；不能成为绕过 `file.write` / coding approval 的平行通道。

### 7.3 M3 安全验收

- `readPaths` 外的文件读取失败。
- `writePaths` 外的写入失败。
- `network:false` 时 TCP / DNS / HTTP 均失败。
- `runsCommands:false` 时无法 spawn。
- 沙箱不可用时失败即拒绝，不退化为无沙箱执行。

## 8. 测试矩阵与发布门槛

| 层级 | 必测内容 |
|---|---|
| Unit | manifest、slug、checksum、工具命名、静态规则、DSL、token 生命周期、状态机补偿 |
| Integration | 动态 import、registry 热装卸、durable commit、启动恢复、prompt snapshot 一致性 |
| Electron IPC | 不可信 sender、未知 channel、过期/复用/错 sender token、renderer 篡改安装内容 |
| E2E（M1） | 生成 → preview → 确认 → 安装 → 调用 → 重启恢复 → 禁用/启用/删除 |
| E2E（M2） | 侧栏、DSL 页面、action 刷新、无效 DSL 拒绝 |
| Security（M3） | 路径逃逸、网络、命令、输出/资源限制、worker 崩溃恢复 |

发布前必须满足：

1. M1 安装弹层明确提示“主进程执行、尚未隔离”。
2. IPC 安装仅使用主进程保存的候选包与一次性 token。
3. 升级和安装失败都不会遗失前一可用版本。
4. `app.subapps` 与真实 registry snapshot 不一致时，prompt 以真实 snapshot 为准。
5. M3 前不允许任何第三方子应用分发能力。
