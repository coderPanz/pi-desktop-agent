# packages/core 阅读顺序

**用途**：按「概念递增 + 启动链路」读这一层，而不是按目录字母序。全层 1580 行（含 5 个测试文件），
按下面的顺序大约 1.5–2 小时能读完一轮。

**依据**：core 内部的依赖极浅——**只有一条内部边** `harness/host.ts → harness/open-harness.ts`，
其余 10 个模块只依赖 SDK（`pi-durable` / `pi-ai`）和 `node:*`。所以顺序不能按依赖图定，
只能按概念与运行时顺序（`storage → open → resume → root`）定。

> 行号锚定于本文写作时的代码状态。代码改动后以**符号名**为准，用 `grep -n "<符号>" <文件>` 重新定位。

## 第 1 轮：先看测试，不要先看实现（10 分钟）

```
packages/core/src/session/manager.test.ts:16-23
```

```ts
async function openFixture() {
  const storage = new MemoryStorage()
  const models = createModels({ credentials: new InMemoryCredentialStore() })
  const registry = createPiRegistry()
  const host = await HarnessHost.open({ storage, models, registry })
  const manager = await SessionManager.open({ harness: host.harness, storage })
  return { storage, host, manager }
}
```

**这 6 行就是整个 core 的最小装配**，也是唯一能立刻跑起来的部分（`pnpm test`，不联网、不需要 `.env`）。
先建立这个骨架，后面每个模块都是往这 6 行里填一块。

再读同文件的 `appendNote()`（`manager.test.ts:28-36`）：用一条**被动条目**（`type: "write"`）就能验证
fork / reset / 分帧而不碰模型——这是理解「哪些操作不需要模型」的最快方式。

## 两条实用建议

**如果目的是排查桌面端问题**：反着读——`index` → `manager` → `frame-hub` → `host` → `open-harness`。
这条路径对应「用户看到的现象怎么落到某个 commit」。

**当前阶段可以最后读**：`agent/env.ts` 与 `dev/crash-point.ts`。前者只在工具调用时才用到（S2 落地后），
后者只在 S4 制造崩溃时才用。

## 不要期待的东西

这一层没有任何 `interface` / 抽象基类——因为项目约定是「没有第二个实现就不建接口」。
`SessionManager`、`HarnessHost`、`FrameHub` 都是具体类；`Storage` / `Harness` / `WatchHandle` 这类接口
来自 SDK，不在 core 里定义。
